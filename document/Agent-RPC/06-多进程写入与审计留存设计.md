# 06 · 多进程写入与审计留存设计

> 文档性质：**设计规范（待实现）**，不是实现说明。

## 0. 结论摘要

1. **当前文件 store 没有跨进程互斥**：8 个 store 中 5 个是"读全量 → 改 → 重写全量"（tasks / sessions / approvals / budget / idempotency），3 个是追加（receipts / audit / events）。两个 CLI 进程同时写同一 `~/.syaocode/arf/<tenant>/` 会丢更新、把审计链写出分叉、把预算预留覆盖掉。
2. **只加一把"进程内"锁不够**：现有 `BudgetLedger` 的串行化是进程内 `Promise` 队列（`budget.ts:49-80`），跨进程无效；现有 `FileSessionStore.withLock` 是无心跳、无 FIFO、无 fencing 的 `mkdir` 自旋锁，崩溃后会留下永久锁目录。
3. **本设计给出"租户目录写租约（Tenant Directory Write Lease）"**：同一租户目录同一时刻只有一个写者；写者持租约期间完成一组写；**每次拿到租约后先 `stat` 文件指纹，变化则重读**，再改再写，杜绝脏读/丢更新。
4. **写入顺序由"工作内容 + coding 层次 + 优先级"三元组决定**；**默认策略是严格的先来先写（FIFO）**，只有显式声明更高优先级的安全/证据写入可以插队；等待过久会老化提权，避免饿死。
5. **审计留存**采用分段（segment）+ manifest：按大小/时间/条数轮转，按天数/总字节/最少段数清理；清理保留 `lastHash` 与 `count`，链可跨段验证；删除动作本身写 tombstone。
6. **`detailHash`** 用内容寻址的 sidecar 保存脱敏后的明细，事件只带哈希；`audit verify --details` 可独立校验。
7. **吞吐**目标分层：内存 ≥200 inv/s、文件+批量 fsync ≥100 inv/s、文件+逐条 fsync ≥30 inv/s；三者都要有可执行基准，而不是只测延迟。

## 1. 术语、范围与不变量

### 1.1 术语

| 术语 | 含义 |
| --- | --- |
| **租户目录（tenant dir）** | `~/.syaocode/arf/<tenantId>/`，一个租户的全部治理记录 |
| **写租约（write lease）** | 跨进程互斥锁；同一租户目录同一时刻最多一个持有者 |
| **租约纪元（epoch）** | 单调递增的 fencing token；每次获取/接管 +1；写者每次落盘前校验 |
| **票据（ticket）** | 排队条目，含 `priority / layer / workKind / seq / enqueuedAt` |
| **写组（write group）** | 一次逻辑操作产生的多条写（一次 invocation 的预算结算/回执/审计/事件/任务状态） |
| **指纹（fingerprint）** | 文件的 `{mtimeMs, size}`；用于判断是否需要重读 |
| **分段（segment）** | 审计日志按大小/时间切分后的单个文件 |
| **manifest** | 审计分段的元数据清单，记录每段的首尾哈希、条数、状态 |

### 1.2 范围

**包含**：

- `packages/rpc/src/runtime/file-stores.ts` 的 8 个 store；
- `packages/node/src/stores.ts` 中同形状的文件 store（如仍被使用，必须复用同一锁协议，不能各写一套）；
- `Runtime.fs` 需要新增的 `rename` / `fsync` 能力；
- 审计留存、轮转、`detailHash`、吞吐基准。

**不包含**：

- 分布式（跨主机）锁：本设计只支持**本机文件系统**。NFS/SMB 的 `mkdir`/`rename` 语义不保证原子，明确不支持（见 §13）；
- 多租户共享目录：一个租户一个目录，租户之间不共享锁；
- 企业控制面：按 anti-roadmap 不做。

### 1.3 不变量（实现与测试的硬门禁）

| ID | 不变量 | 违反后果 |
| --- | --- | --- |
| **W1** | 同一租户目录同一时刻最多一个写租约持有者 | 丢更新、链分叉 |
| **W2** | 每次获取租约后、任何写之前，必须重新读取目标文件（指纹变化则重载） | 用陈旧内存覆盖别人刚写的记录 |
| **W3** | 重写型文件必须 `tmp → fsync → rename` 原子替换；不得原地 `writeFile` | 断电/崩溃留下半文件 |
| **W4** | 追加型文件每行必须是完整 JSON；读取时只允许忽略"最后一行不完整" | 半行污染后续解析 |
| **W5** | 审计/回执链在跨进程下不得分叉：`prevHash` 必须是当前链头 | 证据链失效 |
| **W6** | 写者每次落盘前校验 `epoch`；不一致立即 abort（`LEASE_LOST`） | 被接管的僵尸写者覆盖新数据 |
| **W7** | 默认顺序 = **FIFO**（同优先级按票据 `seq`）；只有显式声明的更高优先级可插队 | 不可预测的写入顺序 |
| **W8** | 任何写者等待不得超过 `lockTimeoutMs`（默认 10s）；超时返回 `STORE_LOCKED`，不得无限自旋 | CLI 挂死 |
| **W9** | 持锁期间不得进行网络/模型/子进程调用；单次持锁 ≤ `maxHoldMs`（默认 2s） | 全局写停顿 |
| **W10** | 读路径不加写锁，但必须能容忍"读到旧版本"；跨文件一致性由快照读提供 | 读阻塞写 / 读到半文件 |
| **W11** | 轮转/清理/checkpoint 与普通写共用同一租约；后台任务用 `tryAcquire`，忙则跳过 | 维护操作与业务写互相破坏 |
| **W12** | 锁等待、持锁、接管、丢失都产生可观测指标与审计事件 | 无法定位"为什么慢/为什么丢" |

### 2.2 七个可复现的故障

| # | 故障 | 交错（两个进程 A/B） | 后果 |
| --- | --- | --- | --- |
| **F1** | 丢更新 | A 读 tasks.jsonl（含 T1）→ B 追加 T2 → A 用 "T1 + 自己的修改" 重写 → T2 消失 | 任务丢失 |
| **F2** | 预算超支 | A 读 budget（reserved=0）→ B 读 budget（reserved=0）→ A 预留 $0.6（写 0.6）→ B 预留 $0.6（写 0.6） | 两个 $0.6 对 $1 限额都通过；账本只记 0.6 |
| **F3** | 重复审批 | A/B 都持有 `pending` 副本 → 各自 `decide` → 各自 `persist` | 同一审批被批准两次；后写覆盖先写 |
| **F4** | 审计链分叉 | A/B 都读到 `lastHash=H0` → A 追加 `H1=H(H0+e1)` → B 追加 `H1'=H(H0+e2)` | 同一租户出现两条链，`verify` 必失败 |
| **F5** | 事件 seq 重复 | A/B 对同一 task 都从 `lastSeq+1` 开始 → 都写 `seq=9` | 事件流出现重复/乱序 |
| **F6** | 半写文件 | A 用 `writeFile` 重写 budget.json 时被 kill → 文件截断 | 下次启动 `JSON.parse` 失败，整个租户不可用 |
| **F7** | 僵尸写者 | A 持锁被 SIGSTOP 超过 TTL → B 接管 → A 恢复后继续写 | 覆盖 B 的新数据 |

> 这七个故障覆盖了用户所说的"实际使用中最可能咬人"的场景：**多人/多终端同时用同一个工作区**、**CI 与本地 CLI 并发**、**editor 与 CLI 同时写**。

## 3. 锁模型：租户目录写租约

### 3.1 为什么是"目录级"而不是"文件级"

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 每文件一把锁 | 并发度高 | 一次 invocation 要写 4~6 个文件，需要多锁；死锁/顺序/回滚复杂；审计链与回执链跨文件 | ❌ |
| **每租户目录一把写租约** | 一次写组内所有文件天然一致；无死锁；顺序可全局调度 | 写吞吐受单写者限制 | ✅ 本设计 |
| 全局一把锁 | 最简单 | 多租户互相阻塞 | ❌ |

> 读不受写租约阻塞（见 §5.4）；写是短临界区（目标 p95 ≤ 3ms），单写者足够支撑 200 inv/s（§9）。

### 3.4 获取算法（伪代码）

```ts
async function acquireLease(opts: LeaseOptions): Promise<WriteLease> {
  await mkdirp(`${dir}/.write/queue`);
  const ticket = {
    ticketId: ids.next('tkt'),
    seq: await nextTicketSeq(),            // 见 §3.6
    priority: opts.priority,               // 默认 P3
    workKind: opts.workKind,               // 默认 execution
    layer: opts.layer,                     // 默认 L2
    intent: opts.intent,
    enqueuedAt: nowIso(),
    expiresAt: new Date(Date.now() + timeoutMs).toISOString(),
  };
  await writeJson(`${queue}/${ticket.ticketId}.json`, ticket);

  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const tickets = await readQueue();      // 解析失败/过期 → 移除并记录
    tickets.sort(compareTickets);           // priority 升序 → seq 升序
    if (tickets[0]?.ticketId !== ticket.ticketId) {
      await sleep(20 + jitter(0, 30));      // 退避，避免 thundering herd
      continue;
    }
    try {
      await mkdir(`${dir}/.write/lease`);   // 原子：已存在则抛错
      const epoch = await bumpEpoch();      // read .write/epoch + 1 → write
      await writeJson(`${dir}/.write/lease/owner.json`, { ...ticket, epoch, heartbeatAt: nowIso(), ttlMs });
      return new Lease(ticket, epoch);      // 启动 heartbeat
    } catch (e) {
      const owner = await readOwner();
      if (owner !== undefined && Date.now() - Date.parse(owner.heartbeatAt) > owner.ttlMs) {
        await takeOver(owner, ticket);      // 见 §3.5
        continue;
      }
      await sleep(20 + jitter(0, 30));
    }
  }
  await removeTicket(ticket);
  throw new StoreLockedError({ ticket, waitedMs: timeoutMs });  // W8
}
```

### 3.5 接管（takeover）与 fencing

```ts
async function takeOver(old: LeaseOwner, next: Ticket): Promise<void> {
  // 1) 把旧租约目录改名为“墓碑”，保留证据
  await rename(`${dir}/.write/lease`, `${dir}/.write/lease.stale.${old.leaseId}`);
  // 2) 纪元 +1：旧持有者从此刻起所有写都会被拒
  const epoch = await bumpEpoch();
  // 3) 新持有者建立自己的租约
  await mkdir(`${dir}/.write/lease`);
  await writeJson(`${dir}/.write/lease/owner.json`, { ...next, epoch, heartbeatAt: nowIso() });
  // 4) 记录接管审计（谁、为什么、旧租约活了多久）
  await appendMetric({ type: 'lease.takeover', oldLeaseId: old.leaseId, oldPid: old.pid, epoch });
  // 5) 清理旧墓碑（保留最近 N 个，便于排障）
}
```

**为什么必须有 fencing**：仅靠"删除锁目录"无法阻止一个被 SIGSTOP 的旧持有者在恢复后继续写。`epoch` 是唯一能证明"你还是当前写者"的凭证。

**写前校验**（每个 store 的每个落盘动作）：

```ts
async function assertLease(lease: WriteLease): Promise<void> {
  const current = Number(await fs.readFile(`${dir}/.write/epoch`, 'utf8'));
  if (current !== lease.epoch) throw new LeaseLostError({ expected: lease.epoch, actual: current });
}
```

> 校验必须紧贴 `rename`/`appendFile`，不能只在获取时校验一次。

### 3.6 票据序号（FIFO 的基石）

`seq` 必须在跨进程下单调，否则"先来"无法定义。用一个**极短的序号锁**：

```ts
async function nextTicketSeq(): Promise<number> {
  const lock = `${dir}/.write/seq.lock`;
  for (;;) {
    try { await mkdir(lock); break; }
    catch { await sleep(5); }
  }
  try {
    const current = Number(await readOr(`${dir}/.write/seq`, '0')) || 0;
    const next = current + 1;
    await writeFile(`${dir}/.write/seq`, String(next));   // 小文件，写失败可重试
    return next;
  } finally {
    await rmdir(lock);
  }
}
```

- `seq.lock` 只保护"取号"，持锁 <1ms；不参与业务写。
- 如果 `seq` 文件损坏/丢失：从 `max(queue.seq)+1` 恢复，并记录 `seq.recovered` 审计。
- `seq` 不必与审计链的 `count` 一致：前者是排队序号，后者是链内计数。

### 3.7 心跳与失效判定

- 持有者每 `ttlMs/3`（默认 ~1.6s）更新 `owner.json.heartbeatAt`。
- 等待者判断：`now - heartbeatAt > ttlMs` → 可接管。
- **没有 pid 探活**（`Runtime` 不提供跨平台 `kill(pid,0)`；且容器/远程文件系统 pid 不可比）。因此：
  - 进程被 SIGKILL → 心跳停止 → TTL 后接管；
  - 进程被 SIGSTOP 超过 TTL → 被接管；恢复后 `epoch` 校验失败 → `LEASE_LOST`，写者必须**放弃本次写并重新走完整流程**（不能"续写"）；
  - 时钟回拨：心跳用 `Date.now()` 可能受系统时间影响；建议用 `performance.now()` 的单调时钟做本地判断，`heartbeatAt` 仅作展示。设计上要求 `Runtime.clock` 提供 `monotonicNow()`（新增可选能力），否则用"每次心跳自增计数 + 文件 mtime"作为兜底。
- 接管规则：**只允许接管已过 TTL 的租约**；接管前必须把旧租约重命名为墓碑，不能直接删。

### 3.8 释放

```ts
async function release(lease: WriteLease): Promise<void> {
  stopHeartbeat(lease);
  if (await currentEpoch() === lease.epoch) {
    await flushDirtyBuffers();               // 见 §4.4
    await unlink(`${dir}/.write/lease/owner.json`);
    await rmdir(`${dir}/.write/lease`);
  } else {
    // 已被接管：只清理自己的票据，绝不碰别人的租约
  }
  await removeTicket(lease.ticketId);
  await appendMetric({ type: 'lease.released', heldMs: ... });
}
```

### 3.9 崩溃恢复

启动时（`FileStoreBundle.open()`）：

1. 若 `lease/` 存在且心跳未过期 → 说明另一个进程正在写：**只读模式启动**，写操作排队等待；不抢占。
2. 若 `lease/` 存在且心跳过期 → 走接管流程（相当于一个空写组），然后继续。
3. 清理 `queue/` 中 `expiresAt` 已过的票据；保留未过期的。
4. 检查 `.write/epoch` 是否可解析；损坏则从墓碑/租约的最大 epoch 恢复，并记录 `epoch.recovered`。
5. 检查 `*.tmp.*` 残留：删除（它们从未被 rename，不是有效数据）。
6. 检查追加文件的最后一行是否完整；不完整则截断到最后一条完整记录，并写 `store.torn_tail_recovered` 审计。

## 4. 重读规则：Read-After-Acquire

### 4.1 规则（用户明确要求）

> **每次解锁后、其他进程上锁之前，必须重新读一遍这个文件，同步更新，防止并发脏读。**

规范化为 W2：

1. 获取租约成功后，**立即**对本次写组涉及的每个文件做 `stat`；
2. 与内存中的 `fingerprint` 比较；不同 → **全量重读 + 重新校验**；
3. 重读成功后才允许应用本次变更；
4. 写入完成后更新 `fingerprint`；
5. 释放租约；下一个写者重复 1-4。

### 4.2 指纹

```ts
interface StoreFingerprint {
  mtimeMs: number;
  size: number;
  /** 可选：内容哈希（仅审计/回执链，代价高，按需开启） */
  contentHash?: string;
}
```

- `stat` 在 `Runtime.fs` 已存在（`FileStat` 含 `size/mtimeMs`）。
- 对**审计/回执**这类链式文件，额外校验链头：`lastHash` 必须等于内存中的 head；不等 → 全量重建。
- 对**重写型**文件（tasks/sessions/approvals/budget/idempotency）：`mtimeMs/size` 变化 → 全量重读。
- 若 `stat` 报 ENOENT（首次创建）：视为空状态，不算错误。

### 4.3 各 store 的重读策略

| Store | 文件形态 | 重读策略 | 校验 |
| --- | --- | --- | --- |
| tasks | JSONL，整文件重写 | 全量重读，按 `id` 后写覆盖 | 状态机合法（`canTransitionTask`） |
| sessions | JSONL，整文件重写 | 全量重读 | `tenantId` 一致 |
| approvals | JSONL，整文件重写（追加新版本） | 全量重读，按 `id` 取最新 revision | revision 单调；终态不可再改 |
| budget | 单 JSON，整文件重写 | 全量重读，重建 accounts + reservations | `reservedUsd >= 0`；账户限额 |
| idempotency | JSONL，整文件重写 | 全量重读 | key 唯一；`completed` 不可回退 |
| receipts | JSONL，追加 | 读尾部；head 哈希变化则全量 | 回执链逐环 |
| audit | JSONL，追加（或分段） | 读尾部；head 哈希变化则全量/跨段 | 审计链逐环 + checkpoint |
| events | JSONL，追加 | 读尾部；按 task 重建 `lastSeq` | `seq` 连续 |

### 4.4 读路径

- **普通读**：不加锁；先 `stat`，指纹变了就重读；否则用缓存。读到的可能是"上一毫秒"的快照，这是允许的（W10）。
- **一致性读**（`audit verify`、`evidence seal`、`rpc status`）：优先取**读快照**：
  - 读 `manifest.json` + 当前 segment 的 `size`；
  - 只读到该 `size` 为止（忽略之后追加的字节）；
  - 若读的过程中发生轮转，重试一次。
- **半写防护**：重写型文件用 `tmp + rename`，读永远看到旧文件或新文件；追加型文件只可能"最后一行不完整"，读取时截断到最后一条完整 JSON，并记录 `tornTail`。
- **不得**在读取时自动修复/覆盖文件（除 §3.9 的启动恢复）；读路径必须无副作用。

### 4.5 替换 `loaded` 标志

现有实现：

```ts
let loaded = false;
const ensureLoaded = async () => { if (loaded) return; loaded = true; memory.hydrate(...); };
```

改为：

```ts
let fingerprint: StoreFingerprint | undefined;
let hydrating: Promise<void> | undefined;
async function ensureFresh(): Promise<void> {
  const st = await statOrUndefined(path);
  const next = st === undefined ? undefined : { mtimeMs: st.mtimeMs, size: st.size };
  if (sameFingerprint(fingerprint, next)) return;
  // 单飞：同一进程内的并发读只重读一次
  hydrating ??= (async () => {
    memory.reset();
    memory.hydrate(parseAll(await readLines(path), label));
    fingerprint = next;
  })().finally(() => { hydrating = undefined; });
  await hydrating;
}
```

> `memory.reset()` 需要各 Memory store 提供；这是实现时的小改动。若不提供，则新建一个 Memory store 实例替换。

## 5. 写入顺序策略

### 5.1 三个维度

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| **工作内容（workKind）** | `safety` / `evidence` / `governance` / `execution` / `telemetry` / `maintenance` | 这次写的是什么 |
| **coding 层次（layer）** | `L0` 决策面 / `L1` 生成面 / `L2` 动作面 / `L3` 证据与审计（横切） | 这次写属于哪一层 |
| **优先级（priority）** | `P0` ~ `P5` | 具体排序权重 |

### 5.2 默认策略：先来先写（FIFO）

**规范**：

- 若调用方没有显式声明 `priority/layer/workKind`，一律使用 `DEFAULT_WRITE_INTENT = { workKind: 'execution', layer: 'L2', priority: P3 }`。
- 所有默认写入的 `priority` 相同 → 严格按票据 `seq` 升序，即 **FIFO**。
- FIFO 是**默认且推荐**的策略；优先级只用于"安全/证据"这类不能等的写，不是给普通业务写插队的借口。

### 5.3 优先级表

| 级别 | 值 | workKind | layer | 典型写入 | 是否可插队 |
| --- | --- | --- | --- | --- | --- |
| **P0** | 0 | `safety` | L0 | 策略拒绝、租户越权、危险命令拦截、审批拒绝 | 是（最高） |
| **P1** | 10 | `evidence` | L3 | 回执封存、审计追加、Evidence Bundle | 是 |
| **P2** | 20 | `governance` | L0/L2 | 审批决策、预算预留/结算、幂等状态 | 是（仅高于 P3+） |
| **P3** | 30 | `execution` | L1/L2 | 任务状态、会话更新、事件流 | 默认，不插队 |
| **P4** | 40 | `telemetry` | L1 | usage、registry 健康、投影刷新 | 否 |
| **P5** | 50 | `maintenance` | — | 轮转、清理、checkpoint、压缩 | 否（且用 `tryAcquire`） |

**规则**：

1. 只有 `safety` 可以声明 P0；只有 `safety/evidence` 可以声明 P0/P1。其他 workKind 声明 P0/P1 会被拒绝（`INVALID_WRITE_INTENT`）并降级到其允许的最高级别。
2. 同一 `priority` 内严格按 `seq`；不同 `priority` 先按 `priority` 升序。
3. `P4/P5` 不得阻塞 `P0-P3`：它们只在队列为空或等待超过 `maintenanceDelayMs`（默认 30s）后执行。
4. **老化（aging）**：等待超过 `agingMs`（默认 2000ms）→ 提升一级（数值 -10），最多提升 2 级；P0 不参与老化；P5 最多升到 P3。老化在每次循环重新计算，不改写票据文件（避免额外写）。
5. **禁止**在持有租约时：
   - 调用模型/网络/子进程；
   - 获取第二个租户目录的租约（跨租户写必须拆成两个独立写组）；
   - 递归调用会再次 `acquire` 的 store 方法（用 `WriteSession` 复用租约，见 §5.6）。

### 5.4 写组（write group）与组内顺序

一次 invocation 的写组固定顺序（先钱、后证据、后审计、后事件、后状态、后幂等）：

```text
1. budget.settle / release        （金额先落，避免"有回执没结算"）
2. receipts.put                   （回执链）
3. audit.append                   （审计链）
4. events.append                  （事件流）
5. tasks.put / sessions.put / approvals.decide  （状态）
6. idempotency.complete / fail    （去重状态最后）
```

理由：崩溃恢复时，`receipt` 存在但 `audit` 缺失 → 可以用 receipt 补审计；反之则无法证明副作用。组内任何一步失败 → 整个写组失败，租约释放，调用方重试；已写入的前序记录由恢复逻辑补齐（`reconcile`）。

### 5.5 写租约 API（草案）

```ts
type WorkKind = 'safety' | 'evidence' | 'governance' | 'execution' | 'telemetry' | 'maintenance';
type Layer = 'L0' | 'L1' | 'L2' | 'L3';

interface WriteIntent {
  workKind?: WorkKind;       // 默认 'execution'
  layer?: Layer;             // 默认 'L2'
  priority?: 0 | 10 | 20 | 30 | 40 | 50;  // 默认 30
  reason?: string;           // 声明高优先级时必填
}

interface WriteLease {
  readonly epoch: number;
  readonly ticketId: string;
  assertHeld(): Promise<void>;       // 写前校验
  release(): Promise<void>;
}

function withWriteLease<T>(
  stores: FileStoreBundle,
  tenantId: string,
  intent: WriteIntent,
  fn: (lease: WriteLease, tx: WriteSession) => Promise<T>,
): Promise<T>;
```

`WriteSession` 提供 `tasks / sessions / approvals / budget / idempotency / receipts / audit / events` 的同名方法，但**复用同一个租约**，不会再次取锁。

### 5.6 与 agent 的约定

- agent 在**发起一次受治理调用前**声明 `WriteIntent`（由 `dispatcher` 根据结果类型决定，不靠模型自述）：
  - 策略拒绝 → `safety/P0`
  - 回执/审计 → `evidence/P1`
  - 审批/预算 → `governance/P2`
  - 任务/事件 → `execution/P3`
  - usage/健康 → `telemetry/P4`
- agent **不得**用"我觉得重要"来声明 P0；`reason` 必须来自可验证的上下文（如 `policy.denied`、`tenant.mismatch`），并写入审计。
- 默认（没有声明）→ FIFO；这正是用户要求的"默认先来先写"。

### 5.7 顺序的可观测性

每次写组记录：

```json
{
  "type": "write.group",
  "tenantId": "acme",
  "ticketId": "tkt_...",
  "priority": 10,
  "layer": "L3",
  "workKind": "evidence",
  "enqueuedAt": "...",
  "startedAt": "...",
  "endedAt": "...",
  "waitMs": 1.2,
  "holdMs": 0.8,
  "files": ["receipts.jsonl", "audit.jsonl", "events.jsonl", "tasks.jsonl"],
  "aged": false,
  "epoch": 42
}
```

指标（见 §10）：`arf_write_wait_ms{p50,p95,p99}`、`arf_write_hold_ms`、`arf_write_queue_depth`、`arf_write_priority_total{level}`、`arf_write_aged_total`、`arf_write_group_failures_total`。

## 6. 原子写与崩溃一致性

### 6.1 `Runtime.fs` 需要新增的能力

当前 `FileSystem` 只有 `readFile/writeFile/appendFile/stat/readdir/realpath/mkdir/rmdir/unlink/exists`，**没有 `rename`、没有 `fsync`**。本设计需要：

```ts
export interface FileSystem {
  // ... existing
  /** Atomic rename (same filesystem). Used for tmp→target replacement. */
  rename(from: string, to: string): Promise<void>;
  /** Flush a file's data to stable storage. Optional: memory hosts may no-op. */
  fsyncFile?(path: string): Promise<void>;
  /** Flush a directory entry (rename durability). Optional. */
  fsyncDir?(path: string): Promise<void>;
  /** Monotonic milliseconds, unaffected by wall-clock changes. Optional. */
  monotonicNow?(): number;
}
```

- `NodeFileSystem`：`fsp.rename`、`fsync`（open + `fh.sync()`）、目录 fsync。
- `MemoryRuntime`：`rename` 直接改 Map；`fsync*` no-op；`monotonicNow` 用 FakeClock。
- 若宿主未实现 `rename`：**降级为 `writeFile` 并标记 `atomic=false`**，同时在启动时打印一次警告；审计/回执这类链式文件**不允许**降级（直接拒绝启动持久化模式）。

### 6.2 重写型文件

```ts
async function writeAllAtomic(fs, path, values): Promise<void> {
  const tmp = `${path}.tmp.${process.pid}.${lease.epoch}`;
  await fs.writeFile(tmp, serialize(values));
  await fs.fsyncFile?.(tmp);
  await fs.rename(tmp, path);          // 同一目录内原子替换
  await fs.fsyncDir?.(dirOf(path));
}
```

### 6.3 追加型文件

```ts
async function appendLine(fs, path, value, lease): Promise<void> {
  await lease.assertHeld();
  const line = `${JSON.stringify(value)}\n`;
  await fs.appendFile(path, line);
  // 批量 fsync 模式：标记 dirty，由 lease release 或每 100ms flush 一次
  await maybeFsync(fs, path);
}
```

- 单行必须 < `maxRecordBytes`（默认 1 MiB）；超过 → 拒绝（`RECORD_TOO_LARGE`），避免半行。
- 读取时若最后一行不是完整 JSON：只允许忽略最后一行（`tornTail`），并记录；若中间行损坏 → `STORE_CORRUPT`，fail-closed。

### 6.4 崩溃点矩阵

| 崩溃点 | 结果 | 恢复 |
| --- | --- | --- |
| 写 tmp 中 | tmp 残留，目标未变 | 删除 tmp |
| tmp 写完、rename 前 | 同上 | 删除 tmp |
| rename 后、fsyncDir 前 | 目标可能是新内容，目录项可能未持久化 | 重启后以目标文件为准；不能确定时用 journal |
| append 半行 | 最后一行不完整 | 截断最后一行；审计记录 |
| 持锁中崩溃 | 租约残留 | TTL 后接管 |
| 写组第 2 步后崩溃 | 回执已写、审计未写 | `reconcile` 用回执补审计 |

### 6.5 可选 journal

对"跨文件写组"提供更强的恢复：

```jsonl
{"type":"begin","groupId":"grp_...","files":["receipts.jsonl","audit.jsonl","events.jsonl","tasks.jsonl"],"at":"..."}
{"type":"commit","groupId":"grp_...","at":"..."}
```

- 启动时扫描未 commit 的 group：按 `receipts/audit` 的实际链头判断已写到哪一步，补齐或标记 `indeterminate`；
- journal 本身也走 append + 租约；默认开启（成本低），可配置关闭。

> 本设计**不追求跨文件事务的 ACID**，只保证：**不会因崩溃产生分叉链/半文件/丢更新**；跨文件一致性由"回执优先、审计可补"的 reconcile 保证。

## 7. 审计留存与轮转

### 7.1 现状

- `audit.jsonl` 单文件无限增长；
- `checkpointEvery=64` + `checkpointIntervalMs=5min`（CLI 默认）；
- 无 retention、无轮转、无 manifest；
- 多进程下追加会分叉（§2 F4）。

### 7.2 分段模型

启用分段后：

```text
<tenantDir>/audit/
  manifest.json
  segments/
    000001.jsonl
    000002.jsonl
    ...
```

`manifest.json`：

```json
{
  "version": 1,
  "tenantId": "acme",
  "segmentSeq": 2,
  "segments": [
    {
      "id": "000001",
      "file": "segments/000001.jsonl",
      "firstSeq": 1,
      "lastSeq": 10000,
      "count": 10000,
      "firstPrevHash": "",
      "lastHash": "sha256:...",
      "bytes": 8388608,
      "openedAt": "2026-10-01T00:00:00.000Z",
      "sealedAt": "2026-10-02T00:00:00.000Z",
      "state": "sealed"
    },
    {
      "id": "000002",
      "file": "segments/000002.jsonl",
      "firstSeq": 10001,
      "lastSeq": 12000,
      "count": 2000,
      "firstPrevHash": "sha256:...",
      "lastHash": "sha256:...",
      "bytes": 1677721,
      "openedAt": "2026-10-02T00:00:00.000Z",
      "sealedAt": null,
      "state": "active"
    }
  ],
  "checkpoints": [
    { "at": "...", "count": 12000, "lastHash": "sha256:...", "checkpointHash": "sha256:..." }
  ],
  "updatedAt": "..."
}
```

### 7.3 轮转

触发条件（任一）：

- 当前段 `bytes >= rotationBytes`（默认 64 MiB）；
- 当前段 `openedAt` 超过 `rotationIntervalMs`（默认 24h）；
- 当前段 `count >= rotationCount`（默认 100,000）；
- 手动 `syao rpc audit rotate`。

流程（在租约内）：

1. `fsync` 当前段；
2. 计算 `lastHash`、`count`；
3. 更新 manifest：当前段 `state:"sealed"`、`sealedAt`；
4. 新建 `00000N+1.jsonl`，`firstPrevHash = lastHash`，`state:"active"`；
5. 写 `audit.rotated` 审计事件（在新段）。
6. 失败则回滚 manifest（保留旧段 active），不得出现两个 active。

### 7.4 保留与清理

配置：

```ts
interface AuditRetentionPolicy {
  retentionDays?: number;        // 默认 30；0 = 不按时间删
  maxTotalBytes?: number;        // 默认 512 MiB；0 = 不按大小删
  minSegments?: number;          // 默认 2；永远保留最近 N 段
  maxSegments?: number;          // 默认 512；硬上限
}
```

清理顺序（在租约内，`tryAcquire` 失败则跳过本次）：

1. 候选 = `state:"sealed"` 且不是"含最新 checkpoint 的段"且不是最近 `minSegments` 段；
2. 按 `sealedAt` 从旧到新；
3. 删除条件：`age > retentionDays` **或** `totalBytes > maxTotalBytes` **或** `segments > maxSegments`；
4. 先写 tombstone 到 manifest：`state:"pruned"`, `prunedAt`, 保留 `firstSeq/lastSeq/count/firstPrevHash/lastHash`；
5. 再 `unlink` 文件；
6. 写 `audit.pruned` 审计事件（当前段），包含被删段的 `lastHash` 与 `count`。

**为什么保留 `lastHash`**：跨段链验证只需要"上一段最后的哈希"，不需要重新读取被删内容。这样 `verify` 能证明"链没有断"，但不能证明"被删内容未被篡改"——所以清理必须同时保留 checkpoint（外部锚点）与 tombstone。

### 7.5 验证语义

`AuditStore.verify(tenantId)` 返回扩展结果：

```ts
interface AuditVerifyResult {
  ok: boolean;
  checked: number;           // 实际重算的段内条数
  pruned: number;            // 已清理段数（只验证链接，不重算内容）
  brokenAt?: string;
  reason?: string;
  checkpoints: number;
  details: 'ok' | 'missing' | 'mismatch';
}
```

规则：

- 未清理段：逐条重算哈希 + `prevHash` 链接；
- 已清理段：只校验 `firstPrevHash === prev.lastHash` 与 `count/lastHash` 是否被后续 checkpoint 覆盖；
- 若 `details: true` 且 sidecar 缺失 → `details:'missing'`，不算链断，但 `ok` 仍为 true（可配置为严格失败）。

### 7.6 导出

```bash
syao rpc audit export --from 2026-10-01 --to 2026-10-31 --out audit-bundle.tar
```

Bundle 内容：

- `manifest.json`（含 tombstone）
- 未清理的 segment 文件
- `checkpoints.jsonl`
- `details/`（可选）
- `README.txt`（如何验证）

验证：

```bash
syao rpc audit verify --bundle audit-bundle
```

### 7.7 多进程下的轮转/清理

- 与普通写共用同一租户租约；
- 后台任务用 `tryAcquire(0)`：拿不到就跳过，下一周期再试；
- 轮转/清理不得在持有租约时做大规模 IO：按段处理，单次最多删 `maxPrunePerRun`（默认 8）段，避免长临界区；
- 清理失败（磁盘/权限）→ 记录 `audit.prune_failed`，不改变 manifest 的 `state`（保持 sealed），下次重试。

## 8. `detailHash`

### 8.1 目的

- 审计事件 `AuditEvent` 当前只有 `action/subject/outcome`，无法证明"当时的明细是什么"；
- 明细可能含敏感内容，不适合直接进链；
- 用 `detailHash` 把"链"与"明细"解耦：链只承诺"这个哈希"，明细放 sidecar，可独立校验、单独脱敏/保留。

### 8.2 结构

```ts
interface AuditEvent {
  // ... existing
  detailHash?: string;   // sha256(canonicalJson(detail))
  detailRef?: string;    // audit-details/<hash>.json（可选）
}
```

Sidecar：

```json
{
  "eventId": "aud_...",
  "hash": "sha256:...",
  "detail": { "capabilityId": "mcp://...", "inputHash": "...", "approvalId": "..." },
  "redacted": true,
  "bytes": 321
}
```

- `detail` 必须**先脱敏**（`Redactor`），再规范化 JSON（键排序），再哈希；
- 单条明细上限 `maxDetailBytes`（默认 16 KiB）；超过 → 只存 `detailHash` + `detailBytes` + `truncated:true`，不存原文；
- 不存 secret 原文；`dataClass=secret` 的明细只存哈希。

### 8.3 生成与校验

```ts
async function append(event, detail?) {
  const detailHash = detail === undefined ? undefined : sha256(canonicalJson(detail));
  const stored = { ...event, ...(detailHash ? { detailHash, detailRef: `audit-details/${detailHash}.json` } : {}) };
  await writeSidecar(detailHash, { eventId: stored.id, detail, redacted: true });
  return chainAppend(stored);
}
```

校验：

- `verify(tenantId, { details: true })`：对每条有 `detailHash` 的事件，读 sidecar，重算哈希，比较；
- 缺失 sidecar → `details:'missing'`；
- 哈希不匹配 → `details:'mismatch'`，该条标记 `broken`（链本身仍可能完好）。

## 9. 性能与容量

### 9.1 目标

| 场景 | 目标 | 说明 |
| --- | --- | --- |
| 内存 store 吞吐 | ≥ 200 inv/s | 设计 02 §15；4 写/调用 |
| 文件 store + 批量 fsync | ≥ 100 inv/s | 组提交；默认模式 |
| 文件 store + 逐条 fsync | ≥ 30 inv/s | 企业合规模式 |
| 锁等待 p95 | ≤ 10ms | 正常竞争 |
| 持锁 p95 | ≤ 3ms | 单写组 |
| 锁等待 p99 | ≤ 50ms | 峰值 |
| 启动恢复 | ≤ 500ms | 1 万条记录内 |

### 9.2 锁开销模型

- 取号（`seq.lock`）：~0.1–0.3ms；
- 租约获取（`mkdir` + `epoch` + `owner.json`）：~0.3–1ms；
- 重读（重写型全量）：~0.2–2ms（取决于文件大小）；
- 写组（4–6 文件）：~1–3ms（不含 fsync）；
- fsync：每条 ~0.5–5ms（取决于磁盘）。

### 9.3 降低开销的手段

1. **组提交**：一次 invocation 一个租约，而不是每个 store 一个；
2. **批量 fsync**：默认 `fsyncMode:'batch'`（每 100ms 或释放租约时 flush）；
3. **增量重读**：追加型文件只读尾部；重写型文件用指纹跳过未变文件；
4. **读写分离**：读不加锁；
5. **租约复用**：`WriteSession` 内不重复取锁；
6. **维护操作让路**：P5 用 `tryAcquire`。

### 9.4 退化策略

| 情况 | 策略 |
| --- | --- |
| 高竞争（队列 > 32） | 增大退避抖动；记录 `write.queue.congested`；不延长持锁 |
| 磁盘慢 | 自动从 `fsync:'always'` 降级为 `'batch'`（记录警告）；审计/回执不允许降级 |
| 锁等待超时 | 返回 `STORE_LOCKED`，调用方决定重试；不得静默丢写 |
| 租约频繁被接管 | 告警（`lease.takeover` 指标）；检查是否有进程被 SIGSTOP/长 GC |

## 15. 一页总结

```text
写者想写
  → 取号（seq.lock，<1ms）
  → 排队（priority, seq；默认 FIFO）
  → 拿租约（mkdir + epoch + owner.json）
  → 重读（stat 指纹变化 → reload；审计/回执校验链头）
  → 写组（budget → receipt → audit → event → task → idempotency）
  → 每次落盘前 assertHeld（epoch）
  → flush/fsync（batch）
  → 释放（删 owner + 删票据）
  → 下一个写者重复
```

**一句话**：**锁保证互斥，重读保证不脏，epoch 保证不被僵尸覆盖，FIFO 保证默认公平，优先级只给安全与证据让路。**

## 16. 决策记录（ADR-06）

> 目的：把"为什么必须这样"钉在文档里，避免后续实现为了方便而悄悄放宽。

### ADR-06-01 多进程写同一目录必须上锁

- **状态**：已确认（2026-10-30，用户）
- **背景**：`file-stores.ts` 的 5 个 store 是"读全量→改→重写全量"，且 `ensureLoaded` 只加载一次；两个进程同时写会丢更新、覆盖预算预留、把审计链写出分叉。
- **决策**：同一租户目录同一时刻只允许一个写者；写者必须持有租约才能落盘。
- **替代方案**：不加锁、依赖"用户不会同时开两个 CLI"——被否决，因为编辑器/CI/TUI 同时使用是常态。
- **后果**：写吞吐受单写者限制；用组提交与批量 fsync 抵消（§9）。

### ADR-06-02 解锁后、下次上锁前必须重读

- **状态**：已确认（2026-10-30，用户）
- **决策**：获取租约后先 `stat` 指纹（`mtimeMs`/`size`）；变化则全量重读并重新校验（审计/回执校验链头），再应用变更。
- **理由**：进程内缓存 + 多进程写 = 必然的脏读；只加锁不重读，锁只能防止"同时写"，防不住"用旧快照覆盖新数据"。
- **后果**：每次写多一次 `stat`（增量）或一次全量读（文件变化时）；这是正确性的必要成本。

### ADR-06-03 写序：工作内容 × 层次 × 优先级，默认 FIFO

- **状态**：已确认（2026-10-30，用户）
- **决策**：
  - 三维度：`workKind`（safety/evidence/governance/execution/telemetry/maintenance）、`layer`（L0/L1/L2/L3）、`priority`（P0–P5）；
  - **默认 = 先来先写**：未声明时统一 `execution/L2/P3`，按票据 `seq` 严格 FIFO；
  - 只有 `safety` 可声明 P0，只有 `safety/evidence` 可声明 P1；其他声明会被拒绝并降级；
  - 等待 >2s 老化一级（最多两级），防饿死。
- **理由**：默认 FIFO 保证可预测、可解释；优先级只用来让"安全拒绝/证据落链"不被普通业务写堵住，而不是给"我觉得急"开后门。
- **后果**：`agent` 必须提供可验证的 `reason` 才能提权，提权会写入审计。

### ADR-06-04 锁粒度：租户目录级（建议，待拍板）

- **状态**：建议
- **决策**：一个租户目录一把写租约，而不是每个文件一把。
- **理由**：一次 invocation 的写组跨 4–6 个文件；文件级锁需要多锁排序、易死锁，且无法保证跨文件一致。
- **代价**：同一租户的写完全串行；读不受影响。
- **备选**：文件级锁 + 全局顺序（复杂度高，收益有限）。

### ADR-06-05 不支持网络文件系统（建议，待拍板）

- **状态**：建议
- **决策**：启动时检测持久化目录所在文件系统；NFS/SMB 等网络 FS 直接拒绝持久化模式（可降级为只读/内存）。
- **理由**：`mkdir`/`rename` 在网络 FS 上不保证原子；"看起来有锁、实际不互斥"比"没锁"更危险。
- **后果**：明确不支持"多人共享一个网络盘"的场景；企业版再考虑真正的分布式锁。

### ADR-06-06 审计留存默认值（建议，待拍板）

- **状态**：建议
- **决策**：`retentionDays=30`、`maxTotalBytes=512MiB`、`minSegments=2`、`maxSegments=512`、`rotationBytes=64MiB`、`rotationIntervalMs=24h`。
- **理由**：本地 CLI 不至于爆盘；30 天覆盖大多数回溯需求；企业可配置更长。
- **后果**：超过 30 天的段会被 prune；prune 保留 `lastHash/count` tombstone，链可验证但被删内容不可重算。
