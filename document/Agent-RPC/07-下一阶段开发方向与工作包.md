## 0. 结论

**项目已经越过了"能不能跑"的阶段，进入"能不能放心交给第二个人/第二个进程用"的阶段。**

- 治理内核（P0）、三协议 wire 与官方 SDK 互通（P1）、主路径接入 ARF、持久化跨进程可读（C-4）、任务状态机、覆盖率与 SLO 断言（P2）都已闭环；MCP / A2A / ACP 分别有 8/8、5/5、6/6 的官方客户端互通用例。
- **唯一尚未闭环的，就是 `code/docs/V0.4-AUDIT-FIXES.md` §7 的六项**。其中 **"多进程并发写同一目录不安全"是当前最高风险**：它不会让测试变红，但会在真实使用中**静默丢数据、把审计链写出分叉、把预算预留覆盖掉**。
- 因此下一阶段的主线不是"再加功能"，而是：**把单进程可信，升级为同机多进程可交付**；在此之上补齐审计留存与协议完整性。

**一句话方向**：

> **v0.5「多进程安全」→ v0.6「可留存、可度量」→ v0.7「协议补全」。**

## 2. 下一阶段的产品方向

### 2.1 定位变化

| 现在 | 下一阶段 |
| --- | --- |
| "实验性预览；单进程 CLI 可用" | "**同机多进程安全的本地治理运行时**" |
| 治理记录"跨进程可读" | 治理记录"**跨进程可写、可轮转、可校验、可导出**" |
| 协议"与官方 SDK 互通" | 协议"**覆盖常用通知与状态变体**" |
| 性能"延迟达标" | 性能"**吞吐有基准、有门禁**" |

### 2.2 三个不做

1. **不做分布式锁/跨主机一致性**：本地文件系统之外的 NFS/SMB 明确不支持；企业版再考虑。
2. **不做企业控制面**（SSO、配额中心、审计导出 SaaS）：按 anti-roadmap。
3. **不为了吞吐牺牲证据链**：审计/回执永远不允许"丢一条换性能"；性能优化只能来自组提交、批量 fsync、增量重读。

### 2.3 成功标准（v0.5 结束时）

- 4 个进程并发写同一租户目录 30 分钟：**零丢更新、零分叉链、零重复审批、零负余额**。
- `kill -9` 持锁进程后 5 秒内自动恢复；被接管的僵尸写者 100% 被 `LEASE_LOST` 拒绝。
- `syao rpc store status` 能回答"谁在写、等了多久、为什么"。
- 审计链跨进程 `verify` 通过；轮转/清理有 tombstone；`detailHash` 可独立校验。
- 吞吐：内存 ≥200 inv/s、文件+batch fsync ≥100 inv/s、文件+always fsync ≥30 inv/s。

### WP-5 MCP `subscriptions/listen` + `notifications/message`（P2，~5 人天）

依据 2026-07-28 规范（已核验）：

- **服务端**：
  - `subscriptions/listen` 长连接请求；`notifications` 过滤器支持 `toolsListChanged` / `promptsListChanged` / `resourcesListChanged` / `resourceSubscriptions[]`；
  - 首条消息必须是 `notifications/subscriptions/acknowledged`，带 `_meta["io.modelcontextprotocol/subscriptionId"]`（= 请求 JSON-RPC id），且只回显服务端**同意**的子集；
  - 之后所有通知都带同一个 `subscriptionId`；**不得**发送未订阅类型；
  - 客户端取消：HTTP 关闭 SSE / stdio 发 `notifications/cancelled`；服务端主动结束：先回 `resultType:"complete"` 再关；
  - `notifications/message`（Logging，已弃用但仍在规范内）：仅当请求 `_meta["io.modelcontextprotocol/logLevel"]` 存在时，在**该请求的响应流**上发送，**不得**发到 subscription 流；级别过滤；无 `logLevel` 的请求一条都不发。
- **客户端**：
  - 处理 `notifications/tools/list_changed` → 失效工具注册表；
  - `prompts/list_changed` → 失效 prompts；
  - `resources/list_changed` / `resources/updated` → 失效资源缓存；
  - `notifications/message` → 日志 sink（级别过滤）；
  - `notifications/tasks` → 任务事件。
- **能力声明**：服务端 `capabilities.logging` 仅在实现 Logging 时声明；`subscriptions/listen` 属于基础协议，不需要额外 capability，但需在 `server/discover` 中体现。
- **测试**：wire 测试（ack 顺序、过滤器、多订阅、取消、优雅关闭）、客户端失效测试、无 opt-in 不发通知的负例。

**为什么排 P2 而不是 P1**：它是"体验/生态"缺口，不影响治理正确性；但它是 `knownGaps` 里唯一被外部基线钉住、且官方 SDK 会真实用到的能力，建议在 v0.6 内完成。

### WP-6 A2A 保留键（P2，~1 人天）

- 定义保留键集合：`metadata.tenantId`、`metadata["A2A-Version"]`（宿主传输层所有）；如未来引入 `traceId`/`subscriptionId` 同样登记；
- 客户端：`metadata()` 改为先展开 `extra`、再写保留键；发现 `extra` 含保留键且值不同 → 抛 `INVALID_ARGUMENT`（本地直接拒绝，不发请求）；
- 服务端：`caller()` 校验保留键与解析出的 caller 上下文一致；不一致 → `-32602`（`reserved_metadata_key`），不静默覆盖；
- `A2A-Version` 以 HTTP 头/传输层为准，body 只能确认、不能改写；
- 测试：客户端覆盖被拒、服务端冲突被拒、一致时通过、缺省时兼容 0.3。

| S3 后（v0.7） | MCP 订阅/日志通知、A2A 保留键、ACP 9 变体补齐 | 协议"完全合规"（仍有 known gaps 需逐条核验） |

## 7. 需要拍板的决策

| # | 决策 | 建议 | 不决定的后果 |
| --- | --- | --- | --- |
| D1 | 锁粒度：目录级 vs 文件级 | **目录级**（06 §3.1） | 文件级会引入多锁死锁与跨文件不一致 |
| D2 | 默认 fsync | **batch（100ms/释放）** | always 会把吞吐压到 30 inv/s 以下 |
| D3 | 审计保留默认 | **30 天 / 512 MiB / 最少 2 段** | 不设上限会爆盘；设太短会丢证据 |
| D4 | 是否支持 NFS | **不支持**，启动检测到网络 FS 拒绝持久化 | 伪锁导致真实丢数据 |
| D5 | 优先级是否可配置 | 只开放 P2–P5；P0/P1 固定给 safety/evidence | 滥用优先级会饿死普通写 |
| D6 | v0.5 是否含 `detailHash` | **含**（1.5 人天，性价比高） | 合规场景缺一块 |
| D7 | 是否现在做 MCP 订阅 | **S3 做**，不阻塞 S1 | 生态体验缺口，但不影响正确性 |

## 8. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 锁实现引入新死锁/活锁 | 中 | 高 | 单租约、无嵌套、无网络；混沌测试 |
| fsync 拖慢 CLI 交互 | 中 | 中 | 默认 batch；仅审计/回执可配 always |
| 旧数据迁移失败 | 低 | 高 | 启动时备份 + 迁移 dry-run + 失败回滚 |
| 多进程测试在 CI 不稳定 | 中 | 中 | 固定临时目录、重试 3 次、超时诊断快照 |
| 优先级机制被滥用 | 低 | 中 | P0/P1 白名单 + `reason` 审计 |
| Windows `mkdir`/`rename` 语义差异 | 中 | 中 | CI 加 Windows 单进程 + 并发小规模用例 |
| 审计分段后 `verify` 语义变化 | 中 | 高 | pruned 段只验链接；文档明确"不能证明被删内容未被篡改" |
