## 0. 结论（先看这里）

**一句话**：**骨架已经建成，性能远超预期，但"治理保证"里有三条在默认配置下并不成立，协议边缘尚未达到可对外宣称"合规/互通"的程度。**

| 维度 | 结论 | 评级 |
| --- | --- | --- |
| **架构骨架**（一个内核 + 三种边缘 + 十步流水线） | 已落地，边界约束有脚本强制 | ✅ 达成 |
| **性能 / SLO** | p95 0.114ms，比 5ms 目标好 40 倍；CLI 启动 0.30s | ✅ 超预期 |
| **工程门禁** | typecheck / 810 测试 / evals 10/10 / 三个 lint / build 全绿 | ✅ 达成 |
| **治理不变量 I1–I13** | 13 条中 **4 条实际失效、5 条部分失效**（见 §2） | ⚠️ 未达成 |
| **功能完整性** | 主链路可用；但"拒绝路径无回执""任务状态机不驱动""obligation 不执行""审批记忆失效" | ⚠️ 部分达成 |
| **协议一致性** | MCP/A2A/ACP 各 ≥1 个 MUST 级破坏，共 8 项；自洽 ≠ 互通 | ❌ 未达成 |
| **"统一治理"主张** | ARF 与主 agent 路径**并行**，`syao -p` 的工具调用不产生 ARF 回执/审计/预算 | ❌ 未达成 |
| **文档可信度** | 实现报告 §5 对 MCP SDK 的"更正"基于**错误的包名**，结论不成立 | ❌ 需修正 |

**最重要的三条判断**：

1. **现在不能说"预算说停就停"**：默认（调用方不给 estimate）时预留金额恒为 `$0`，账本 `reserved=spent=0`；且 `reserve()` 是 check-then-write，**并发下 10 笔 $0.5 可以全部通过 $1.00 的限额**（实测提交 $5.00）。这是治理底座的立身之本，必须最先修。
2. **现在不能说"每个调用都有回执"**：拒绝/审批拒绝/预算不足/幂等冲突四条路径都不写 Receipt（只有审计行），`outcome:'denied'` 不可达。这直接削弱"Verified Completion"的证据链。
3. **现在不能说"协议合规/可互通"**：A2A 协议错误码根本到不了 wire（全部退化成 `-32603`）、A2A 流式用了私有帧、ACP 取消失效、MCP 错误码钉错、`McpServer`/`A2aServer` 零测试。这些是"能和自己的测试互通"，不是"能和官方 SDK 互通"。

**预期**：修完 §5 的 P0（约 5–8 人天）可宣称"**内核治理在单机/单租户场景可信**"；再修完 P1（约 15–20 人天，含真实互通测试）可宣称"**三协议可用且与官方 SDK 互通**"；再修 P2（约 10–15 人天）才配得上"**一个内核 + 三种边缘**"。**在那之前，对外只能讲"实验性预览"，不能讲"合规/可治理"。**

## 2. 治理不变量实测：I1–I13

> 图例：✅ 实测成立｜⚠️ 部分成立｜❌ 实测失效

| --- | --- | --- | --- |

## 4. 架构一致性：ARF 与主路径并行（最需要拍板的一条）

**实测**：`syao -p` / TUI / REPL 的 agent 工具调用**不经过 ARF**。

- `packages/cli/src/run.ts`、`interactive.ts`、`tui/tui.ts` 均直接 `createAgent(...)` + `createBuiltinTools()`，走 core 的 `executeToolCall` → core `PermissionEngine` → core `ToolReceipt`。
- ARF 只在 `serve`/`call`/`rpc`/`mcp` 子命令与 `/rpc`、`/peer`、`/call` 交互指令中使用（`main.ts:96-121`）。

**后果**：

1. **两套治理**：日常 agent 改文件的路径没有 ARF 回执、没有审计链、没有层级预算；"一个内核 + 三种边缘"目前只在"被治理控制台调用的那条路径"上成立。
2. 好处是规则不冲突（ARF 用 `createPermissionPreset` 包装同一个 `PermissionEngine`），但**证据与预算不统一**。
3. 这也是 `document/Agent-RPC/03 §8` 早就列出的风险（"双实现漂移"）——现在确实发生了。

**建议**：M4 收尾时把"主 agent 路径接入 ARF"作为独立工作项（两种做法：把 core pipeline 的 receipt/audit 作为 ARF 的本地执行器后端；或让 `createAgent` 的 tools 经 `fabric.call('local://tools/...')` 路由）。在此之前，**不要对外宣称跨协议统一治理**。

## 10. 补遗：集成与 CLI 真值（第三轮审计，2026-10-28 16:13–17:10）

> 本节补充第三轮"集成 / CLI / 持久化 / 构建"审计的结论。除注明"审计报告"外，**下列每条都由本次评估本机复核**。

### 10.1 新增关键缺陷

#### C-1（**最严重**）协议边缘绕过本地安全围栏 —— 已用探针坐实

`packages/rpc/src/governance/policy.ts:207`：

```ts
private async presetVerdict(input: PolicyInput) {
  if (this.preset === undefined) return undefined;
  if (input.capability.protocol !== 'local') return undefined;   // ← 只对 local:// 生效
  return await this.preset.evaluateLocal(input);
}
```

core 的 `PermissionEngine`（承载 **BR-006 危险命令库**、`realpath` 工作区围栏、敏感路径清单）**只对 `local://` 能力参与判定**。对 MCP / A2A / ACP 边缘，只有 ARF 规则引擎生效；客户写一条普通的 `mcp://**` allow，就等于放弃了全部本地安全语义。

**本机探针结果**（`createFabric` + 真实 dispatcher + 挂载 MCP 边缘 + 普通 org allow 规则）：

```text
  dangerous command rm -rf /   -> succeeded
  read /etc/passwd             -> succeeded
  read ~/.ssh/id_rsa           -> succeeded
peer invoked 3/3 times
>>> EDGE BYPASS CONFIRMED: local fence did not apply to the protocol edge
```

对照组：`syao call local://tools/bash --input '{"command":"rm -rf /"}'` → 退出码 3（BR-006 命中）。

**这意味着 v0.2 花力气修好的三个安全洞（读围栏、危险命令、敏感路径）在新引入的协议边缘上全部失效**，且方向恰好相反：越是接入生态（MCP/A2A/ACP），越不安全。这是必须最优先修的项，也是"实验性预览"口径的主要理由。

#### C-2 `syao serve --a2a` 是未治理的伪造桩

`packages/cli/src/serve.ts:270-280` 在收到 `SendMessage` 时：创建 ARF Task，然后**直接返回**：

```ts
return { id: task.id, contextId: task.sessionId,
         status: { state: 'TASK_STATE_COMPLETED' }, artifacts: [], metadata: {...} };
```

**没有经过 dispatcher**，没有执行任何工作，却对调用方宣告 `COMPLETED`。审计报告实测：0 条回执、0 条审计事件、任务仍停在 `submitted`。这比"不支持"更糟——它**伪造成功**，直接违背本设计的"Verified Completion / 不伪装"原则，也会污染任何依赖该状态的 A2A 调用方。

#### C-3 `syao serve --acp` 无法执行任何回合

`packages/protocols/src/acp/server.ts:316-317` 在 `runTurn` 未注入时抛 `-32603 "this agent has no prompt handler"`；而 CLI 的 `serve.ts` **没有注入 `runTurn`**。即 ACP 服务端可以 `initialize`/`session/new`，但 `session/prompt` 必然失败。设计 §5.5 的 `syao acp --stdio` 端到端场景目前不可用。

#### C-4 持久化未接线：审计/策略/审批只活在单进程内存里

| 组件 | 状态 |
| --- | --- |
| `EventSink` / `FileEventSink`（C3） | 库存在，**CLI 无任何路径注入**（`grep eventSink packages/cli/src` 为空）；agent 仍只写 `type:'message'` |
| ARF 存储 | `cli/src/arf.ts:275-285` 明确写着 "PERSISTENCE SEAM"：**全部使用内核内存 store**，`@syaocode/node` 的文件 store 从未接线 |
| 实测 | `syao call …` 之后 `syao rpc audit --json` → `{"verify":{"ok":true,"checked":0}}` |
| `permissionRuleStore`（C5 `project`） | CLI 无注入 → `remember:'project'` 生产环境永不落盘 |
| `config.rpc.*`（C9） | schema 与分层测试都有，但**无任何生产代码读取**；peers 实际存在第二个注册表 `~/.syaocode/config.json.peers` |

**结论**：**当前不能宣称任何"审计留痕/可回放/策略持久化"能力**。审计链本身实现正确，但每次 CLI 退出即消失。

#### C-5 构建产物不可运行；CI 漏掉两道门禁

- `node packages/cli/dist/main.js --version` → **`ERR_MODULE_NOT_FOUND`**（workspace `exports` 指向 `./src/index.ts`，Node 无法加载 `.ts`）。`pnpm build` 通过**不等于**产物可运行，且没有任何 build/pack 冒烟测试。

#### C-6 其他已复核项

- **CLI 命令缺口**：设计 §5.5 列的 `syao acp` / `syao a2a` / `syao arf` **不存在**；`args.ts:31` 无这些成员，于是 `syao acp` 被当作 prompt **静默进入 REPL**（退出 0），`syao acp --stdio` 报 unknown option（退出 2）。`mcp get|login|logout` 与项目级首次信任确认（`SY-CFG-003`）也缺失。

### 10.5 补充结论

2. **C-2 的"伪造成"是本轮最需要立刻处理的诚信问题**：治理底座的全部价值建立在"不伪装完成"之上，一个伪造 `COMPLETED` 的服务端桩会直接摧毁这个前提。建议**当天降级为明确不支持**。
3. **C-4 说明"可审计"目前只是接口而非能力**：审计链实现是好的，但没有任何生产路径把事件写出进程。
4. **C-5 说明"构建通过"与"可交付"之间还有一道没人守的门**：CI 漏 `lint:rpc`/`build`，产物入口不可运行。
5. **修订后的建议路径**：P0（~14 人天，含 C-1/C-2/C-3）→ 让安全与诚信承诺成真；P1（~23.5 人天，含持久化与交付门禁）→ 让协议能互通、审计能留痕；P2（~11.5 人天）→ 让架构名副其实。**总计约 49 人天。**

### 11.2 真实互通发现、自指测试无法发现的 4 个 MUST 缺陷（已修 + 已加回归）

2. 列表结果缺 `resultType` 判别符；
