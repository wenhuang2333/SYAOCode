## 0. 结论（先看这里）

**一句话**：**骨架已经建成，性能远超预期，但"治理保证"里有三条在默认配置下并不成立，协议边缘尚未达到可对外宣称"合规/互通"的程度。**

| 维度 | 结论 | 评级 |
| --- | --- | --- |
| **架构骨架**（一个内核 + 三种边缘 + 十步流水线） | 已落地，边界约束有脚本强制 | ✅ 达成 |
| **性能 / SLO** | p95 0.114ms，比 5ms 目标好 40 倍；CLI 启动 0.30s | ✅ 超预期 |
| **工程门禁** | typecheck / 810 测试 / evals 10/10 / 三个 lint / build 全绿 | ✅ 达成 |
| **治理不变量 I1–I13** | 13 条中 **4 条实际失效、5 条部分失效**（见 §2） | ⚠️ 未达成 |
| **功能完整性** | 主链路可用；但"拒绝路径无回执""任务状态机不驱动""obligation 不执行""审批记忆失效" | ⚠️ 部分达成 |
| **协议一致性** | MCP/A2A/ACP 各 ≥1 个 MUST 级破坏，共 8 项；自洽 ≠ 互通 | ❌ 未达成 |
| **"统一治理"主张** | ARF 与主 agent 路径**并行**，`syao -p` 的工具调用不产生 ARF 回执/审计/预算 | ❌ 未达成 |
| **文档可信度** | 实现报告 §5 对 MCP SDK 的"更正"基于**错误的包名**，结论不成立 | ❌ 需修正 |

**最重要的三条判断**：

1. **现在不能说"预算说停就停"**：默认（调用方不给 estimate）时预留金额恒为 `$0`，账本 `reserved=spent=0`；且 `reserve()` 是 check-then-write，**并发下 10 笔 $0.5 可以全部通过 $1.00 的限额**（实测提交 $5.00）。这是治理底座的立身之本，必须最先修。
2. **现在不能说"每个调用都有回执"**：拒绝/审批拒绝/预算不足/幂等冲突四条路径都不写 Receipt（只有审计行），`outcome:'denied'` 不可达。这直接削弱"Verified Completion"的证据链。
3. **现在不能说"协议合规/可互通"**：A2A 协议错误码根本到不了 wire（全部退化成 `-32603`）、A2A 流式用了私有帧、ACP 取消失效、MCP 错误码钉错、`McpServer`/`A2aServer` 零测试。这些是"能和自己的测试互通"，不是"能和官方 SDK 互通"。

**预期**：修完 §5 的 P0（约 5–8 人天）可宣称"**内核治理在单机/单租户场景可信**"；再修完 P1（约 15–20 人天，含真实互通测试）可宣称"**三协议可用且与官方 SDK 互通**"；再修 P2（约 10–15 人天）才配得上"**一个内核 + 三种边缘**"。**在那之前，对外只能讲"实验性预览"，不能讲"合规/可治理"。**

### 1.3 与设计的实现差异（正面）

- C1（审批事件即时可见）、C2（信封加 `schemaVersion`/`ts`/`sessionId`）、C3（`EventSink` + 文件事件落盘）、C4（trust 标注）、C5（审批记忆/稳定 id 的**接口**）、C6（SHA-256 审计链）、C7（新增 A2A 错误域，87 codes）、C9（`config.rpc` 段）都已落地。
- 审计链是**真的** SHA-256 前向链 + checkpoint + `verify()`，能检出改链/换序/中间删除（`audit.ts:45-53,113-167`，有篡改测试）。
- 适配器边界是**真的**：`AuthorizedInvocation` 是唯一入口，脚本强制 `rpc`/`protocols` 不 import `node:`、不 import `agent.ts`、不直接 `Tool.execute`。
- `lossy` 降级词表、`direction: reverse` 的治理接入（ACP 反向 `fs/*`、`terminal/*` 走同一条流水线）是设计意图的正确落地。

## 2. 治理不变量实测：I1–I13

> 图例：✅ 实测成立｜⚠️ 部分成立｜❌ 实测失效  
> "探针"= 本次评估在 `/tmp` 用真实模块运行的验证（未修改仓库）。

| 不变量 | 判定 | 证据 |
| --- | --- | --- |
| **I1** 每个调用有已认证 Principal + Tenant | ❌ | `identity` 服务被注入但**从未调用**（`dispatcher.ts:85-95` 只断言非空）；调用方自带 principal 即被接受。**探针 V3**：以 `tenantId:'tenant-victim'` 的 principal 调用，任务被写入 `tenant-victim`（`tasks.list` 只在该租户可见） |
| **I2** 无 PolicyDecision 不得派发 | ✅ | 唯一副作用出口 `dispatcher.ts:271`，在 `policy.evaluate`（:163）与 deny 抛出（:173）之后；无旁路。**但** `AuthorizedInvocation` 是无签名对象，`mount()` 把适配器交还给宿主，宿主可绕过 Dispatcher 直接 `adapter.invoke()` |
| **I3** `ask` 无审批不得派发 | ⚠️ | `effect==='ask'` 路径正确（:193-211）。**但 `allow` + `require_approval` obligation 被忽略**：**探针 V5** 显示策略写"允许但需审批"时，审批 0 次、副作用已发生 |
| **I4** 协议注解/AgentCard/模型文本不得提升策略 | ✅ | 注册表把 peer 自述只记为 `peer.declaredRisk` 标签，有效风险来自注册表默认（`registry.ts:131-152`）；红队 #1/#2/#10 真实。**偏差**：注册表存的是 peer 自报的 capability id（§4.5.1 要求由注册表分配） |
| **I5** 每个 Invocation 恰好一个终态 + 一张回执 | ❌ | Receipt 只在派发路径写（:290）。拒绝、审批拒绝、obligation 失败、预算不足、幂等冲突**都不写回执**（`dispatcher.test.ts:204-209` 甚至把这个行为断言为期望）；`outcome:'denied'` 不可达 |
| **I6** 先预留后派发；余额不得为负 | ❌ | 顺序对（:217-243 在 :271 之前）。**探针 V2**：`tenantLimitUsd=1.0`、6 次调用不给 estimate → 全部通过，`reserved=0 spent=0`（默认估算 `{usd:0}`，`dispatcher.ts:218`）。**探针 V1**：10 笔并发 $0.5 对 $1.00 限额 → 10/10 成功、实际提交 $5.00（check-then-write TOCTOU，`budget.ts:83-115`）。另：session 账户未挂到 tenant 账户（`fabric.ts:321-339,417`），`recoverExpired` 不看 receipt 就退款（`:169-178`） |
| **I7** secret 不进上下文/事件/审计/回执 | ⚠️ | 输入与输出**有**脱敏（探针 V6：`{"apiKey":"[REDACTED...]"}`）。**但** `redactEvent/redactReceipt/redactError/sanitizeUsage` 零调用（`redactor-bridge.ts:65-105`）；适配器事件、错误消息、`lossy`/`artifacts` 未脱敏；默认 `NoopRedactor`（`fabric.ts:451`）；<8 字符的 secret 被静默丢弃 |
| **I8** 所有查询按 tenantId 过滤 | ⚠️ | 任务/会话/预算账户列表已过滤。**未过滤**：`ApprovalStore.get/decide`（可跨租户读取与批准，且 `by` 是自由字符串）、`BudgetStore.getReservation/listReservations`、`registry.get`、`EventLog.list`、`fabric.tasks.events()`、`evidence.seal()`、`audit.list()`（无 filter 时合并所有租户） |
| **I9** 审批单赢家；超时/取消 = deny | ⚠️ | CAS 单赢家与超时→deny 是真的（`stores.ts:174-183`、`approval.ts:141-188`）。**但** `decide` 不校验 `expiresAt`、不校验 tenant/authority、审批未绑定 capability/input、`allow_always/allow_session` **永不生效**（`approvalHistory` 三处硬编码 `[]`）；§6.5 的 recheck 无生产调用者且 fabric 的 `recheckPolicy` 用错误的 capabilityId 与合成 principal |
| **I10** 非幂等 + 结果未知不得自动重试 | ❌ | 任何非成功结果都写 `idempotency.fail`，而 `begin` 把所有 `failed` 视为可重试（`idempotency.ts:82-90`），忽略 `retryable`/`sideEffect`。**探针**（审计 L）：非幂等 capability 标 `indeterminate` 后同 key 重试 → 执行器被调用两次。`retryVerdict`/`no_retry` 是死代码 |
| **I11** 反向调用与正向同权治理 | ✅/⚠️ | ACP 反向调用确实走同一条 Dispatcher 流水线（`acp/fs.ts:117,134` → `edges.ts:259-275` → `dispatcher.invoke(direction:'reverse')`）。**但** `direction` 由调用方提供，`directions:['reverse']` 规则可被绕过；且 `AcpAdapter.invoke` 这条实际被 dispatcher 调用的路径**没有** realpath 围栏（围栏只在可选的 `AcpFsBridge` 里，且是词法匹配） |
| **I12** 审计链可重算；断链告警 | ⚠️ | 链本身真实且可验证。**但** 尾部截断只有 checkpoint 能发现，而 fabric 从不创建 checkpoint（`checkpoint()` 只在 append 自动节奏里）；写路径从不调用 `verify()`，没有告警也没有"高风险暂停"；`dropForTest` 是生产 API；无 `detailHash` |
| **I13** 适配器不得直接执行工具 | ⚠️ | 只有文本级脚本强制，且脚本引用了**不存在的目录** `packages/rpc/src/adapters`，且不扫 `packages/cli`；`.execute(` 启发式要求同行出现 "tool"。更严重的是适配器拿到了**含 `decide` 的完整 ApprovalBroker**（`fabric.ts:450`），与 02 §12.2"适配器不得自行决定 allow/deny"冲突 |

### 2.1 十步流水线的达成度

| # | 步骤 | 判定 | 关键缺口 |
| --- | --- | --- | --- |
| 1 | Normalize | ⚠️ | 只校验 capabilityId 非空；不按 `inputSchemaRef` 校验输入、无 payload 上限 |
| 2 | Authenticate | ❌ | 空实现（I1） |
| 3 | Resolve | ✅ | 仅从注册表解析。缺陷：任何解析错误都被改写成 `capability_not_found`，注册表故障被报成"能力不存在" |
| 4 | Idempotency | ⚠️ | 顺序正确（在预算前）。缺陷：**派生键用常量 `'pending'`**（`dispatcher.ts:115`）——**探针 V4**：同一 task 内第二次不同输入的合法调用被 `idempotency_conflict` 拒绝；策略/预算抛错时记录会卡在 `in_flight` 24h；重放无内联结果时伪造 `succeeded`/`unknown` |
| 5 | Authorize | ✅ | deny 先于派发、obligation 取并集、缓存只缓存无时间敏感 obligation 的 allow |
| 6 | Approve | ⚠️ | 见 I3/I9 |
| 7 | Reserve | ❌ | 见 I6；另 `skipBudget` 是调用方可控的绕过开关（`contracts.ts:418`） |
| 8 | Dispatch | ✅/⚠️ | 唯一出口。但 obligation 只执行 `sandbox`；`inputHash` 覆盖**未脱敏**输入而执行的是脱敏输入；`deadlineAt` 只透传不强制；无取消传播 |
| 9 | Settle | ⚠️ | 结算失败被吞（只 warn）；崩溃后无条件退款 |
| 10 | Receipt + Audit | ⚠️ | 同步写回执 ✓；拒绝路径无回执；`timing` 三个时间戳同值；回执无 error 字段；`writeReceipt` 先于 `writeAudit`，审计失败时副作用已发生且幂等记录卡住 |

## 4. 架构一致性：ARF 与主路径并行（最需要拍板的一条）

**实测**：`syao -p` / TUI / REPL 的 agent 工具调用**不经过 ARF**。

- `packages/cli/src/run.ts`、`interactive.ts`、`tui/tui.ts` 均直接 `createAgent(...)` + `createBuiltinTools()`，走 core 的 `executeToolCall` → core `PermissionEngine` → core `ToolReceipt`。
- ARF 只在 `serve`/`call`/`rpc`/`mcp` 子命令与 `/rpc`、`/peer`、`/call` 交互指令中使用（`main.ts:96-121`）。

**后果**：

1. **两套治理**：日常 agent 改文件的路径没有 ARF 回执、没有审计链、没有层级预算；"一个内核 + 三种边缘"目前只在"被治理控制台调用的那条路径"上成立。
2. 好处是规则不冲突（ARF 用 `createPermissionPreset` 包装同一个 `PermissionEngine`），但**证据与预算不统一**。
3. 这也是 `document/Agent-RPC/03 §8` 早就列出的风险（"双实现漂移"）——现在确实发生了。

**建议**：M4 收尾时把"主 agent 路径接入 ARF"作为独立工作项（两种做法：把 core pipeline 的 receipt/audit 作为 ARF 的本地执行器后端；或让 `createAgent` 的 tools 经 `fabric.call('local://tools/...')` 路由）。在此之前，**不要对外宣称跨协议统一治理**。

## 6. 需要修正的文档事实（我已核实）

`code/docs/AGENT-RPC.md §5` 声称对设计文档做了"外部事实核验更正"，但其中 MCP 部分**基于错误的包名**，结论不成立：

| 报告断言 | 实测（2026-10-28） | 判定 |
| --- | --- | --- |
| "`@modelcontextprotocol/sdk` 只有 0.4.0→1.32.2，无任何 2.x 版本线；2.4.0 → 404" | 该包确实是 v1 线（latest 1.32.2）。但 **v2 是独立包名**：`@modelcontextprotocol/server@2.4.0` 存在，`dependencies: {zod: ^4.2.0, @modelcontextprotocol/core: 2.4.0}` | ❌ 断言错误 |
| "MCP SDK 的 zod 是 `^3.25 \|\| ^4.0`，无强制嵌套" | 那是 **v1** 的区间；**v2** 的 `@modelcontextprotocol/core@2.4.0` 硬依赖 `zod ^4.2.0` | ❌ 断言错误 |
| "MCP SDK 不支持 2026-07-28 modern 时代（`server/discover`/`resultType`/`_meta` 命中数均为 0）" | 下载 `@modelcontextprotocol/server@2.4.0` tarball 实测：`server/discover` 148 处、`resultType` 226 处、`io.modelcontextprotocol/protocolVersion` 4 处、`2026-07-28` 844 处 | ❌ 断言错误 |

**结论**：自研 wire 的**决定可以保留**（零传递依赖、无嵌套 zod、完全可控、已有 drift 守卫），但**理由必须重写**：不是"官方 SDK 不存在/不支持"，而是"我们选择零依赖与完全可控，代价是自行维护 wire"。A2A/ACP 的观察（A2A SDK 无 stdio、ACP SDK 零运行时依赖但会引入外部依赖面）基本属实，可以保留。

## 9. 最终结论

1. **工程执行力优秀**：31k 行、两个新包、810 测试、三套 lint、build 与 evals 全绿，性能远超 SLO，边界约束用脚本强制。骨架质量高于多数同类项目的第一版。
2. **但"治理保证"尚未兑现**：I1/I5/I6/I10 四条在默认配置下失效，且都属于"文档承诺了、代码没做到"的类型——这比"没写"更危险，因为使用方会据此信任它。
3. **协议边缘是"自洽"而非"互通"**：8 个 MUST 级破坏 + 两个 server 零测试 + 自指 drift，说明当前一致性验证只能证明"改坏了会报错"，不能证明"基线是对的"。
4. **"统一治理"还差一步**：ARF 与主 agent 路径并行，最常用的路径没有回执/审计/预算。
5. **建议路径**：P0（~10 人天）→ 让承诺成真；P1（~17 人天）→ 让协议能互通；P2（~11.5 人天）→ 让架构名副其实。**在 P0 完成前，对外统一用"实验性预览"口径。**
