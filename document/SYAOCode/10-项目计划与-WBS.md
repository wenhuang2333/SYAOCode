# 十、项目计划与 WBS

## 10.1 计划假设

- 工作量按人日估算，包含实现、自测和必要文档，不等于日历日；外部模型接口、Windows 兼容与安全加固存在明显不确定性。
- 单人兼职以每周 2.5 人日估算；应追加 15%–20% 风险缓冲。
- v1.0 把“可用 CLI 的完整纵向切片、三角色最小编排、JEV 可选决策层、MCP 工具接入和可验证 goal”作为 P0；loop 调度、ACP、Desktop 和丰富插件生态不与首版争资源。
- 评测必须在 M1 起建立最小版本，不应拖到功能完成之后。

## 10.3 里程碑基线

| 里程碑 | 工作量（约） | 目标周期（按 5 人日/周） | 退出标准 |
| --- | ---: | --- | --- |
| M0 | 10 | 2 周 | 官方规范/依赖/许可证核验完成；关键 PoC 通过；最小评测集建立 |
| M1 | 31 | 6–7 周 | 可在测试项目完成“读—改—运行—报告”；Mock 与真实 Provider 合约通过 |
| M2 | 25 | 5 周 | TUI/非交互/会话恢复/预算/权限稳定；无 S1 级安全缺陷 |
| M3 | 27 | 5–6 周 | JEV shadow 可回放；hyaki/sota/common 交接 schema 通过；goal 终止条件可靠 |
| M4 | 14 | 3 周 | MCP 双传输工具接入，断线和恶意输出处理通过 |
| M5 | 12 | 3 周 | 全 P0 测试、评测、安全、三平台验证、文档和 RC 完成 |
| v1.1 | +32 | 后续单独排期 | `/loop` 与 `serve/attach` 的安全、并发和恢复测试通过 |

**工作量口径**：M0–M5 的阶段工作包合计 119 人日；项目治理/架构评审另计 8 人日，故 P0 合计 127 人日。里程碑周期按约 5 人日/周表示全职等效周；单人兼职周期按 10.2 估算。

**进度控制**：如果 M1 的纵向切片还不能稳定读/改/测，就暂停高级 JEV/多 Agent 优化，优先完成最小内核。若多角色方案无法在评测中改善成本或成功率，先保留角色 API 与结构化交接，默认使用 balanced/common，避免把复杂度误当作产品价值。

0.1/0.2 → 1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 2.1 → 2.2 → 2.3 → 2.4 → 2.5 → 3.1 → 3.4 → 3.5 → 4.1 → 4.3 → 5.1 → 5.3。

评测集（4.3）虽排在 M4，但其最小版本须在 M2 结束前建立（R-12），否则压缩与提示词调整缺少依据。

## 10.5 治理与度量

| 项 | 做法 |
| --- | --- |
| 节奏 | 每周一次自评审：完成项、偏差、风险变化；每个里程碑末做一次范围冻结评审 |
| 变更控制 | 新需求先进入 backlog，评审后更新 SRS、RTM，再排期（R-01） |
| 分支 | 主干开发，短分支加 PR，自动化检查通过才合并 |
| 完成定义 DoD | 代码、测试、TSDoc、RTM 更新、错误码登记、CI 全绿 |
| 度量 | 每周完成人日、评测通过率趋势、缺陷数、冷启动与包体积趋势 |
