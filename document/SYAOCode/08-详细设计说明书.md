# 八、详细设计说明书

> 本章代码均为接口草案，用于固化契约，实现时可在不破坏语义的前提下调整。章节编号 DD-n 与 RTM 对应。

## DD-1 类型、配置与 Runtime

**内部消息模型**

```ts
type ContentBlock =
  | { type: 'text'; text: string }
  | { type: 'image'; source: ImageSource }
  | { type: 'thinking'; text: string; signature?: string; redacted?: boolean }
  | { type: 'tool_use'; id: string; name: string; input: unknown }
  | { type: 'tool_result'; toolUseId: string; content: ToolResultContent[]; isError?: boolean };

interface Message {
  id: string;
  role: 'user' | 'assistant';
  content: ContentBlock[];
  meta?: { providerData?: unknown; createdAt: number };
}
```

`meta.providerData` 用于透传 provider 专有字段（如签名、缓存标记），内核不解释、不丢弃，缓解风险 R-03。

**Runtime 抽象**

```ts
interface Runtime {
  fs: FileSystem;      // readFile / writeFile / stat / readdir / realpath ...
  shell: Shell;        // spawn(cmd, opts) -> ProcessHandle
  http: HttpClient;    // fetch 兼容
  clock: Clock;        // now() / sleep()，便于测试
  logger: Logger;
  env: Env;            // 环境变量只读视图
  ids: IdGenerator;
}
```

`@syaocode/core` 附带 `nodeRuntime()` 默认实现；测试使用内存实现。

**AgentConfig**

```ts
interface AgentConfig {
  model: ModelSpec;                  // { provider, name } 或路由表
  cwd?: string;
  tools?: Tool[];
  permissions?: PermissionConfig;
  permissionHandler?: PermissionHandler;
  context?: ContextConfig;
  session?: SessionStore | SessionOptions;
  hooks?: HookConfig;
  plugins?: PluginRef[];
  mcpServers?: McpServerConfig[];
  limits?: Limits;                   // maxTurns, maxBudgetUsd, timeoutMs
  runtime?: Partial<Runtime>;
}
```

**配置加载**：`loadConfig({ user, project, env, code })` 依次合并，Zod 校验，错误汇总为 `SY-CFG-001`。密钥以引用形式出现（`{ env: 'ANTHROPIC_API_KEY' }`），解析后只存在于内存，并加入脱敏器的已知密钥集合。

## DD-2 Agent 循环

**事件定义（节选）**

```ts
type AgentEvent =
  | { type: 'session.start'; sessionId: string; permissionMode: PermissionMode }
  | { type: 'turn.start'; turn: number }
  | { type: 'text.delta'; text: string }
  | { type: 'thinking.delta'; text: string }
  | { type: 'message.complete'; message: Message; stopReason: StopReason }
  | { type: 'tool.proposed'; call: ToolCall }
  | { type: 'permission.request'; id: string; call: ToolCall; reason: string }
  | { type: 'permission.result'; id: string; decision: 'allow' | 'deny'; by: string }
  | { type: 'tool.start' | 'tool.progress' | 'tool.result'; callId: string /* ... */ }
  | { type: 'usage'; usage: Usage; costUsd?: number }
  | { type: 'budget.warning'; kind: 'tokens' | 'cost' | 'turns'; ratio: number }
  | { type: 'context.compacting' | 'context.compacted' /* ... */ }
  | { type: 'hook'; name: string; outcome: string }
  | { type: 'error'; error: SyaoError; fatal: boolean }
  | { type: 'turn.end'; turn: number }
  | { type: 'session.end'; reason: EndReason };
```

**循环伪代码**

```ts
async function* runLoop(ctx: RunContext, input: UserInput) {
  ctx.history.append(userMessage(input));
  while (true) {
    const stop = ctx.limits.check();                 // BR-010
    if (stop) return yield* end(stop);
    await ctx.context.maybeCompact();                 // BR-013
    const req = ctx.context.buildRequest();
    const assistant = yield* streamModel(ctx, req);   // 含重试，BR-014
    ctx.history.append(assistant);
    const calls = toolCallsOf(assistant);
    if (calls.length === 0) {
      if (await ctx.hooks.stop(assistant) === 'continue') continue;
      return yield* end('completed');
    }
    const results = yield* executeCalls(ctx, calls);  // 分批并行或串行
    ctx.history.append(toolResultMessage(results));   // BR-009
    ctx.steering.drainInto(ctx.history);              // 回合边界注入用户消息
  }
}
```

**工具调用批次划分**：按调用顺序扫描，连续的「只读且并发安全」调用合并为一个并行批次；遇到写类或执行类工具则单独成为串行批次；结果按原顺序回填（BR-008）。

**状态机**

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| Idle | 创建或上一次运行结束 | 调用 run |
| Streaming | 发起模型调用 | 模型流结束或出错 |
| Executing | 收到 tool\_use | 全部结果回填 |
| AwaitingPermission | 权限判定为 ask | 收到用户决定或超时 |
| Compacting | 触达压缩阈值 | 压缩完成或失败 |
| Done / Aborted / Failed | 正常结束 / 被中断 / 致命错误 | 不再迁移 |

**中断**：`AbortSignal` 同时传给 provider 流、工具与子进程；已产生但未执行的 tool\_use，以 `SY-LOOP-003` 的错误结果回填，保证历史合法（BR-009）。

**Steering**：运行中提交的消息进入队列，只在回合边界合并，不打断正在进行的模型流。

## DD-3 Provider 层

```ts
interface Provider {
  readonly id: string;
  capabilities(model: string): Capabilities;
  stream(req: ModelRequest, opts: { signal: AbortSignal }): AsyncIterable<ModelStreamEvent>;
  countTokens?(req: ModelRequest): Promise<number>;
}

interface Capabilities {
  contextWindow: number;
  maxOutputTokens: number;
  parallelToolCalls: boolean;
  thinking: 'none' | 'budget' | 'effort';
  promptCache: 'none' | 'explicit' | 'automatic';
  vision: boolean;
  structuredOutput: boolean;
  pricing?: Pricing;
}
```

**流式事件归一化**：各适配器把原生事件转为 `message_start`、`block_start`、`block_delta`、`block_stop`、`usage`、`message_stop(stopReason)`。`StopReason` 统一为 `end_turn | tool_use | max_tokens | refusal | error`。

**适配差异处理**

| 特性 | Anthropic | OpenAI Chat（含兼容服务） | Responses | Gemini |
| --- | --- | --- | --- | --- |
| 工具调用 | tool\_use 块 | tool\_calls 数组 | function\_call 项 | functionCall part |
| 并行工具 | 支持 | 支持（可开关） | 支持 | 支持 |
| thinking | thinking 块，带签名 | 因服务而异（如 reasoning 字段） | reasoning 项 | thought parts |
| 缓存 | 显式 cache\_control | 自动 | 自动 | 显式或自动 |

thinking 内容的回传规则由适配器按各 provider 要求决定，并以合约测试固化，内核只保证 `providerData` 原样保留。以上差异为立项时的认知，WP-0 中须对照最新官方文档核实。

**重试中间件**：`withRetry(provider, policy)` 实现 BR-014；只重试可重试错误；已向调用方发出过内容增量的流，仅当尚无已提交的工具调用时才重放。

**路由**：`ModelRouter` 支持角色 `main`、`fast`（用于摘要、标题等）、`fallback`（主模型连续失败后切换）。

## DD-4 工具系统与内置工具

```ts
interface Tool<I = unknown> {
  name: string;
  description: string | ((ctx: PromptContext) => string);
  inputSchema: z.ZodType<I>;
  risk: 'read' | 'write' | 'exec' | 'network' | 'meta';
  readOnly: boolean;
  concurrencySafe: boolean;
  timeoutMs?: number;
  permissionSubject?(input: I): PermissionSubject;   // 供规则匹配，如路径、命令
  execute(input: I, ctx: ToolContext): Promise<ToolOutput> | AsyncGenerator<ToolProgress, ToolOutput>;
}
```

**执行管道**：`validate → PreToolUse hooks → permission → execute(timeout, abort) → truncate → PostToolUse hooks → tool_result`。任何一步失败都以结构化错误结果回填，模型可据此自我纠正（BR-025）。

**FileStateTracker**：记录每个文件最近一次读取的 `{ path, mtimeMs, hash, range }`，为先读后写与外部修改检测提供依据（BR-004）。

**edit 算法**

1. 解析并规范化路径，经权限闸门。
2. 校验 tracker 中存在读取记录，否则 `SY-FS-001`。
3. 读取当前内容并比对哈希，不一致 `SY-FS-002`。
4. 统计 old 出现次数：0 次 `SY-FS-004`（附近似行提示）；多于 1 次且未指定 `replace_all` 为 `SY-FS-003`（附匹配位置）。
5. 替换后写入临时文件再原子重命名，保持原文件权限与换行风格。
6. 更新 tracker，返回变更摘要与 diff 片段。

**bash 工具**：经 `Shell` 抽象启动子进程，使用独立进程组以便整体终止；输出写入环形缓冲并按 BR-012 截断；工作目录在调用之间保持；支持后台任务（`bash_output`、`kill_shell` 配套工具）；默认超时 120s，可调。

**截断算法**：超出阈值时保留头部 40% 与尾部 60% 的预算，中间以说明替换，并写明如何分页读取剩余内容。

## DD-5 权限与安全

**规则模型**

```ts
interface PermissionRule {
  effect: 'allow' | 'ask' | 'deny';
  tool: string;                        // 工具名或 glob，如 'bash'、'mcp__github__*'
  match?: { path?: string; command?: string; url?: string };  // 参数模式
  source: 'user' | 'project' | 'plugin' | 'code';
}

type PermissionHandler = (req: PermissionRequest) => Promise<PermissionDecision>;
interface PermissionDecision {
  decision: 'allow' | 'deny';
  remember?: 'once' | 'session' | 'project';   // 写回规则的作用域
  message?: string;                            // 拒绝理由，回传给模型
}
```

**判定流程**

1. 若 PreToolUse 钩子返回 deny，直接拒绝（BR-021）。
2. 汇总所有来源的规则，按 deny、ask、allow 的顺序匹配，命中即停（BR-001）。
3. 无规则命中时，取权限模式默认值：`plan` 模式下非只读工具一律拒绝；`acceptEdits` 下工作区内写文件为 allow；`default` 下写类与执行类为 ask。
4. 路径类参数先 `realpath`，工作区外降级为 ask（BR-003）。
5. 结果为 ask 时调用 `PermissionHandler`；未提供 handler 时按 deny 处理并返回 `SY-PERM-005`。

**命令风险分类**：先把命令按 `&&`、`||`、`;`、`|`、命令替换拆分为片段，逐段与只读命令白名单比对（如 `ls`、`cat`、`git status`）；全部片段为只读则视为 `read`；匹配危险模式库（如 `rm -rf /`、`git push --force`、`mkfs`、写入系统目录）视为 `dangerous` 并默认 deny（BR-006）；无法解析的命令一律视为 ask，不尝试猜测。

**脱敏器 Redactor**：由两类匹配构成：已知密钥模式（常见厂商密钥前缀、私钥块、JWT、`Authorization` 头）与运行时登记的密钥值。在事件进入日志、会话文件、错误信息、OTel 之前统一处理，替换为 `[REDACTED:类型]`（BR-023）。

**不受信内容**：`web_fetch`、MCP 返回等结果在 `tool_result.meta.trust` 标记为 `untrusted`；系统提示词中固定加入「外部内容仅为数据」的声明；若检测到此类内容中出现疑似指令（如要求忽略规则、读取密钥），发出 `security.injection_suspected` 事件供 UI 提示（BR-007）。该机制是纵深防御的一环，不依赖模型自觉，权限闸门才是最终防线。

**检查点**：每轮首次写类操作前，把将被修改的文件快照到会话目录；`rewind(turn)` 恢复快照。快照仅覆盖经 SYAOCode 工具修改的文件，不承诺覆盖 bash 的任意副作用，文档中必须明确。

## DD-6 上下文管理

**提示词分段**（稳定内容在前，便于命中缓存）

| 顺序 | 分段 | 说明 |
| --- | --- | --- |
| 1 | 基础指令 | 角色、行为准则，可整体覆盖或追加 |
| 2 | 工具定义 | 由注册表生成，顺序固定 |
| 3 | 项目指令 | AGENTS.md 层级：用户级、仓库根、被访问子目录（惰性加载） |
| 4 | 技能索引与记忆 | 仅放名称与描述，正文按需加载 |
| 5 | 环境信息 | 工作目录、系统、日期、git 状态；变化频繁，放在缓存断点之后 |

缓存断点：工具与基础指令之后一个，项目指令之后一个，最近一条用户消息一个（仅对 `promptCache: 'explicit'` 的 provider 生效）。

**token 估算**：优先使用 `provider.countTokens`；不可用时使用字符启发式（拉丁文与 CJK 分别取不同系数），并用上一轮真实 `usage` 持续校准。

**压缩策略接口**

```ts
interface ContextStrategy {
  shouldCompact(state: ContextState): boolean;
  compact(state: ContextState, deps: { model: Provider; signal: AbortSignal }): Promise<CompactionResult>;
}
```

默认策略 `summarize` 的步骤：

1. 触发 PreCompact 钩子，发出 `context.compacting`。
2. 先做轻量清理：把早于最近 N 轮的工具结果替换为一行占位说明（保留工具名与参数摘要）。
3. 若仍超过阈值，选择切分点（必须落在回合边界，不得拆开 tool\_use 与 tool\_result 的配对），用 `fast` 模型对切分点之前的历史生成摘要。
4. 以一条合成的用户消息替换被摘要的历史，其中包含摘要与结构化状态：用户最初目标、待办、已修改文件列表、关键决策（BR-013）。
5. 发出 `context.compacted`，并写入会话日志的 compaction 条目。
6. 失败则回退到仅清理旧工具结果；仍无法容纳返回 `SY-CTX-002`。

**项目指令**：默认文件名 `AGENTS.md`，可配置兼容名单（如 `CLAUDE.md`）；子目录中的指令文件在 agent 首次读取该目录下文件时注入，而不是启动时全部加载。

## DD-7 会话与持久化

**日志条目**

```ts
interface LogEntry {
  v: 1;                       // schemaVersion
  id: string;                 // 单调递增的唯一 id
  ts: number;
  sessionId: string;
  parentId?: string;          // 分叉时指向父条目
  type: 'message' | 'usage' | 'compaction' | 'meta' | 'checkpoint' | 'fork';
  data: unknown;
}
```

```ts
interface SessionStore {
  append(sessionId: string, entries: LogEntry[]): Promise<void>;
  load(sessionId: string): AsyncIterable<LogEntry>;
  list(filter?: SessionFilter): Promise<SessionInfo[]>;
  fork(sessionId: string, atEntryId?: string): Promise<string>;
  delete(sessionId: string): Promise<void>;
}
```

**文件存储实现**：路径 `~/.syaocode/sessions/<项目哈希>/<sessionId>.jsonl`；追加写，批量刷盘（默认每 200ms 或每个回合结束）；同一会话以锁文件保证单写者；条目写入前经脱敏器。

**恢复**：流式读取并重建历史；遇到 compaction 条目，以其摘要作为新起点；末尾若存在没有 tool\_result 的 tool\_use，合成 `SY-LOOP-003` 结果使历史合法；单行 JSON 损坏则跳过并告警，超过阈值比例则 `SY-SES-002`；`v` 高于当前支持版本则 `SY-SES-003`（BR-016）。

**分叉**：复制到指定条目为止的日志到新会话，并在首条记录 `fork` 条目，保留血缘。

## DD-8 MCP 集成

```ts
interface McpServerConfig {
  name: string;
  transport:
    | { type: 'stdio'; command: string; args?: string[]; env?: Record<string, string>; cwd?: string }
    | { type: 'http'; url: string; headers?: Record<string, string>; auth?: 'oauth' | 'none' };
  trust?: boolean;                          // 为 true 才允许规则放行其工具
  enabled?: boolean;
  timeoutMs?: number;
  tools?: { include?: string[]; exclude?: string[] };
}
```

**生命周期**：`connect`（握手并协商能力）→ `listTools`（处理分页）→ 映射为 `Tool` → 运行 → `close`。断线按指数退避重连，重连后重新获取工具列表并以 `mcp.status` 事件通知；收到 `tools/list_changed` 通知时热更新注册表（FR-074）。

**工具映射**：名称为 `mcp__{server}__{tool}`，仅保留字母、数字、下划线、连字符；超过 64 字符时截断并附短哈希（BR-017）。对 DD-4 的补充：`Tool` 允许携带 `jsonSchema` 覆盖 Zod 生成的 schema，MCP 工具使用该字段向模型暴露原始 JSON Schema，参数校验交给服务器，客户端仅做基础类型检查。

**调用**：`callTool` 带取消与超时；返回内容按类型映射（文本、图片、资源引用、结构化内容）；`isError` 映射为 `tool_result.isError`，同时结果标记为 `untrusted`；风险级别默认 `network` 或 `exec`，即 ask（BR-018）。

**stdio 子进程管理**：stderr 导入 logger；关闭时先 SIGTERM，3 秒后 SIGKILL；父进程退出时确保子进程回收。

**鉴权**：HTTP 传输支持自定义头与 OAuth；令牌经注入的 `CredentialStore` 保存（默认文件权限 0600，可选系统密钥链），并登记到脱敏器。

**resources 与 prompts**：resources 通过 `mcp_list_resources`、`mcp_read_resource` 两个元工具暴露；prompts 映射为自定义斜杠命令（FR-072、FR-102）。

**服务端模式（P2）**：把 agent 封装为单个 `run_task` 工具暴露，复用同一套权限引擎。


**ACP 映射**（方法与字段名为立项时认知，WP-0 须对照官方规范核实）

## DD-10 插件系统

**插件清单**（`syaocode.plugin` 字段或独立清单文件，以下以对象形式示意）

```ts
const manifest = {
  name: '@acme/sy-plugin-jira',
  version: '1.0.0',
  engines: { syaocode: '^1.0.0' },          // BR-020
  main: './dist/index.js',
  contributes: ['tools', 'commands', 'hooks'],
  permissions: { net: ['*.atlassian.net'], fs: 'none', exec: false, env: ['JIRA_TOKEN'] },
  configSchema: './schema.json',
};
```

**插件入口**

```ts
export default definePlugin({
  async setup(api: PluginApi) {
    api.registerTool(searchIssuesTool);
    api.registerCommand('jira', jiraCommand);
    api.registerHook('PreToolUse', guardHook);
    // 还可：registerProvider / registerMcpServer / registerSkill
  },
  async dispose() {},
});
```

**基于能力的 API**：插件拿到的 `api.runtime` 是按清单权限裁剪后的代理（受限域名的 `http`、只读或受限路径的 `fs`），插件通过正常途径只能使用被授予的能力。

> **必须明确的边界**：进程内插件无法阻止恶意代码直接 `import 'node:fs'`，因此权限声明在 v1.0 是「约定加审计加首次确认」，不是硬隔离。需要硬隔离的第三方能力应以 MCP 子进程形式提供；v1.x 评估基于 Node 权限模型或 Worker 的隔离加载。此项已纳入风险 R-07，并须写入对外文档。

**生命周期**

| 状态 | 说明 |
| --- | --- |
| discovered | 在用户目录、项目目录或配置的包名中发现 |
| validated | 清单通过 Zod 校验，`engines` 匹配（`SY-PLG-001`、`SY-PLG-002`） |
| loaded | 动态 `import()` 成功，`setup` 在 5s 内完成（`SY-PLG-003`） |
| enabled | 用户已确认其权限声明，贡献项已注册 |
| disabled / failed | 用户禁用，或连续 3 次运行时异常被自动禁用（BR-019） |
| unloaded | 调用 `dispose`，注销全部贡献项 |

**信任确认**：首次启用时列出清单中的权限与贡献项，由用户确认；确认记录入口文件哈希，清单或入口变化后重新确认。

**错误边界**：插件提供的所有回调（工具、钩子、命令）均被统一包装，异常转为 `SY-PLG-005` 并按 BR-019 计数，不向宿主抛出。

## DD-11 钩子、技能、命令与子 agent

**钩子**

```ts
type HookEvent = 'SessionStart' | 'UserPromptSubmit' | 'PreToolUse' | 'PostToolUse'
  | 'PreCompact' | 'Stop' | 'SubagentStop' | 'SessionEnd';

interface HookResult {
  decision?: 'allow' | 'deny' | 'ask';
  reason?: string;
  updatedInput?: unknown;            // 仅 PreToolUse 可用
  additionalContext?: string;        // 注入上下文
  continue?: boolean;                // Stop 钩子要求继续
}
type HookHandler = (input: HookInput, ctx: HookContext) => Promise<HookResult | void>;
```

钩子可由代码函数提供，也可配置为外部命令：事件 JSON 从 stdin 传入，stdout 返回结果 JSON，退出码 2 表示阻断。按配置顺序执行，超时默认 10s，`failMode` 默认 `closed`（BR-021）。`updatedInput` 改写后的参数必须重新通过 schema 校验与权限判定。

**技能 Skills（FR-101）**：目录结构 `skills/<name>/SKILL.md`，前置元数据含 `name`、`description`。提示词中只放技能索引（名称加描述）；模型通过 `skill` 工具按需加载正文，正文中引用的相对资源在加载时按路径解析。技能内容同样受 BR-007 约束，不得提升权限。

**自定义命令（FR-102）**：`commands/*.md`，前置元数据加正文模板，支持 `$ARGUMENTS` 占位；也可由插件以代码注册。MCP prompts 映射为同类命令。

**子 agent（FR-103）**

```ts
interface AgentDefinition {
  name: string;
  description: string;               // 供主 agent 决策何时委派
  systemPrompt: string;
  tools?: string[];                  // 必须是父工具集的子集
  model?: string;
  maxTurns?: number;
}
```

通过内置工具 `task` 委派：新建独立实例，独立历史与预算；权限不得超出父级（BR-022），权限请求冒泡到父级的 `PermissionHandler` 并标注 `agentId`；只读子 agent 可并行，其余串行；仅把最终文本与用量汇总返回给父 agent；子事件以 `agentId` 标注后转发；默认最大嵌套深度 2。

## DD-12 可观测性

**Logger**：`debug | info | warn | error` 四级，结构化字段，默认空实现或写 stderr 由应用决定；所有输出过脱敏器（BR-023）。

**Trace 结构**：`session` span 包含多个 `turn` span，每个 turn 内含 `model.call` 与 `tool.call` 子 span；子 agent 作为子树挂在发起它的 `tool.call` 下。属性命名对齐 OpenTelemetry GenAI 语义约定（字段名以实现时的规范版本为准）。**默认不记录提示词与工具内容**，需显式开启 `captureContent`。

**Metrics**：token 用量（输入、输出、缓存读写）、模型延迟、工具耗时、按错误码计数、压缩次数。

**费用**：`UsageTracker` 按 `Capabilities.pricing` 与 `usage`（含缓存读写）累计，超预算则向 `limits` 报告（BR-010）。

#### 输入语法与按键

- `@path`：引用文件/目录，TUI 展示实际解析路径并允许移除；目录先汇总再按需读取，不直接塞入完整上下文。
- `!command`：显式提议 shell 命令；仍经 schema、风险分类、权限和审批，不是绕过通道。
- `/name`：命令；未知斜杠命令应给出相近建议。
- `Esc`：取消当前生成/子进程并向下传播 AbortSignal。
- `Ctrl+C`：第一次取消当前动作，第二次退出；退出前保证会话日志状态合法。
- `Ctrl+R`：搜索历史；`Shift+Enter`：输入换行。
- 权限模式切换应在状态栏明显显示，不应使用“快捷键一按就进入无审批高危模式”的默认行为。

#### 输出、退出码与协议

| 退出码 | 意义 |
| --- | --- |
| `0` | 任务完成且满足配置的验收策略 |
| `1` | 未分类运行错误 |
| `2` | 参数、配置或协议格式错误 |
| `3` | 权限拒绝/无法满足权限导致任务未完成 |
| `4` | 预算、轮次或总时长上限触发 |
| `5` | Agent 运行结束，但确定性验收失败或未通过 |
| `130` | 用户中断（SIGINT） |

JSON/stream-json envelope 必须包含 `schemaVersion`、`sessionId`、`runId`、事件类型、时间戳与事件 payload。未知非关键事件可忽略；schema 主版本不兼容必须明确失败。stdout 用于协议，stderr 用于人类诊断。

#### MCP CLI 约定

- 用户级配置默认位于 `~/.syaocode/config.json`；项目级 `.syaocode/config.json`；私有本地配置 `.syaocode/local.json`，后者应加入 `.gitignore`。
- 项目级 MCP server、hook、plugin 首次使用前显示来源和权限，请用户确认；清单/命令哈希变化后重新确认。
- 外部 MCP 工具默认 `ask`；server 的只读注解不等于授权，工具描述属于不可信输入。
- MCP 的 stdio 子进程不是强沙箱；其 OS 权限应通过启动环境、容器/OS policy 或独立用户账户进一步限制。

## DD-15 错误处理与韧性（横切）

**错误边界**

| 边界位置 | 捕获内容 | 处理 |
| --- | --- | --- |
| Provider 适配器 | SDK 与 HTTP 异常 | 转为 `SY-PRV-*`，标注 retryable |
| 工具管道 | 校验、执行、超时异常 | 转为 `SY-TOOL-*`，以 tool\_result 回填模型 |
| 插件与钩子包装层 | 第三方代码异常 | 转为 `SY-PLG-*` 或 `SY-HOOK-*`，计数与隔离 |
| MCP 客户端 | 连接与调用异常 | 转为 `SY-MCP-*`，触发重连策略 |
| SessionStore | IO 与格式异常 | 转为 `SY-SES-*`，尽量降级继续 |
| 内核顶层 | 其余未预期异常 | 转为 `SY-INT-001`，事件流以 fatal error 结束 |

**取消树**：`AbortController` 形成「会话 → 回合 → 工具调用 → 子进程」的树，上层取消向下传播。

**资源管理**：会话、子进程、MCP 连接实现 `AsyncDisposable`，支持 `await using`；`agent.close()` 幂等。

**进程级行为**：库不注册 `uncaughtException`、`unhandledRejection` 与信号处理，这些只在 CLI 中处理（NFR-011）。

**背压**：事件总线对每个订阅者使用有界队列。持久化订阅者采用阻塞策略以保证不丢；UI 订阅者可合并连续的 `text.delta`，保证慢消费者不拖垮循环。

**国际化**：错误 `message` 默认英文；`@syaocode/core/i18n` 提供按 code 索引的 zh-CN 消息表（NFR-023）。

## DD-16 决策层（Decision Plane）详细设计

### DD-16.1 目标与边界

`@syaocode/decision` 为有限选项判断提供一致接口。它不执行工具、不保存 provider 密钥、不拥有 PermissionEngine，也不接受“模型说安全所以放行”的调用方式。

### DD-16.2 领域类型

```ts
export type DecisionMode = 'off' | 'shadow' | 'enforce';
export type DecisionKind = 'choice' | 'score' | 'noul';
export type DecisionAction =
  | 'route_hyaki' | 'route_sota' | 'route_common'
  | 'raise_to_ask' | 'raise_to_deny'
  | 'suggest_retry' | 'suggest_replan'
  | 'completion_candidate' | 'unverified';

export interface DecisionRequest {
  decisionPointId: string;
  schemaVersion: number;
  state: unknown;              // 构建之前须经 allowlist + redact
  questions: DecisionQuestion[];
  modelVersion?: string;       // enforce 模式要求固定版本
  timeoutMs: number;
  sessionId: string;
  runId: string;
}

export type DecisionQuestion =
  | { id: string; type: 'choice'; instructions: string; options: { id: string; description?: string }[] }
  | { id: string; type: 'score'; instructions: string; levels: { value: number; label: string }[] }
  | { id: string; type: 'noul'; instructions: string; trueCriteria?: string; falseCriteria?: string };

export interface DecisionAnswer {
  questionId: string;
  type: DecisionKind;
  value: string | number | boolean | null;
  probabilities?: Record<string, number>;
  confidence?: number;          // optional; Noul providers may only provide P(yes)
  rawYesProbability?: number;   // normalize Noul without inventing confidence
}

export interface DecisionResult {
  providerId: string;
  modelVersion?: string;
  answers: DecisionAnswer[];
  elapsedMs: number;
  inputTokens?: number;
  costUsd?: number;
  degraded: boolean;
  errorCode?: string;
}

export interface DecisionProvider {
  readonly id: string;
  judge(request: DecisionRequest, signal?: AbortSignal): Promise<DecisionResult>;
  close?(): Promise<void>;
}
```

**Schema 约束**：`DecisionResult` 的值必须匹配 question type 与已定义候选。不能把未知选项自动映射为 `allow`。无 `confidence` 的输出保持缺失，不能伪造 1.0。超出状态限制、非法概率、缺少题目 ID 或模型版本异常都视为非法响应。

### DD-16.3 决策点注册

```ts
interface DecisionPointDefinition {
  id: string;
  version: number;
  mode: DecisionMode;
  buildRequest(ctx: DecisionContext): DecisionRequest | null;
  allowedStatePaths: string[];
  timeoutMs: number;
  policy(result: DecisionResult, ctx: DecisionContext): DecisionAction;
  onFailure: 'safe_ask' | 'default_route' | 'unverified' | 'keep_all';
  minEvalVersion?: string;
}
```

建议的首批决策点：

| ID | 决策问题 | v1.0 模式 | 允许影响 |
| --- | --- | --- | --- |
| DP-01 | 当前任务是否需要长输入摘要/高推理规划/直接执行 | off/shadow | 仅路由建议，不改权限 |
| DP-03 | 计划动作是否出现更高风险信号 | shadow | 只可升级为 ask/deny |
| DP-07 | 自然语言目标是否看似完成 | shadow | 只能成为候选；不能替代确定性验收 |
| DP-08 | 失败应重试、换方法、重规划还是提问 | shadow | 推荐下一阶段，不直接执行未授权动作 |
| DP-05 | 外部内容是否疑似提示注入 | shadow/P1 | 只用于增加风险或隔离提示 |

所有决策点都必须有版本化样本集。`enforce` 需要通过评测门槛和显式配置；首版不提供“JEV 自动批准工具”的能力。

### DD-16.4 调用顺序与降级

1. deterministic rules 先检查硬约束和预算。
2. 根据决策点生成最小状态：用户目标摘要、当前阶段、工具名、规范化参数的允许字段、已有验收状态；不默认包含代码全文或主模型推理。
3. 状态通过脱敏和长度限制；若超限，先由本地摘要器缩减或回退规则，不把整个会话无差别发给 JEV。
4. 在同一回合内对相同 `stateHash + questionVersion + modelVersion` 去重；缓存范围仅限同一会话且有 TTL。
5. 调用 provider。429/5xx/超时按不同错误分类；安全点回退 ask/deny，路由点使用静态默认值，完成度点回退未验证。
6. `shadow` 只记录“如果 enforce 会采取什么动作”；实际动作沿旧规则执行。
7. `enforce` 只应用决策点白名单中的收紧/路由动作；不能修改权限配置。
8. 产出 `decision` 事件与 `DecisionReceipt`，记录 schema/model/provider 版本、脱敏输入哈希、返回摘要、阈值、决策模式、耗时、成本、降级原因和真实后续结果。

### DD-16.5 JEV adapter 与隐私

JEV adapter 独立放在 `@syaocode/decision-jev`（或作为 optional subpath）中；core 不静态导入专有 SDK。endpoint、模型 ID、凭证来源与重试语义均由配置注入，并在 M0 对官方 SDK/REST contract 验证。密钥只从环境变量或系统密钥链读取。

提供 `decision.egress = allow|deny`、`decision.redactionProfile`、最大外发字符/token、允许字段列表。`deny` 时不得调用任何远端 judge；缺少密钥时自动切换到 off/local rules。日志保存输入哈希与经脱敏摘要，不保存原始密钥或敏感文件全文。

### DD-16.6 校准与准入门槛

- 每个决策点至少准备 100 个代表性样本起步；关键安全评估目标不少于 300 个样本并覆盖对抗变体。样本不足时只做 shadow。
- 报告混淆矩阵、precision/recall、false allow、false block、覆盖率、Brier/ECE（样本允许时）、p50/p95 延迟、每千次成本和人工覆盖率。
- 任何一个已知高风险样本被误判为自动允许即阻止该决策点进入 enforce。
- 模型版本、提示问题版本或状态构造逻辑发生变化后重新跑回归集。

## DD-17 本地服务与客户端协议详细设计（v1.1）

### DD-17.1 目标

把 AgentRuntime 生命周期留在一个服务端，由 CLI attach、未来 Desktop 和第三方客户端订阅事件。该层与 MCP 分开：MCP 用于接入外部工具；SYAOCode Server API 用于控制 SYAOCode 自己的运行时。

### DD-17.2 资源模型

- `Session`: 会话基础信息和事件日志引用。
- `Run`: 一次运行，包含输入、状态、预算、开始/结束时间和结果。
- `Agent`: 当前进程内/服务内的角色实例与父子关系。
- `PermissionRequest`: 待处理权限请求，带过期时间与一次性应答 token。
- `Artifact`: diff、报告、验证输出等可读取产物。
- `Subscription`: 客户端事件订阅；断线后通过事件序号继续读取，是否能够补齐取决于保留策略。

### DD-17.3 初始 HTTP API 草案

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/v1/health` | 健康状态（不返回 secrets） |
| `GET/POST` | `/v1/sessions` | 查询/创建会话 |
| `GET` | `/v1/sessions/{id}` | 会话状态 |
| `POST` | `/v1/sessions/{id}/runs` | 创建一次运行 |
| `POST` | `/v1/runs/{id}/cancel` | 取消运行 |
| `GET` | `/v1/runs/{id}/events` | 事件流订阅（SSE） |
| `GET` | `/v1/permissions/pending` | 当前待审批请求 |
| `POST` | `/v1/permissions/{id}/respond` | 一次性应答；服务端校验权限和超时 |
| `GET` | `/v1/artifacts/{id}` | 读取 diff/报告/安全可公开产物 |

协议须发布 OpenAPI 与事件 JSON Schema，并给出 `schemaVersion`。以上路径是本项目 API 草案，不代表任何外部标准。

### DD-17.4 安全与并发

- 默认只监听 `127.0.0.1` 或本地 socket；远程监听要求显式 `--host`、强 token、TLS/SSH 隧道建议和明显警告。
- token 至少 256 bit 随机；文件权限在 POSIX 环境为 0600；Windows 使用当前用户 ACL；不可写入日志。
- 默认拒绝跨源浏览器请求；如未来 UI 需要，必须采用明确的 origin allowlist 与 CSRF 防护。
- 服务端为每个会话设置 single-writer lease；多客户端可以只读订阅，写入/权限回应需持有 lease 或一次性 token。
- 同一权限请求只能成功响应一次；超时、重复应答和会话关闭均返回结构化错误。
- `serve` 进程关闭时先停止接收新 run，再取消/等待现有 run，最后 flush 事件日志。

## DD-18 三角色 Agent 编排与证据账本详细设计

### DD-18.1 内置角色与能力预算

```ts
export type AgentRoleId = 'hyaki' | 'sota' | 'common' | (string & {});
export interface AgentRoleConfig {
  id: AgentRoleId;
  provider: string;
  model: string;
  systemPromptRef: string;
  toolAllowlist: string[];
  maxTurns: number;
  maxTokens?: number;
  maxCostUsd?: number;
  timeoutMs: number;
  reasoningEffort?: 'low' | 'medium' | 'high';
}
```

- `hyaki` 默认只允许 read/glob/grep/web_fetch（如果 web 功能开启）；不得写入、执行 shell 或改变配置。
- `sota` 默认使用只读工具；不得通过计划文本授予 common 新权限。
- `common` 获取的工具仍受父会话权限引擎约束；交接 Plan 中写出的权限需求只代表“请求”，不是授权。
- 子 agent 的 `maxCostUsd`、`maxTurns`、`timeoutMs` 不得大于父 run 剩余预算；父 run 取消时所有子角色和工具进程收到取消。

### DD-18.2 交接物 schema

```ts
interface SourceRef {
  uri: string;                  // workspace 相对路径或已允许的来源标识
  lineStart?: number;
  lineEnd?: number;
  contentHash?: string;
  excerpt?: string;              // 有长度上限并经过脱敏
}
interface FactItem {
  id: string;
  statement: string;
  exactLiteral?: string;         // 数字、错误码、路径、名称等不可随意改写的文本
  sourceRefs: SourceRef[];
  confidenceLabel: 'observed' | 'inferred' | 'unknown';
}
interface Brief {
  schemaVersion: 1;
  taskId: string;
  summary: string;
  facts: FactItem[];
  userConstraints: string[];
  unknowns: string[];
  recommendedNextStep: 'plan' | 'execute' | 'ask_user';
}
interface PlanStep {
  id: string;
  description: string;
  dependsOn: string[];
  touchedPaths: string[];
  proposedTools: string[];
  acceptanceChecks: string[];
  risk: 'low' | 'medium' | 'high';
  rollbackNotes: string[];
}
interface Plan {
  schemaVersion: 1;
  goal: string;
  steps: PlanStep[];
  globalAcceptance: string[];
  maxCostUsd: number;
  maxTurns: number;
  stopConditions: string[];
  openQuestions: string[];
}
interface EvidenceReceipt {
  id: string;
  kind: 'file_diff' | 'command' | 'test' | 'manual_review' | 'decision';
  createdAt: number;
  status: 'pass' | 'fail' | 'unknown';
  summary: string;
  artifactRef?: string;
  exitCode?: number;
  sourceRefs?: SourceRef[];
  contentHash?: string;
}
interface Result {
  schemaVersion: 1;
  taskId: string;
  completedSteps: string[];
  failedSteps: string[];
  changedFiles: { path: string; beforeHash?: string; afterHash?: string; diffRef?: string }[];
  receipts: EvidenceReceipt[];
  blockers: string[];
  remainingBudgetUsd: number;
}
```

### DD-18.3 Orchestrator 状态机

1. `INTAKE`: 接收目标、读取工作区元数据，识别用户约束和敏感范围。
2. `ROUTE`: 由规则先判断输入量、任务规模与可用角色；JEV 只提供路由建议。
3. `SYNTHESIZE`: 大输入交给 hyaki；Brief 中每条关键事实必须有引用或显式标记 unknown。
4. `PLAN`: sota 输出 Plan，内核校验步骤依赖、预算、目标路径和验收条件。
5. `APPROVAL`: 预判会触及的权限；一次性把必要高风险操作展示给用户；用户批准仅适用于具体请求范围。
6. `EXECUTE`: common 逐步执行；写入由单一文件协调器串行化；每步记录变更前哈希、diff 和命令结果。
7. `VERIFY`: 运行确定性验收器（测试/类型检查/lint/文件断言）；生成 EvidenceReceipt。
8. `REVIEW`: 验收失败或风险高时把证据交给 sota；最多重规划默认 3 次。
9. `DONE`: 仅当明确验收策略达成才标记 `verified`; 否则输出 `partially_completed`、`blocked` 或 `unverified`。

### DD-18.4 任务路由与成本策略

初始规则建议：小任务（上下文少、≤3 个文件、目标单一）直达 common；输入超过约 20k tokens 或涉及大量文档时优先 hyaki；跨模块设计/多方案/连续失败时调用 sota。20k/10 文件是配置初值，不是通用最优阈值，应通过 PoC-10 调整。

三个预设只是模型/预算策略：

| 预设 | 默认路线 | 适用场景 | 约束 |
| --- | --- | --- | --- |
| `economy` | common 优先；长输入才 hyaki；失败后 sota | 小任务、代码问答、低成本探索 | 总成本最低优先；遇高复杂度必须升级/提示 |
| `balanced` | 大输入 hyaki；sota 做计划；common 执行 | 默认工作流 | 成本、成功率、速度均衡 |
| `max` | 必要时 hyaki；sota 先规划、关键步骤复核；common 执行 | 高影响重构或长任务 | 不意味着权限放宽，仍按预算与确认策略运行 |

### DD-18.5 文件冲突、并行与回滚

- hyaki 可并行读不同片段；任何两个角色不得同时写同一路径。
- common 的写操作先检查工作区、分支、文件哈希是否与 Plan 创建时一致；不一致则重新读取/重规划。
- 每个逻辑步骤生成独立 diff；默认建议工作区位于 Git 仓库并提醒建立 checkpoint，但不假定所有项目都有 Git。
- 文件工具变更可通过反向 diff 尝试回滚；shell 命令、网络调用、数据库变更等副作用需记录为“不保证可回滚”。
- `EvidenceLedger` 持久化来源引用、工具调用、diff、测试和最终判断；只记录必要片段，默认对日志内容脱敏。

## DD-19 Goal / Loop 自治运行详细设计

### DD-19.1 Goal 数据模型

```ts
interface GoalSpec {
  id: string;
  objective: string;
  acceptance: ({ type: 'command'; command: string; expectedExitCode?: number }
    | { type: 'file_exists'; path: string }
    | { type: 'file_contains'; path: string; literal: string }
    | { type: 'custom'; verifierId: string; input?: unknown })[];
  maxTurns: number;
  maxCostUsd: number;
  timeoutMs: number;
  maxReplans: number;
  permissionMode: 'default' | 'plan' | 'acceptEdits';
}
interface GoalReport {
  goalId: string;
  state: 'verified' | 'unverified' | 'blocked' | 'failed' | 'cancelled' | 'budget_exhausted';
  acceptanceResults: { id: string; status: 'pass' | 'fail' | 'unknown'; outputRef?: string }[];
  changedFiles: string[];
  decisionReceipts: string[];
  totalCostUsd: number;
  elapsedMs: number;
  stopReason: string;
}
```

### DD-19.2 Goal 运行循环

```text
validate GoalSpec
  → snapshot workspace state
  → orchestrator run one iteration
  → run deterministic verifiers
  → if all required verifiers pass: verified
  → else if budget/turn/time/replan limit reached: stop + report
  → else if blockers need user or permission: blocked / await in TUI
  → else update plan and continue
```

JEV Noul 可以回答“目标看起来是否满足”作为辅助指标；它不能替代 `command`、测试或文件断言。不存在确定性验收条件时，报告状态最多为 `unverified` 或“语义候选完成”，由用户决定是否接受。

### DD-19.3 Loop 运行模型（v1.1）

`LoopSpec` 必须具备 `trigger`、`maxRuns`、`until`（或明确停止条件）、`perRunBudgetUsd`、`totalBudgetUsd`、`timeoutMs`、`failurePolicy`、`permissionPolicy`。支持 fixed interval、基于明确事件的 trigger；不支持自然语言“永远运行”这种没有结束条件的任务。

- loop 每轮采用新的短上下文，并从 `LoopState` 载入只保留的状态摘要和上轮 `EvidenceReceipt`。
- 每轮有独立 runId，和 loopId 关联；所有日志可追踪到触发事件。
- 无人值守时，任何 `ask` 等同于暂停/拒绝该轮，不可假设用户批准。
- 连续失败 3 次、预算耗尽、最大运行次数达到、工作区分支/权限设置变化、MCP 凭证失效时暂停。
- `pause/resume/stop` 是幂等操作；恢复时重新校验 `GoalSpec`、配置、工作区和授权状态。
- v1.1 只实现本机运行与本地状态；跨设备/云端 scheduler 不在此范围。

### DD-19.4 运行安全与防失控

1. 每个 Goal/Loop 必须提前设定模型费用、回合、运行时长上限；超限时不再发起新模型调用。
2. 对自动执行设置命令与路径 allowlist；禁止动作始终有效，无法询问用户时转为 deny/暂停。
3. 运行前显示将要影响的目录、模型/角色 preset、预算、验收器和授权模式；后台 loop 启动需明确确认。
4. 每轮写入前记录文件快照或哈希；关键变更可以设置“每步确认”或“每轮确认”。
5. 为每轮输出可读报告：做了什么、变更文件、执行命令、验收结果、成本、停止原因和下一步建议。
6. Loop 不是安全监控系统，不应被用于绕过平台/服务的使用条款、访问控制或频率限制。
