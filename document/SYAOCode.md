## v0.3 修订摘要

本版以「先交付可用 CLI，再扩展本地服务与 Desktop」为主线，保留 TypeScript harness 库优先的产品定位，同时将核心差异化收敛为可验证的机制：

1. **分层协同**：确定性控制面（权限、路径、预算、验收）是最终权威；L0 Decision Plane 通过 `DecisionProvider` 调用 JEV 或替代 judge 处理有限选项的判断题；L1 Generation Plane 由 LLM 进行生成与推理；L2 Action Plane 通过内置工具、MCP 和插件执行动作。
2. **三角色 agents**：hyaki 负责大输入的证据提取、分块与保真摘要；sota 负责规划、复杂推理和独立评审；common 负责实际修改、命令执行和验证。角色之间只传带 schema 与来源引用的交接物，不能相互转交权限。
3. **Goal / Loop**：v1.0 提供受预算与验收条件约束的 `/goal` 最小闭环；`/loop` 的定时、条件触发和后台调度列为 v1.1，防止首版过度扩张。
4. **CLI-first**：统一交互 TUI、非交互执行、管道输入、结构化输出、会话恢复、权限审批、MCP 管理、配置诊断与 agents 操作。命令参考 Claude Code、Codex CLI、ZCode、MiMo Code 与 DeepSeek Harness 的公开行为，但不复制代码、私有提示词或商标表达，也不承诺逐项兼容。
5. **MCP 版本治理**：面向当前 MCP 2026-07-28 规范与 TypeScript SDK v2 设计版本协商、传输适配和能力降级；旧协议只作为兼容路径，不把已弃用能力当作新实现的基础。
6. **补齐详细设计**：新增 DD-16（决策层）、DD-17（服务化协议）、DD-18（三角色编排）、DD-19（Goal / Loop）；为 DEC、AGT、RUN、SRV 等错误码补齐注册与测试要求。
7. **重估计划**：将 agents、JEV、CLI、MCP 和回归评测纳入 WBS；v1.0 目标按约 127 人日的 P0 基线估算，单人兼职开发实际周期须加缓冲，不能按短期项目承诺。

## 本版关键一致性修复

- 补齐 DD-16 至 DD-19，不再出现需求有引用但详细设计不存在的断链。
- WBS 改为明确区分 v1.0 P0 与 v1.1 P1；ACP 与 Desktop 不再被误列入首版关键路径。
- 把错误体系登记表扩展到 DEC/AGT/RUN/SRV/CLI，并要求每个 active 错误码有测试。
- 明确 JEV 的 Noul 概率不能伪装成通用 confidence；所有 decision 输出都需 schema 校验、回放和版本记录。
- 明确工具执行必须经过权限管线；MCP server、插件、hooks 和模型输出本身都不构成信任凭证。
- 将 Goal 的“已验证完成”与“语义上看似完成”分开；loop 必须有 `maxRuns`、停止条件、预算和时长上限。
- 收敛首版范围，避免在 CLI 核心尚未稳定时同时做 Desktop、ACP、任意插件市场与后台调度器。

## 文档使用约定

- **规范性要求**：SRS、BR、RTM、DD、错误码、测试准入准出为开发与验收依据。
- **预研假设**：具体模型、价格、延迟、JEV SDK 字段和 MCP 兼容性必须用 M0 的官方文档与 PoC 复核。
- **安全边界**：模型建议不是授权；权限引擎和执行环境是最终控制点。任何模型不能把 `deny` 提升为 `allow`。
- **版本术语**：v1.0 指 CLI-first 的首个稳定可用版本；v1.1 指本地 `serve/attach`、loop 调度等增强；Desktop 是后续独立阶段。

## 1.2 背景与问题

Claude Code、Codex CLI 等 agent 工作流工具已形成共同范式：LLM 加工具加循环，再叠加上下文管理、权限控制和扩展机制。现状存在三个缺口：

1. 主流产品多数与特定模型或厂商绑定，换模型成本高。
2. 多数产品以「应用」形态交付，难以作为库嵌入到自己的系统（IDE 插件、Web 后端、CI 机器人）。
3. 协议零散：MCP、ACP（编辑器接入）、A2A（agent 互通）、各家模型 API 形态不一，缺少一个 TS 原生、统一接入的基础设施。

## 1.3 愿景与定位

**SYAOCode 是一个 TypeScript 原生、模型中立、可嵌入、可审计的 Agent Harness，并以 CLI 作为第一个完整产品。**它既能作为 `@syaocode/*` 库嵌入其他应用，也提供日常编码与自动化工作流的命令行入口。

### 产品核心：三层协同 + 确定性控制面

- **L0 Decision Plane（判断）**：通过 `DecisionProvider` 将 JEV 作为优先候选，用于有限选项的语义分类、路由、风险提升、完成度建议和失败分诊。JEV 是可替换的决策提供者，不是整套 Agent 的唯一依赖。
- **L1 Generation Plane（生成）**：主 LLM 承担理解、规划、代码生成、复杂推理、修复建议和解释；按任务需要由 hyaki、sota、common 三个角色分工。
- **L2 Action Plane（执行）**：内置工具、MCP、受信插件和子进程负责文件、命令与外部系统操作。
- **确定性控制面（最高权威）**：权限、工作区围栏、危险命令策略、预算、并发限制、验收器和取消机制独立于模型。所有有副作用的动作必须经过该控制面；JEV 或 LLM 都不能授予本来没有的权限。

### 三个内置角色

| 角色 | 主要职责 | 典型模型取向 | 默认权限 | 标准交接物 |
| --- | --- | --- | --- | --- |
| `hyaki` | 大规模文本、多文件、日志、网页与文档的分块读取；提取事实、错误、数字、路径与引用；分层摘要 | 长上下文、低成本、高吞吐 | 只读 | `Brief` / `EvidenceIndex` |
| `sota` | 任务拆解、方案比较、风险分析、复杂推理、重规划与独立评审 | 高推理能力、调用频率较低 | 只读 | `Plan` / `Review` |
| `common` | 根据计划落实文件修改、命令、测试、MCP 操作；收集验证证据 | 成本与编码能力均衡 | 按会话权限受控的读写与执行 | `Result` / `EvidenceReceipt` |

这些是产品角色，不是模型名称。用户可以为每个角色绑定不同 Provider、模型、思考强度、预算与工具集。任务较小时允许绕过多角色流程，直接进入 common，避免为了“多 Agent”而额外增加 token 与延迟。

### 交付顺序

1. **第一阶段：CLI v1.0**——打通从理解仓库、规划、修改、执行测试到验收报告的闭环。
2. **第二阶段：服务化 v1.1**——增加本地 `serve/attach`，让多个客户端观察/控制同一会话。
3. **第三阶段：Desktop**——CLI 与 Desktop 共用内核、事件 schema、会话协议和客户端 SDK，不复制 Agent 逻辑。

### 创新方向（纳入产品设计，而不是首版全部实现）

- **Evidence Ledger（证据账本）**：每个关键事实、计划步骤、文件变更和验收结果都链接来源或命令输出，降低摘要失真与“声称完成但没有证据”的风险。
- **Adaptive Routing（自适应路由）**：基于输入规模、任务类型、历史失败、预算剩余与 Provider 能力决定是否调用 hyaki/sota/common；规则优先，JEV 仅提供判断信号。
- **Verified Goal（可验证目标）**：尽量把自然语言目标转成验收命令、文件断言或测试；验收器没通过就不能仅凭模型说“完成”而停止。
- **Checkpointed Change Set（检查点变更集）**：每批文件修改记录基线哈希和 diff；验证失败可恢复由 SYAOCode 文件工具管理的变更。Shell 的任意副作用不能假装可回滚。
- **Replayable Runs（可回放运行）**：事件日志、provider cassette、工具结果和决策版本共同支撑 bug 复现、成本对比与模型替换评测。
- **Workflow Distillation（工作流沉淀）**：在后续版本把重复成功任务归纳为 Skill/Workflow 候选，但必须由用户审阅，不能自动将不可信会话内容转成高权限插件。

| G5 | 安全边界可审计 | 无模型能覆盖 deny；权限、路径、预算、工具执行和关键决策均有事件 |

| G7 | 三角色协作有实际价值 | 与“全程 sota”基线比较成本、成功率、耗时；目标成本下降 ≥ 25%，成功率下降不超过 5 个百分点，未达标不宣传收益 |

| G9 | 工程可持续 | core 行覆盖率 ≥ 80%、分支 ≥ 70%；公共 API/事件/错误码自动合约检查 |
| G10 | Desktop 可复用 | `AgentEvent`、会话 schema 与客户端边界有文档和版本策略；不以 v1.0 提前实现 Desktop |

**指标约定**：G1 与 G7 是工程评测目标，不是对任意仓库或模型的效果保证。M0/M1 建立基线后，若评测任务不足以支撑统计，应先扩大样本，再调整数字。

## 1.5 范围

### v1.0 必须交付（P0）

- Agent Loop、流式事件、取消、轮次/时长/token/费用预算、工具调用历史一致性。
- Provider 抽象、能力声明、MockProvider、OpenAI-compatible 适配器、一个原生 Provider；失败重试与用量统计。
- 本地编码基础工具：read/write/edit 的最小可靠实现、glob/grep、受限 shell；路径围栏、权限审批、危险命令防护。`apply_patch` 列为 P1，首版可通过多次可靠的 `edit` 完成修改。
- 会话 JSONL 持久化、恢复、基础分叉/检查点、上下文截断与压缩。
- CLI TUI、`-p` 非交互执行、管道输入、`text/json/stream-json`、稳定退出码、`--model`、`--permission-mode`、`--max-turns`、`--max-budget-usd`、会话继续与恢复。
- `hyaki`、`sota`、`common` 三角色最小编排：结构化交接、角色预算、权限继承、失败时可升级到 sota。
- `/goal` 最小闭环：目标、验收器、最大续跑次数、总预算、取消、报告。
- JEV 的 `DecisionProvider` 接口和可选适配器；off 为默认、shadow 显式启用，并具备超时、熔断、回退、决策日志与脱敏。
- MCP 客户端的 stdio 与 Streamable HTTP 传输、工具发现与调用；服务器首次信任确认。
- 配置、`doctor`、基础 `mcp` 命令、错误体系、最小评测框架、安装/使用/安全文档。

### v1.1 建议交付（P1）

- `/loop` 的固定间隔/条件重复运行、后台状态、通知与运行报告；需具备次数、总时长、单次与总预算上限。
- MCP resources/prompts、工具变更通知、OAuth 的完整体验；更多 Provider（OpenAI Responses、Gemini 等）。
- 插件、Hooks、Skills、自定义命令、更多只读子 agent；更完整的 diff/rewind 体验。
- `serve/attach`、客户端 SDK、服务鉴权与并发客户端控制；成本与决策校准报告。

### v1.2 及以后（P2）

- ACP 服务端、A2A 互操作、MCP 服务端模式、OS 级强沙箱、插件进程隔离/签名、长期记忆与工作流市场。
- Desktop 客户端（独立阶段），技术选型在协议验证后决定；候选 Electron/Tauri，但不在当前首版锁定。
- 云端托管、远程执行集群、模型微调和商业化运营。

**范围管理原则**：若进度超出基线，先推迟 P2，再推迟 P1 的增强能力；不得通过降低权限校验、取消评测或跳过安全验证来赶工。

## 1.6 差异化

1. **库优先、CLI 验证**：核心不依赖终端 UI；CLI 是可运行的参考客户端，不是内核本身。
2. **判断与生成分离**：JEV 负责类型受限的判断候选，LLM 负责开放式生成，确定性代码负责精确规则与验收，工具执行副作用。
3. **三角色分工而非泛化多 Agent**：角色职责、权限、预算、交接 schema 固定且可观察，避免多个 Agent 同时改同一份文件。
4. **先证据、再宣称完成**：文件 diff、测试输出、验收规则和来源位置组成 `EvidenceReceipt`；未执行验收就不能标为“已验证完成”。
5. **成本质量双目标**：以同一批任务对比 economy/balanced/max 和全程高推理基线，公布成功率、总成本、延迟和重规划次数，不仅公布平均 token。
6. **协议与模型双可插拔**：Provider、DecisionProvider、MCP、SessionStore、Tool、Runtime 分离，JEV 及任何一家 LLM 都不是核心运行的硬依赖。
7. **可回放、可审计**：事件追加写入；可通过脱敏 cassette 与工具夹具重现相同路径；高风险事件带决策和授权证据。

**工作量初估**：v1.0 P0 基线约 127 人日，尚需以 PoC 结果重新估算；按每周 2.5 人日的兼职投入，纯开发约 51 周，加入约 15%–20% 风险缓冲后约 59–61 周。该数字不是进度承诺；若只保留一个 Provider、核心 MCP tools、三角色最小编排与 goal 最小闭环，可能进一步缩短。

## 1.8 资源与预算

- 人力：1 名主力开发（兼具架构、开发、测试），每周约 15–25 小时。
- 费用：模型 API 调用（开发与评测）预估每月 100–300 美元，可用 DeepSeek 等低成本模型承担大部分回归评测。
- 基础设施：GitHub、GitHub Actions、npm 账号、文档站点（VitePress）。

## 1.9 假设与约束

- 假设：主流模型持续提供稳定的 tool use 接口；MCP 规范保持向后兼容。
- 约束：单人开发，范围必须克制；许可证初定 Apache-2.0；不得内置任何第三方密钥。

## 2.3 重点议题分析

### T2 模型接口形态

四类主流接口：Anthropic Messages（内容块、tool\_use / tool\_result、thinking 块、cache\_control）、OpenAI Chat Completions（tool\_calls 数组、广泛被兼容）、OpenAI Responses（带状态的响应对象、内置工具）、Gemini（function calling、parts）。DeepSeek 等提供 OpenAI 兼容接口，复用 Chat Completions 适配器即可，仅需处理推理内容字段差异。

**决策**：内部采用「内容块」模型（与 Anthropic 最接近，表达力最强），适配器负责降级。每个适配器通过 `capabilities` 声明自己支持的特性（并行工具、thinking、缓存、视觉、结构化输出），内核据此启用或回退，这是「充分发挥模型能力」的关键机制。

### T5 文件编辑策略

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 精确字符串替换（old/new，要求唯一匹配） | 简单、可校验、失败可解释 | 模型需复述原文，多处修改需多次调用 |
| 补丁格式（类 apply\_patch） | 一次多处修改，token 省 | 解析复杂，容错要求高 |
| 整文件重写 | 最简单 | 贵，易丢内容，大文件不可行 |

**决策**：`edit`（字符串替换）为默认，`apply_patch` 为可选工具，由 provider 能力或配置决定对模型暴露哪一个；编辑前强制「先读后写」校验，并检测文件在读取后是否被外部修改。

### T6 上下文管理

1. 工具结果在入历史前按字节与行数截断，保留头尾并提示可分页读取。
2. 达到窗口阈值（如 80%）时，由摘要器压缩较早历史，保留最近 N 轮原文与关键状态（待办、已改文件列表）。
3. 对稳定前缀（系统提示词、工具定义、项目指令文件）启用 provider 的缓存标记。

### T10 插件模型

进程内插件性能好、能力强，但无隔离，只能面向受信代码；MCP 子进程隔离好，但能力局限于工具、资源与提示词。**决策**：两条路并存，插件清单声明能力与所需权限，加载时需用户确认。

### T15 决策层与 JEV（v0.3 修订）

**设计定位**：JEV 是 `DecisionProvider` 的一种实现，不是权限引擎，也不是主 LLM 的替代品。它适合有限选项的类型化判断。官方/项目资料中可见的题型包括 Choice、Score、Noul：Choice 从给定选项中选择；Score 按有序量表打分；Noul 返回答案为 yes 的概率。Noul 不应假定额外存在一个与其等价的通用 confidence 字段。当前资料显示 API 请求体包含 `model`、`state`、`questions`，具体 endpoint、SDK 包名、限额和定价必须在 WP-0 按官方文档再次确认。

**输入边界**：JEV 当前资料声明只支持文本状态（JSON 可序列化为文本），不直接接收图像/音频/视频；请求有 token 上限，超长状态必须先摘要/切片；数值、日期、精确计算、正则匹配和最终权限校验应交给确定性代码。JEV 结构化输出只保证答案形式受限，不保证业务判断一定正确。

**适用问题**：是否将任务交给 hyaki；任务属于哪种有限类型；候选执行计划哪类风险较高；是否满足某个语义性完成条件；失败后应建议重试、升级或请求用户。**不适用问题**：自由文本生成、完整规划、数学计算、权限最终授权、仅靠模型判定的不可逆操作。

**实现策略**：

1. `DecisionProvider` 定义统一的 `judge(request)`，至少支持 `jev`、`llm-judge`、`rule-based` 三种实现；实现和模型版本进入事件日志。
2. 默认 `off`；开发期 `shadow` 只记录不改变行为；只有决策点评测达标且用户明确启用时才允许 `enforce`。
3. v1.0 中 JEV **不得把 `deny` 变成 `allow`，也不能独立批准 write/exec/network 操作**。风险信号可将动作提升到 `ask` 或 `deny`；低风险信号最多作为路由/提示，不绕过既有权限。
4. 决策输入只传最小化、脱敏后的状态摘要和规范化候选动作，不发送主模型自由文本推理、密钥或不必要文件全文；允许用户对所有决策外发设置总开关。
5. 对超时、无效响应、低置信、限流和熔断分别定义失败策略。安全类回退为 `ask/deny`；路由类回退到默认模型与完整工具集；完成度类回退为“未验证”。
6. 概率不等于校准置信度。阈值必须由分场景样本校准，并报告 false allow / false block、覆盖率、成本与延迟。

**资料核实入口**：JEV API 与题型资料见文末参考资料。部分专门汇总页面为独立社区页面，只能辅助定位，不能作为接口/计价的唯一依据。

### T16 CLI 对标：Claude Code、Codex CLI、ZCode、MiMo Code、DeepSeek Harness

对标目标是建立用户熟悉的命令交互与可靠运行机制，不是照抄功能清单。公开资料截至 2026-10-15 显示：Claude Code 提供交互/print 模式、JSON/stream-json、会话恢复、权限模式和子 agent；Codex CLI 强调 `codex` 与 `codex exec`、沙箱与审批策略；MiMo Code 已强调 goal/stop condition、Skills、任务跟踪、子 agent 与工作流；ZCode 将 TUI、Web、Desktop 与 Agent CLI/runtime 组合为同一工作区；DeepSeek Harness 采用插件化 harness，并公开 goal、schedule、preset、guard、session 等包边界。具体功能状态会快速变化，必须以对应官方仓库/文档为准。

| 维度 | 公开实践带来的启发 | SYAOCode 决策 |
| --- | --- | --- |
| 呼出入口 | 一条命令进交互；参数可带初始提示；`exec` 用于脚本 | `syao` 进入 TUI；`syao "prompt"`；`syao -p`/`syao exec` 非交互 |
| 管道与自动化 | stdin/stdout 组合使 agent 可嵌入 CI | 支持管道输入、text/json/stream-json、稳定退出码；stdout 只输出机器协议，诊断走 stderr |
| 权限与执行 | 沙箱边界与审批策略是不同概念 | 分离 `permissionMode`、`sandboxPolicy`、`approvalPolicy`；首版提供应用层围栏，不宣称 OS 级沙箱 |
| 会话连续性 | Continue/Resume、检查点、分支与任务状态 | `--continue`、`--resume`、`resume --last`、检查点与报告 |
| 项目指令与 Skills | 项目级 Agent 指令、按需技能降低重复说明 | `AGENTS.md` 优先，支持导入/识别其他指令文件；Skills 延后开放并按需加载 |
| MCP | CLI 里管理连接、授权、工具并查看状态 | `mcp add/list/get/remove/login/logout`；`/mcp` 看状态；敏感操作默认 ask |
| 子 Agent/工作流 | 多 Agent 适合并行只读分析和结构化 pipeline | 首版固定三角色，先固定流程与交接 schema，避免一开始做任意 agent 市场 |
| Goal / Loop | Judge 防过早停止；长期任务需要 checkpoint 和可取消调度 | goal 验收器优先；loop 必须有最大次数、期限和预算，默认暂停而非无限重试 |
| 插件/Everything-as-plugin | 可扩展性强，也会扩大供应链与信任风险 | 先交付 Tool/Provider/DecisionProvider 接口；插件能力与权限声明后续逐步开放 |
| 服务化与 Desktop | 同一 runtime 被多客户端复用 | `AgentEvent` 和会话 schema 版本化；serve/attach 与 Desktop 后续复用同一 SDK |

**命令兼容原则**：只尽量沿用用户容易理解的命令命名；不宣称 CLI 旗标逐项兼容，不导入其他工具的凭证，不复制其代码、专有提示词或视觉商标。参考产品的版本、许可证、用途限制与公开 API 在 M0 留存审查记录。

### T17 服务化与 Desktop 路线

CLI 默认直接在本进程创建 AgentRuntime；不要求首版必须启动后台服务。v1.1 的 `syao serve` 运行本地服务，`syao attach` 作为客户端连接。服务端通过版本化 API 暴露会话、事件订阅、取消、权限请求与应答、文件 diff 摘要和状态查询。

- 默认绑定 `127.0.0.1` 或本地套接字；非回环监听必须显式指定 host 并使用 token。
- 服务层不是权限绕过通道：服务端仍拥有唯一执行权限，多个客户端不能重复批准同一权限请求。
- HTTP/SSE 可以用于应用层事件订阅，但需要区分 SYAOCode 自身服务协议与 MCP 的 Streamable HTTP，不应混为一谈。
- Desktop 不在 v1.0 范围。其技术选型（Electron/Tauri 等）等到 `serve/attach`、会话迁移与本地安全模型稳定后再做决定。

### T18 三角色 agents：hyaki、sota、common

三角色按“信息规模与任务难度”分工，不按固定的厂商或模型品牌分工。

| 角色 | 主要工作 | 不负责 | 输出契约 |
| --- | --- | --- | --- |
| `hyaki` | 文件/日志/网页分块；事实、数字、标识符、路径、报错提取；层级摘要；证据索引 | 规划最终方案、写文件、运行命令、决定权限 | `Brief`：摘要、事实条目、引用、未确定项、遗漏风险 |
| `sota` | 解读 Brief 和用户目标；任务 DAG、验收定义、风险与回滚方案；失败后的重规划；独立评审 | 执行写操作或直接运行命令 | `Plan`：步骤、依赖、验收器、风险、预算、停止条件 |
| `common` | 按 Plan 实施；执行文件工具、shell、MCP；跑验收命令；收集 diff 与结果 | 越过权限控制、无证据宣布完成 | `Result`：步骤状态、变更、命令结果、错误、证据收据 |

**核心协作流**：请求 → L0 选择入口（或规则短路）→ 必要时 hyaki 建立证据索引 → sota 产出计划 → common 执行 → 确定性验收器验证 → sota 仅在失败/高风险/验收歧义时复核。简单、低风险任务可直接走 common。JEV 只建议是否需要某阶段，调度器还需检查输入大小、预算、权限和用户偏好。

**成本逻辑是待验证假设**：对同一评测任务集比较全程 sota、balanced 和 economy，至少测总费用、通过率、延迟、交接开销、重规划次数和事实遗漏率。若 economy 的成本没有下降或成功率下降超过 5 个百分点，系统应自动推荐 balanced，不应把“多 Agent 一定更省钱”写成事实。

# 四、软件需求规格说明书（SRS）

## 4.1 引言

**目的**：定义 SYAOCode v1.0 的功能需求（FR）与非功能需求（NFR），作为设计、开发、测试与验收的唯一依据。

**读者**：开发者、测试者、插件作者、库使用者。

**产品形态**：一组 npm 包。核心是可嵌入的库，CLI 只是库的一个使用者。

| 包 | 职责 |
| --- | --- |
| `@syaocode/core` | 类型、agent 循环、事件、权限、上下文、会话、钩子、错误体系 |
| `@syaocode/providers` | 各模型接口适配器 |
| `@syaocode/tools` | 内置工具集 |
| `@syaocode/mcp` | MCP 客户端（及可选服务端） |
| `@syaocode/acp` | ACP 服务端与协议适配层 |
| `@syaocode/plugin` | 插件加载与生命周期 |
| `@syaocode/otel` | OpenTelemetry 集成 |
| `@syaocode/testing` | MockProvider、录制回放、评测工具 |
| `@syaocode/cli` | 参考命令行应用（Ink） |
| `syaocode` | 聚合入口，便于一行安装 |
| `@syaocode/decision` | DecisionProvider、问题模型、决策点框架与回放接口；JEV adapter 为 optional peer/subpath |
| `@syaocode/server` | 本地服务 API 与协议定义（v1.1） |
| @syaocode/client | 服务客户端 SDK，供 attach、Desktop 与第三方使用（v1.1） |
| `@syaocode/desktop` | Desktop 客户端（第二阶段，v1.0 不含） |
| `@syaocode/agents` | 三角色（hyaki、sota、common）编排、交接协议、预算统计与预设档位 |

**术语**：Agent 循环＝模型调用与工具执行的往复；Provider＝模型接口适配器；Harness＝包裹模型的运行框架；ACP＝Agent Client Protocol；MCP＝Model Context Protocol。

## 4.2 总体描述

**用户类别**：应用开发者（嵌入库）、CLI 终端用户、插件作者、MCP/ACP 生态方。

**运行环境**：Node.js 22 LTS 及以上；Linux、macOS、Windows；Bun 为兼容目标。

**依赖假设**：模型服务可通过 HTTPS 访问；用户自行提供密钥。

**优先级定义**：P0＝v1.0 必须；P1＝v1.0 应当；P2＝可推迟到 v1.x。

## 4.5 外部接口与约束

- **模型接口**：v1.0 优先一个 OpenAI-compatible Provider 与一个原生 Provider；其他官方 API 按 `Provider` adapter 扩展。
- **协议接口**：MCP 客户端（v1.0）、SYAOCode 本地服务协议（v1.1）、ACP/A2A（v1.x 规划）。
- **文件与进程**：通过 FileSystem、Shell 抽象访问，默认实现基于 Node。
- **约束**：许可证 Apache-2.0；不内置任何密钥；默认不收集遥测。

* **决策服务接口**：JEV 作为可选适配器接入；优先验证官方 SDK 与 REST 契约，endpoint、字段和定价在 WP-0 锁定；其他决策模型按 `DecisionProvider` 接入。

全部 P0 需求对应测试用例通过；NFR 达标；内部评测集通过率 ≥ 60%；高风险项均有已落实的应对措施。

# 七、概要设计说明书

## 7.1 设计原则

1. **库优先**：一切能力先以库 API 提供，CLI 不得使用库之外的私有通道。
2. **事件驱动**：运行过程的唯一对外出口是类型化事件流，UI、日志、持久化、评测都是事件的消费者。
3. **依赖注入**：文件、进程、网络、时钟、日志全部经 `Runtime` 抽象注入，便于嵌入与测试。
4. **能力协商**：不取最小公分母，由 provider 声明能力，内核据此启用或降级。
5. **默认安全**：所有有副作用的工具必须经过统一权限闸门，闸门不可被工具自身绕过。
6. **可替换**：Provider、SessionStore、PermissionHandler、Tool、Logger 均为可替换接口。

**v0.3 补充原则**

- **判断与生成分离**：有限选项内的语义判断交给决策层，开放式生成与推理交给生成层，规则与计算交给确定性代码。
- **非对称安全**：决策层默认只能收紧；即使配置低风险自动批准，也必须先由确定性策略预授权，模型信号不能单独授予权限或覆盖 deny。
- **成本分层**：把最贵的模型留给最需要的环节，读入、摘要、执行分别由更合适的角色承担。
- **一个内核，多个客户端**：CLI 默认在进程内运行内核，serve 让 attach 与 Desktop 共用同一事件协议。

### 7.2.1 三层协同与三角色

```text

┌──────────────────────────────────────────────────────────┐

└──────────────────────────────────────────────────────────┘
        │ 选择处理路径，不授予工具权限
        ▼
┌────────────────────── L1 Generation Plane ──────────────┐
```

## 7.5 一次运行的数据流

1. 应用调用 `agent.run(input)`，得到事件流。
2. 内核读取会话历史，经 ContextManager 组装请求（系统提示、工具定义、消息、缓存标记）。
3. ProviderLayer 协商能力后发起流式调用，增量转换为统一事件。
4. 模型返回 tool\_use 后，ToolPipeline 依次执行：参数校验、PreToolUse 钩子、权限判定、执行、截断、PostToolUse 钩子。
5. 工具结果以 tool\_result 回填历史，进入下一轮；若无工具调用则触发 Stop 钩子并结束。
6. 全程事件同时写入 SessionStore，并分发给订阅者（UI、日志、OTel）。

**v0.3 数据流中的决策点与角色**

1. 步骤 2 之前：决策层 DP-01 判断入口；若待读取内容超过阈值，先由 hyaki 摘要，再由 sota 规划，再交给 common（BR-049）。
2. 步骤 4：每个工具调用先经决策层风险门 DP-03 与注入检测 DP-05，再经规则闸门；决策层结果只能收紧（BR-027）。
3. 步骤 5：无工具调用时，若设置了 `/goal`，先由确定性验收器、再由决策层 DP-07 判定是否真正完成（BR-050）。
4. 失败路径：决策层 DP-08 判断重试、换方法、升级到 sota 或询问用户（BR-047）。
5. 每次决策与每次角色交接均产生事件并写入会话日志（BR-033、BR-045）。

## 7.6 关键设计决策（ADR 摘要）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| ADR-01 | 内部消息采用内容块模型 | 表达力最强，向下适配其他格式比向上还原容易 |
| ADR-02 | 事件流是唯一对外出口 | UI、日志、回放、评测复用同一数据源 |
| ADR-03 | 所有 IO 经 Runtime 注入 | 可嵌入、可测试、可在沙箱或远程环境运行 |
| ADR-04 | 权限闸门位于工具管道中，且在钩子之后、执行之前 | 任何工具（含插件、MCP）无法绕过 |
| ADR-05 | 会话以追加式事件日志为事实来源 | 崩溃可恢复，可分叉、回放与审计 |
| ADR-06 | 插件采用「进程内受信插件」加「MCP 隔离」双轨 | 兼顾能力与安全 |
| ADR-07 | Zod 作为 schema 单一事实来源 | 同时产生运行时校验、类型推导与 JSON Schema |
| ADR-08 | 仅发布 ESM | 降低维护成本，Node 22 已支持 require(esm) |
| ADR-09 | 决策层独立于生成层，判断题与生成题分开处理 | 判断题用专用模型更快更省，且使控制流可审计、可回放 |
| ADR-10 | 非对称权限原则：决策层默认只能收紧 | 模型判断可能出错，错误收紧的代价远低于错误放宽 |
| ADR-11 | DecisionProvider 抽象加降级链 | JEV 为早期访问，需避免锁定，并保证没有 JEV 时系统仍完整可用 |
| ADR-12 | 生成层拆为 hyaki、sota、common，角色间只传结构化交接物 | 差异化配置降低成本；隔离上下文以控制交接开销并限制越权 |
| ADR-13 | 内核可嵌入也可服务化，CLI 默认进程内运行 | CLI 保持简单；serve 为 attach 与 Desktop 铺路 |
| ADR-14 | Desktop 作为同一协议的客户端，列为第二阶段 | 避免过早投入第二套界面，先用 CLI 验证内核与协议 |

## DD-2 Agent 循环

**事件定义（节选）**

```ts
type AgentEvent =
  | { type: 'session.start'; sessionId: string; permissionMode: PermissionMode }
  | { type: 'turn.start'; turn: number }
  | { type: 'text.delta'; text: string }
  | { type: 'thinking.delta'; text: string }
  | { type: 'message.complete'; message: Message; stopReason: StopReason }
  | { type: 'tool.proposed'; call: ToolCall }
  | { type: 'permission.request'; id: string; call: ToolCall; reason: string }
  | { type: 'permission.result'; id: string; decision: 'allow' | 'deny'; by: string }
  | { type: 'tool.start' | 'tool.progress' | 'tool.result'; callId: string /* ... */ }
  | { type: 'usage'; usage: Usage; costUsd?: number }
  | { type: 'budget.warning'; kind: 'tokens' | 'cost' | 'turns'; ratio: number }
  | { type: 'context.compacting' | 'context.compacted' /* ... */ }
  | { type: 'hook'; name: string; outcome: string }
  | { type: 'error'; error: SyaoError; fatal: boolean }
  | { type: 'turn.end'; turn: number }
  | { type: 'session.end'; reason: EndReason };
```

**循环伪代码**

```ts
async function* runLoop(ctx: RunContext, input: UserInput) {
  ctx.history.append(userMessage(input));
  while (true) {
    const stop = ctx.limits.check();                 // BR-010
    if (stop) return yield* end(stop);
    await ctx.context.maybeCompact();                 // BR-013
    const req = ctx.context.buildRequest();
    const assistant = yield* streamModel(ctx, req);   // 含重试，BR-014
    ctx.history.append(assistant);
    const calls = toolCallsOf(assistant);
    if (calls.length === 0) {
      if (await ctx.hooks.stop(assistant) === 'continue') continue;
      return yield* end('completed');
    }
    const results = yield* executeCalls(ctx, calls);  // 分批并行或串行
    ctx.history.append(toolResultMessage(results));   // BR-009
    ctx.steering.drainInto(ctx.history);              // 回合边界注入用户消息
  }
}
```

**工具调用批次划分**：按调用顺序扫描，连续的「只读且并发安全」调用合并为一个并行批次；遇到写类或执行类工具则单独成为串行批次；结果按原顺序回填（BR-008）。

**状态机**

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| Idle | 创建或上一次运行结束 | 调用 run |
| Streaming | 发起模型调用 | 模型流结束或出错 |
| Executing | 收到 tool\_use | 全部结果回填 |
| AwaitingPermission | 权限判定为 ask | 收到用户决定或超时 |
| Compacting | 触达压缩阈值 | 压缩完成或失败 |
| Done / Aborted / Failed | 正常结束 / 被中断 / 致命错误 | 不再迁移 |

**中断**：`AbortSignal` 同时传给 provider 流、工具与子进程；已产生但未执行的 tool\_use，以 `SY-LOOP-003` 的错误结果回填，保证历史合法（BR-009）。

**Steering**：运行中提交的消息进入队列，只在回合边界合并，不打断正在进行的模型流。

```ts
  parallelToolCalls: boolean;
  thinking: 'none' | 'budget' | 'effort';
  promptCache: 'none' | 'explicit' | 'automatic';
  vision: boolean;
  structuredOutput: boolean;
  pricing?: Pricing;
}
```

**流式事件归一化**：各适配器把原生事件转为 `message_start`、`block_start`、`block_delta`、`block_stop`、`usage`、`message_stop(stopReason)`。`StopReason` 统一为 `end_turn | tool_use | max_tokens | refusal | error`。

**适配差异处理**

| 特性 | Anthropic | OpenAI Chat（含兼容服务） | Responses | Gemini |
| --- | --- | --- | --- | --- |
| 工具调用 | tool\_use 块 | tool\_calls 数组 | function\_call 项 | functionCall part |
| 并行工具 | 支持 | 支持（可开关） | 支持 | 支持 |
| thinking | thinking 块，带签名 | 因服务而异（如 reasoning 字段） | reasoning 项 | thought parts |
| 缓存 | 显式 cache\_control | 自动 | 自动 | 显式或自动 |

thinking 内容的回传规则由适配器按各 provider 要求决定，并以合约测试固化，内核只保证 `providerData` 原样保留。以上差异为立项时的认知，WP-0 中须对照最新官方文档核实。

**重试中间件**：`withRetry(provider, policy)` 实现 BR-014；只重试可重试错误；已向调用方发出过内容增量的流，仅当尚无已提交的工具调用时才重放。

**路由**：`ModelRouter` 支持角色 `main`、`fast`（用于摘要、标题等）、`fallback`（主模型连续失败后切换）。

## DD-4 工具系统与内置工具

```ts
interface Tool<I = unknown> {
  name: string;
  description: string | ((ctx: PromptContext) => string);
  inputSchema: z.ZodType<I>;
  risk: 'read' | 'write' | 'exec' | 'network' | 'meta';
  readOnly: boolean;
  concurrencySafe: boolean;
  timeoutMs?: number;
  permissionSubject?(input: I): PermissionSubject;   // 供规则匹配，如路径、命令
  execute(input: I, ctx: ToolContext): Promise<ToolOutput> | AsyncGenerator<ToolProgress, ToolOutput>;
}
```

**执行管道**：`validate → PreToolUse hooks → permission → execute(timeout, abort) → truncate → PostToolUse hooks → tool_result`。任何一步失败都以结构化错误结果回填，模型可据此自我纠正（BR-025）。

**FileStateTracker**：记录每个文件最近一次读取的 `{ path, mtimeMs, hash, range }`，为先读后写与外部修改检测提供依据（BR-004）。

**edit 算法**

1. 解析并规范化路径，经权限闸门。
2. 校验 tracker 中存在读取记录，否则 `SY-FS-001`。
3. 读取当前内容并比对哈希，不一致 `SY-FS-002`。
4. 统计 old 出现次数：0 次 `SY-FS-004`（附近似行提示）；多于 1 次且未指定 `replace_all` 为 `SY-FS-003`（附匹配位置）。
5. 替换后写入临时文件再原子重命名，保持原文件权限与换行风格。
6. 更新 tracker，返回变更摘要与 diff 片段。

**bash 工具**：经 `Shell` 抽象启动子进程，使用独立进程组以便整体终止；输出写入环形缓冲并按 BR-012 截断；工作目录在调用之间保持；支持后台任务（`bash_output`、`kill_shell` 配套工具）；默认超时 120s，可调。

**截断算法**：超出阈值时保留头部 40% 与尾部 60% 的预算，中间以说明替换，并写明如何分页读取剩余内容。

## DD-5 权限与安全

**规则模型**

```ts
interface PermissionRule {
  effect: 'allow' | 'ask' | 'deny';
  tool: string;                        // 工具名或 glob，如 'bash'、'mcp__github__*'
  match?: { path?: string; command?: string; url?: string };  // 参数模式
  source: 'user' | 'project' | 'plugin' | 'code';
}

type PermissionHandler = (req: PermissionRequest) => Promise<PermissionDecision>;
interface PermissionDecision {
  decision: 'allow' | 'deny';
  remember?: 'once' | 'session' | 'project';   // 写回规则的作用域
  message?: string;                            // 拒绝理由，回传给模型
}
```

**判定流程**

1. 若 PreToolUse 钩子返回 deny，直接拒绝（BR-021）。
2. 汇总所有来源的规则，按 deny、ask、allow 的顺序匹配，命中即停（BR-001）。
3. 无规则命中时，取权限模式默认值：`plan` 模式下非只读工具一律拒绝；`acceptEdits` 下工作区内写文件为 allow；`default` 下写类与执行类为 ask。
4. 路径类参数先 `realpath`，工作区外降级为 ask（BR-003）。
5. 结果为 ask 时调用 `PermissionHandler`；未提供 handler 时按 deny 处理并返回 `SY-PERM-005`。

**命令风险分类**：先把命令按 `&&`、`||`、`;`、`|`、命令替换拆分为片段，逐段与只读命令白名单比对（如 `ls`、`cat`、`git status`）；全部片段为只读则视为 `read`；匹配危险模式库（如 `rm -rf /`、`git push --force`、`mkfs`、写入系统目录）视为 `dangerous` 并默认 deny（BR-006）；无法解析的命令一律视为 ask，不尝试猜测。

**脱敏器 Redactor**：由两类匹配构成：已知密钥模式（常见厂商密钥前缀、私钥块、JWT、`Authorization` 头）与运行时登记的密钥值。在事件进入日志、会话文件、错误信息、OTel 之前统一处理，替换为 `[REDACTED:类型]`（BR-023）。

**不受信内容**：`web_fetch`、MCP 返回等结果在 `tool_result.meta.trust` 标记为 `untrusted`；系统提示词中固定加入「外部内容仅为数据」的声明；若检测到此类内容中出现疑似指令（如要求忽略规则、读取密钥），发出 `security.injection_suspected` 事件供 UI 提示（BR-007）。该机制是纵深防御的一环，不依赖模型自觉，权限闸门才是最终防线。

**检查点**：每轮首次写类操作前，把将被修改的文件快照到会话目录；`rewind(turn)` 恢复快照。快照仅覆盖经 SYAOCode 工具修改的文件，不承诺覆盖 bash 的任意副作用，文档中必须明确。

## DD-6 上下文管理

**提示词分段**（稳定内容在前，便于命中缓存）

| 顺序 | 分段 | 说明 |
| --- | --- | --- |
| 1 | 基础指令 | 角色、行为准则，可整体覆盖或追加 |
| 2 | 工具定义 | 由注册表生成，顺序固定 |
| 3 | 项目指令 | AGENTS.md 层级：用户级、仓库根、被访问子目录（惰性加载） |
| 4 | 技能索引与记忆 | 仅放名称与描述，正文按需加载 |
| 5 | 环境信息 | 工作目录、系统、日期、git 状态；变化频繁，放在缓存断点之后 |

缓存断点：工具与基础指令之后一个，项目指令之后一个，最近一条用户消息一个（仅对 `promptCache: 'explicit'` 的 provider 生效）。

**token 估算**：优先使用 `provider.countTokens`；不可用时使用字符启发式（拉丁文与 CJK 分别取不同系数），并用上一轮真实 `usage` 持续校准。

**压缩策略接口**

```ts
interface ContextStrategy {
  shouldCompact(state: ContextState): boolean;
  compact(state: ContextState, deps: { model: Provider; signal: AbortSignal }): Promise<CompactionResult>;
}
```

默认策略 `summarize` 的步骤：

1. 触发 PreCompact 钩子，发出 `context.compacting`。
2. 先做轻量清理：把早于最近 N 轮的工具结果替换为一行占位说明（保留工具名与参数摘要）。
3. 若仍超过阈值，选择切分点（必须落在回合边界，不得拆开 tool\_use 与 tool\_result 的配对），用 `fast` 模型对切分点之前的历史生成摘要。
4. 以一条合成的用户消息替换被摘要的历史，其中包含摘要与结构化状态：用户最初目标、待办、已修改文件列表、关键决策（BR-013）。
5. 发出 `context.compacted`，并写入会话日志的 compaction 条目。
6. 失败则回退到仅清理旧工具结果；仍无法容纳返回 `SY-CTX-002`。

**项目指令**：默认文件名 `AGENTS.md`，可配置兼容名单（如 `CLAUDE.md`）；子目录中的指令文件在 agent 首次读取该目录下文件时注入，而不是启动时全部加载。

## DD-8 MCP 集成

```ts
interface McpServerConfig {
  name: string;
  transport:
    | { type: 'stdio'; command: string; args?: string[]; env?: Record<string, string>; cwd?: string }
    | { type: 'http'; url: string; headers?: Record<string, string>; auth?: 'oauth' | 'none' };
  trust?: boolean;                          // 为 true 才允许规则放行其工具
  enabled?: boolean;
  timeoutMs?: number;
  tools?: { include?: string[]; exclude?: string[] };

```

**生命周期**：`connect`（握手并协商能力）→ `listTools`（处理分页）→ 映射为 `Tool` → 运行 → `close`。断线按指数退避重连，重连后重新获取工具列表并以 `mcp.status` 事件通知；收到 `tools/list_changed` 通知时热更新注册表（FR-074）。

**工具映射**：名称为 `mcp__{server}__{tool}`，仅保留字母、数字、下划线、连字符；超过 64 字符时截断并附短哈希（BR-017）。对 DD-4 的补充：`Tool` 允许携带 `jsonSchema` 覆盖 Zod 生成的 schema，MCP 工具使用该字段向模型暴露原始 JSON Schema，参数校验交给服务器，客户端仅做基础类型检查。

**调用**：`callTool` 带取消与超时；返回内容按类型映射（文本、图片、资源引用、结构化内容）；`isError` 映射为 `tool_result.isError`，同时结果标记为 `untrusted`；风险级别默认 `network` 或 `exec`，即 ask（BR-018）。

**stdio 子进程管理**：stderr 导入 logger；关闭时先 SIGTERM，3 秒后 SIGKILL；父进程退出时确保子进程回收。

**鉴权**：HTTP 传输支持自定义头与 OAuth；令牌经注入的 `CredentialStore` 保存（默认文件权限 0600，可选系统密钥链），并登记到脱敏器。

**resources 与 prompts**：resources 通过 `mcp_list_resources`、`mcp_read_resource` 两个元工具暴露；prompts 映射为自定义斜杠命令（FR-072、FR-102）。

**服务端模式（P2）**：把 agent 封装为单个 `run_task` 工具暴露，复用同一套权限引擎。

**基于能力的 API**：插件拿到的 `api.runtime` 是按清单权限裁剪后的代理（受限域名的 `http`、只读或受限路径的 `fs`），插件通过正常途径只能使用被授予的能力。

**生命周期**

| 状态 | 说明 |
| --- | --- |
| discovered | 在用户目录、项目目录或配置的包名中发现 |

**错误边界**：插件提供的所有回调（工具、钩子、命令）均被统一包装，异常转为 `SY-PLG-005` 并按 BR-019 计数，不向宿主抛出。

## DD-11 钩子、技能、命令与子 agent

**钩子**

```ts
type HookEvent = 'SessionStart' | 'UserPromptSubmit' | 'PreToolUse' | 'PostToolUse'
  | 'PreCompact' | 'Stop' | 'SubagentStop' | 'SessionEnd';

interface HookResult {
  decision?: 'allow' | 'deny' | 'ask';
  reason?: string;
  updatedInput?: unknown;            // 仅 PreToolUse 可用
```

钩子可由代码函数提供，也可配置为外部命令：事件 JSON 从 stdin 传入，stdout 返回结果 JSON，退出码 2 表示阻断。按配置顺序执行，超时默认 10s，`failMode` 默认 `closed`（BR-021）。`updatedInput` 改写后的参数必须重新通过 schema 校验与权限判定。

**技能 Skills（FR-101）**：目录结构 `skills/<name>/SKILL.md`，前置元数据含 `name`、`description`。提示词中只放技能索引（名称加描述）；模型通过 `skill` 工具按需加载正文，正文中引用的相对资源在加载时按路径解析。技能内容同样受 BR-007 约束，不得提升权限。

**自定义命令（FR-102）**：`commands/*.md`，前置元数据加正文模板，支持 `$ARGUMENTS` 占位；也可由插件以代码注册。MCP prompts 映射为同类命令。

**子 agent（FR-103）**

```ts
interface AgentDefinition {
  name: string;
  description: string;               // 供主 agent 决策何时委派
  systemPrompt: string;
  tools?: string[];                  // 必须是父工具集的子集
  model?: string;
  maxTurns?: number;

```

通过内置工具 `task` 委派：新建独立实例，独立历史与预算；权限不得超出父级（BR-022），权限请求冒泡到父级的 `PermissionHandler` 并标注 `agentId`；只读子 agent 可并行，其余串行；仅把最终文本与用量汇总返回给父 agent；子事件以 `agentId` 标注后转发；默认最大嵌套深度 2。

## DD-12 可观测性

**Logger**：`debug | info | warn | error` 四级，结构化字段，默认空实现或写 stderr 由应用决定；所有输出过脱敏器（BR-023）。

**Trace 结构**：`session` span 包含多个 `turn` span，每个 turn 内含 `model.call` 与 `tool.call` 子 span；子 agent 作为子树挂在发起它的 `tool.call` 下。属性命名对齐 OpenTelemetry GenAI 语义约定（字段名以实现时的规范版本为准）。**默认不记录提示词与工具内容**，需显式开启 `captureContent`。

**Metrics**：token 用量（输入、输出、缓存读写）、模型延迟、工具耗时、按错误码计数、压缩次数。

**费用**：`UsageTracker` 按 `Capabilities.pricing` 与 `usage`（含缓存读写）累计，超预算则向 `limits` 报告（BR-010）。

**配置位置**：用户级 `~/.syaocode/config.json`，项目级 `.syaocode/config.json`，本地私有 `.syaocode/local.json`（应加入 .gitignore）。

### DD-13.1 命令体系与呼出方式（v0.3 基线）

命令采用“熟悉的 CLI 习惯 + 自己稳定的 schema”，不承诺逐项兼容其他产品。CLI 一律调用公开内核 API；TUI 和脚本模式只区别输出/交互策略，不各写一套 Agent loop。

```bash
syao doctor
```

#### 输入语法与按键

- `@path`：引用文件/目录，TUI 展示实际解析路径并允许移除；目录先汇总再按需读取，不直接塞入完整上下文。

- `/name`：命令；未知斜杠命令应给出相近建议。
- `Esc`：取消当前生成/子进程并向下传播 AbortSignal。

#### 输出、退出码与协议

| 退出码 | 意义 |
| --- | --- |
| `0` | 任务完成且满足配置的验收策略 |
| `1` | 未分类运行错误 |
| `2` | 参数、配置或协议格式错误 |
| `3` | 权限拒绝/无法满足权限导致任务未完成 |
| `4` | 预算、轮次或总时长上限触发 |
| `5` | Agent 运行结束，但确定性验收失败或未通过 |
| `130` | 用户中断（SIGINT） |

JSON/stream-json envelope 必须包含 `schemaVersion`、`sessionId`、`runId`、事件类型、时间戳与事件 payload。未知非关键事件可忽略；schema 主版本不兼容必须明确失败。stdout 用于协议，stderr 用于人类诊断。

#### MCP CLI 约定

- 用户级配置默认位于 `~/.syaocode/config.json`；项目级 `.syaocode/config.json`；私有本地配置 `.syaocode/local.json`，后者应加入 `.gitignore`。
- 项目级 MCP server、hook、plugin 首次使用前显示来源和权限，请用户确认；清单/命令哈希变化后重新确认。
- 外部 MCP 工具默认 `ask`；server 的只读注解不等于授权，工具描述属于不可信输入。
- MCP 的 stdio 子进程不是强沙箱；其 OS 权限应通过启动环境、容器/OS policy 或独立用户账户进一步限制。

## DD-15 错误处理与韧性（横切）

**错误边界**

| 边界位置 | 捕获内容 | 处理 |
| --- | --- | --- |
| Provider 适配器 | SDK 与 HTTP 异常 | 转为 `SY-PRV-*`，标注 retryable |
| 工具管道 | 校验、执行、超时异常 | 转为 `SY-TOOL-*`，以 tool\_result 回填模型 |
| 插件与钩子包装层 | 第三方代码异常 | 转为 `SY-PLG-*` 或 `SY-HOOK-*`，计数与隔离 |
| MCP 客户端 | 连接与调用异常 | 转为 `SY-MCP-*`，触发重连策略 |
| SessionStore | IO 与格式异常 | 转为 `SY-SES-*`，尽量降级继续 |
| 内核顶层 | 其余未预期异常 | 转为 `SY-INT-001`，事件流以 fatal error 结束 |

**取消树**：`AbortController` 形成「会话 → 回合 → 工具调用 → 子进程」的树，上层取消向下传播。

**资源管理**：会话、子进程、MCP 连接实现 `AsyncDisposable`，支持 `await using`；`agent.close()` 幂等。

**进程级行为**：库不注册 `uncaughtException`、`unhandledRejection` 与信号处理，这些只在 CLI 中处理（NFR-011）。

**背压**：事件总线对每个订阅者使用有界队列。持久化订阅者采用阻塞策略以保证不丢；UI 订阅者可合并连续的 `text.delta`，保证慢消费者不拖垮循环。

**国际化**：错误 `message` 默认英文；`@syaocode/core/i18n` 提供按 code 索引的 zh-CN 消息表（NFR-023）。

## DD-16 决策层（Decision Plane）详细设计

### DD-16.1 目标与边界

`@syaocode/decision` 为有限选项判断提供一致接口。它不执行工具、不保存 provider 密钥、不拥有 PermissionEngine，也不接受“模型说安全所以放行”的调用方式。

### DD-16.2 领域类型

```ts
export type DecisionMode = 'off' | 'shadow' | 'enforce';
export type DecisionKind = 'choice' | 'score' | 'noul';
export type DecisionAction =
  | 'route_hyaki' | 'route_sota' | 'route_common'
  | 'raise_to_ask' | 'raise_to_deny'
  | 'suggest_retry' | 'suggest_replan'
  | 'completion_candidate' | 'unverified';

export interface DecisionRequest {
  decisionPointId: string;
  schemaVersion: number;
  state: unknown;              // 构建之前须经 allowlist + redact
  questions: DecisionQuestion[];
  modelVersion?: string;       // enforce 模式要求固定版本
  timeoutMs: number;
  sessionId: string;
  runId: string;
}

export type DecisionQuestion =
  | { id: string; type: 'choice'; instructions: string; options: { id: string; description?: string }[] }
  | { id: string; type: 'score'; instructions: string; levels: { value: number; label: string }[] }
  | { id: string; type: 'noul'; instructions: string; trueCriteria?: string; falseCriteria?: string };

export interface DecisionAnswer {
  questionId: string;
  type: DecisionKind;
  value: string | number | boolean | null;
  probabilities?: Record<string, number>;
  confidence?: number;          // optional; Noul providers may only provide P(yes)
  rawYesProbability?: number;   // normalize Noul without inventing confidence
}

export interface DecisionResult {
  providerId: string;
  modelVersion?: string;
  answers: DecisionAnswer[];
  elapsedMs: number;
  inputTokens?: number;
  costUsd?: number;
  degraded: boolean;
  errorCode?: string;
}

export interface DecisionProvider {
  readonly id: string;
  judge(request: DecisionRequest, signal?: AbortSignal): Promise<DecisionResult>;
  close?(): Promise<void>;
}
```

**Schema 约束**：`DecisionResult` 的值必须匹配 question type 与已定义候选。不能把未知选项自动映射为 `allow`。无 `confidence` 的输出保持缺失，不能伪造 1.0。超出状态限制、非法概率、缺少题目 ID 或模型版本异常都视为非法响应。

### DD-16.3 决策点注册

```ts
interface DecisionPointDefinition {
  id: string;
  version: number;
  mode: DecisionMode;
  buildRequest(ctx: DecisionContext): DecisionRequest | null;
  allowedStatePaths: string[];
  timeoutMs: number;
  policy(result: DecisionResult, ctx: DecisionContext): DecisionAction;
  onFailure: 'safe_ask' | 'default_route' | 'unverified' | 'keep_all';
  minEvalVersion?: string;
}
```

建议的首批决策点：

| ID | 决策问题 | v1.0 模式 | 允许影响 |
| --- | --- | --- | --- |
| DP-01 | 当前任务是否需要长输入摘要/高推理规划/直接执行 | off/shadow | 仅路由建议，不改权限 |
| DP-03 | 计划动作是否出现更高风险信号 | shadow | 只可升级为 ask/deny |
| DP-07 | 自然语言目标是否看似完成 | shadow | 只能成为候选；不能替代确定性验收 |
| DP-08 | 失败应重试、换方法、重规划还是提问 | shadow | 推荐下一阶段，不直接执行未授权动作 |
| DP-05 | 外部内容是否疑似提示注入 | shadow/P1 | 只用于增加风险或隔离提示 |

所有决策点都必须有版本化样本集。`enforce` 需要通过评测门槛和显式配置；首版不提供“JEV 自动批准工具”的能力。

### DD-16.4 调用顺序与降级

1. deterministic rules 先检查硬约束和预算。
2. 根据决策点生成最小状态：用户目标摘要、当前阶段、工具名、规范化参数的允许字段、已有验收状态；不默认包含代码全文或主模型推理。
3. 状态通过脱敏和长度限制；若超限，先由本地摘要器缩减或回退规则，不把整个会话无差别发给 JEV。
4. 在同一回合内对相同 `stateHash + questionVersion + modelVersion` 去重；缓存范围仅限同一会话且有 TTL。
5. 调用 provider。429/5xx/超时按不同错误分类；安全点回退 ask/deny，路由点使用静态默认值，完成度点回退未验证。
6. `shadow` 只记录“如果 enforce 会采取什么动作”；实际动作沿旧规则执行。
7. `enforce` 只应用决策点白名单中的收紧/路由动作；不能修改权限配置。
8. 产出 `decision` 事件与 `DecisionReceipt`，记录 schema/model/provider 版本、脱敏输入哈希、返回摘要、阈值、决策模式、耗时、成本、降级原因和真实后续结果。

### DD-16.5 JEV adapter 与隐私

JEV adapter 独立放在 `@syaocode/decision-jev`（或作为 optional subpath）中；core 不静态导入专有 SDK。endpoint、模型 ID、凭证来源与重试语义均由配置注入，并在 M0 对官方 SDK/REST contract 验证。密钥只从环境变量或系统密钥链读取。

提供 `decision.egress = allow|deny`、`decision.redactionProfile`、最大外发字符/token、允许字段列表。`deny` 时不得调用任何远端 judge；缺少密钥时自动切换到 off/local rules。日志保存输入哈希与经脱敏摘要，不保存原始密钥或敏感文件全文。

### DD-16.6 校准与准入门槛

- 每个决策点至少准备 100 个代表性样本起步；关键安全评估目标不少于 300 个样本并覆盖对抗变体。样本不足时只做 shadow。
- 报告混淆矩阵、precision/recall、false allow、false block、覆盖率、Brier/ECE（样本允许时）、p50/p95 延迟、每千次成本和人工覆盖率。
- 任何一个已知高风险样本被误判为自动允许即阻止该决策点进入 enforce。
- 模型版本、提示问题版本或状态构造逻辑发生变化后重新跑回归集。

## DD-17 本地服务与客户端协议详细设计（v1.1）

### DD-17.1 目标

把 AgentRuntime 生命周期留在一个服务端，由 CLI attach、未来 Desktop 和第三方客户端订阅事件。该层与 MCP 分开：MCP 用于接入外部工具；SYAOCode Server API 用于控制 SYAOCode 自己的运行时。

### DD-17.2 资源模型

- `Session`: 会话基础信息和事件日志引用。
- `Run`: 一次运行，包含输入、状态、预算、开始/结束时间和结果。
- `Agent`: 当前进程内/服务内的角色实例与父子关系。
- `PermissionRequest`: 待处理权限请求，带过期时间与一次性应答 token。
- `Artifact`: diff、报告、验证输出等可读取产物。
- `Subscription`: 客户端事件订阅；断线后通过事件序号继续读取，是否能够补齐取决于保留策略。

### DD-17.3 初始 HTTP API 草案

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/v1/health` | 健康状态（不返回 secrets） |
| `GET/POST` | `/v1/sessions` | 查询/创建会话 |
| `GET` | `/v1/sessions/{id}` | 会话状态 |
| `POST` | `/v1/sessions/{id}/runs` | 创建一次运行 |
| `POST` | `/v1/runs/{id}/cancel` | 取消运行 |
| `GET` | `/v1/runs/{id}/events` | 事件流订阅（SSE） |
| `GET` | `/v1/permissions/pending` | 当前待审批请求 |
| `POST` | `/v1/permissions/{id}/respond` | 一次性应答；服务端校验权限和超时 |
| `GET` | `/v1/artifacts/{id}` | 读取 diff/报告/安全可公开产物 |

协议须发布 OpenAPI 与事件 JSON Schema，并给出 `schemaVersion`。以上路径是本项目 API 草案，不代表任何外部标准。

### DD-17.4 安全与并发

- 默认只监听 `127.0.0.1` 或本地 socket；远程监听要求显式 `--host`、强 token、TLS/SSH 隧道建议和明显警告。
- token 至少 256 bit 随机；文件权限在 POSIX 环境为 0600；Windows 使用当前用户 ACL；不可写入日志。
- 默认拒绝跨源浏览器请求；如未来 UI 需要，必须采用明确的 origin allowlist 与 CSRF 防护。
- 服务端为每个会话设置 single-writer lease；多客户端可以只读订阅，写入/权限回应需持有 lease 或一次性 token。
- 同一权限请求只能成功响应一次；超时、重复应答和会话关闭均返回结构化错误。
- `serve` 进程关闭时先停止接收新 run，再取消/等待现有 run，最后 flush 事件日志。

## DD-18 三角色 Agent 编排与证据账本详细设计

### DD-18.1 内置角色与能力预算


### DD-18.3 Orchestrator 状态机

1. `INTAKE`: 接收目标、读取工作区元数据，识别用户约束和敏感范围。
2. `ROUTE`: 由规则先判断输入量、任务规模与可用角色；JEV 只提供路由建议。
3. `SYNTHESIZE`: 大输入交给 hyaki；Brief 中每条关键事实必须有引用或显式标记 unknown。
4. `PLAN`: sota 输出 Plan，内核校验步骤依赖、预算、目标路径和验收条件。
5. `APPROVAL`: 预判会触及的权限；一次性把必要高风险操作展示给用户；用户批准仅适用于具体请求范围。
6. `EXECUTE`: common 逐步执行；写入由单一文件协调器串行化；每步记录变更前哈希、diff 和命令结果。
7. `VERIFY`: 运行确定性验收器（测试/类型检查/lint/文件断言）；生成 EvidenceReceipt。
8. `REVIEW`: 验收失败或风险高时把证据交给 sota；最多重规划默认 3 次。
9. `DONE`: 仅当明确验收策略达成才标记 `verified`; 否则输出 `partially_completed`、`blocked` 或 `unverified`。

### DD-18.4 任务路由与成本策略

初始规则建议：小任务（上下文少、≤3 个文件、目标单一）直达 common；输入超过约 20k tokens 或涉及大量文档时优先 hyaki；跨模块设计/多方案/连续失败时调用 sota。20k/10 文件是配置初值，不是通用最优阈值，应通过 PoC-10 调整。

三个预设只是模型/预算策略：

| 预设 | 默认路线 | 适用场景 | 约束 |
| --- | --- | --- | --- |
| `economy` | common 优先；长输入才 hyaki；失败后 sota | 小任务、代码问答、低成本探索 | 总成本最低优先；遇高复杂度必须升级/提示 |
| `balanced` | 大输入 hyaki；sota 做计划；common 执行 | 默认工作流 | 成本、成功率、速度均衡 |
| `max` | 必要时 hyaki；sota 先规划、关键步骤复核；common 执行 | 高影响重构或长任务 | 不意味着权限放宽，仍按预算与确认策略运行 |

### DD-18.5 文件冲突、并行与回滚

- hyaki 可并行读不同片段；任何两个角色不得同时写同一路径。
- common 的写操作先检查工作区、分支、文件哈希是否与 Plan 创建时一致；不一致则重新读取/重规划。
- 每个逻辑步骤生成独立 diff；默认建议工作区位于 Git 仓库并提醒建立 checkpoint，但不假定所有项目都有 Git。
- 文件工具变更可通过反向 diff 尝试回滚；shell 命令、网络调用、数据库变更等副作用需记录为“不保证可回滚”。
- `EvidenceLedger` 持久化来源引用、工具调用、diff、测试和最终判断；只记录必要片段，默认对日志内容脱敏。

## DD-19 Goal / Loop 自治运行详细设计

### DD-19.1 Goal 数据模型

```ts
interface GoalSpec {
  id: string;
  objective: string;
  acceptance: ({ type: 'command'; command: string; expectedExitCode?: number }
    | { type: 'file_exists'; path: string }
    | { type: 'file_contains'; path: string; literal: string }
    | { type: 'custom'; verifierId: string; input?: unknown })[];
  maxTurns: number;
  maxCostUsd: number;
  timeoutMs: number;
  maxReplans: number;
  permissionMode: 'default' | 'plan' | 'acceptEdits';
}
interface GoalReport {
  goalId: string;
  state: 'verified' | 'unverified' | 'blocked' | 'failed' | 'cancelled' | 'budget_exhausted';
  acceptanceResults: { id: string; status: 'pass' | 'fail' | 'unknown'; outputRef?: string }[];
  changedFiles: string[];
  decisionReceipts: string[];
  totalCostUsd: number;
  elapsedMs: number;
  stopReason: string;
}
```

### DD-19.2 Goal 运行循环

```text
validate GoalSpec
  → snapshot workspace state
  → orchestrator run one iteration
  → run deterministic verifiers
  → if all required verifiers pass: verified
  → else if budget/turn/time/replan limit reached: stop + report
  → else if blockers need user or permission: blocked / await in TUI
  → else update plan and continue
```

JEV Noul 可以回答“目标看起来是否满足”作为辅助指标；它不能替代 `command`、测试或文件断言。不存在确定性验收条件时，报告状态最多为 `unverified` 或“语义候选完成”，由用户决定是否接受。

### DD-19.3 Loop 运行模型（v1.1）

`LoopSpec` 必须具备 `trigger`、`maxRuns`、`until`（或明确停止条件）、`perRunBudgetUsd`、`totalBudgetUsd`、`timeoutMs`、`failurePolicy`、`permissionPolicy`。支持 fixed interval、基于明确事件的 trigger；不支持自然语言“永远运行”这种没有结束条件的任务。

- loop 每轮采用新的短上下文，并从 `LoopState` 载入只保留的状态摘要和上轮 `EvidenceReceipt`。
- 每轮有独立 runId，和 loopId 关联；所有日志可追踪到触发事件。
- 无人值守时，任何 `ask` 等同于暂停/拒绝该轮，不可假设用户批准。
- 连续失败 3 次、预算耗尽、最大运行次数达到、工作区分支/权限设置变化、MCP 凭证失效时暂停。
- `pause/resume/stop` 是幂等操作；恢复时重新校验 `GoalSpec`、配置、工作区和授权状态。
- v1.1 只实现本机运行与本地状态；跨设备/云端 scheduler 不在此范围。

### DD-19.4 运行安全与防失控

1. 每个 Goal/Loop 必须提前设定模型费用、回合、运行时长上限；超限时不再发起新模型调用。
2. 对自动执行设置命令与路径 allowlist；禁止动作始终有效，无法询问用户时转为 deny/暂停。
3. 运行前显示将要影响的目录、模型/角色 preset、预算、验收器和授权模式；后台 loop 启动需明确确认。
4. 每轮写入前记录文件快照或哈希；关键变更可以设置“每步确认”或“每轮确认”。
5. 为每轮输出可读报告：做了什么、变更文件、执行命令、验收结果、成本、停止原因和下一步建议。
6. Loop 不是安全监控系统，不应被用于绕过平台/服务的使用条款、访问控制或频率限制。

# 九、错误体系专项设计文档

## 9.1 目标与原则

1. **稳定的错误码**：错误码是公共 API 的一部分，遵循 SemVer；一经发布不得复用或改义。
2. **机器可判定**：调用方只需依据 `code`、`category`、`retryable`、`recovery` 就能决定行为，不必解析 message。
3. **双受众消息**：面向人的 `message` 与面向模型的 `modelMessage` 分开，后者只含纠错所需信息。
4. **不泄密**：错误的 message、details、cause 序列化前一律经脱敏器（BR-023）。
5. **类型化**：对外只抛出 `SyaoError` 及其子类（BR-025），禁止裸 `Error` 与字符串。

## 9.2 SyaoError 设计

```ts
type Severity = 'info' | 'warning' | 'error' | 'fatal';
type Recovery = 'retry' | 'fix_input' | 'ask_user' | 'reconfigure' | 'abort' | 'none';

class SyaoError extends Error {
  readonly code: ErrorCode;                 // 如 'SY-PRV-002'
  readonly category: ErrorCategory;         // 'provider' | 'loop' | 'tool' | ...
  readonly severity: Severity;
  readonly retryable: boolean;
  readonly recovery: Recovery;
  readonly modelMessage?: string;           // 回填给模型的纠错提示
  readonly details?: Record<string, unknown>; // 已脱敏的结构化上下文
  readonly cause?: unknown;
  toJSON(): SerializedError;                // 用于事件、日志、会话文件
  static is(e: unknown): e is SyaoError;
  static wrap(e: unknown, defaults: Partial<ErrorInit>): SyaoError;
}
```

**子类**：`ProviderError`（含 `status`、`requestId`、`retryAfterMs`）、`ToolError`（含 `toolName`、`callId`）、`PermissionError`、`FsError`、`ContextError`、`SessionError`、`McpError`、`ProtocolError`、`PluginError`、`HookError`、`InternalError`。

**序列化**：`{ code, category, severity, retryable, recovery, message, details }`，跨进程（ACP、stream-json）统一使用。`cause` 仅在日志中保留，不进入事件。

## 9.3 编码规则

- 格式 `SY-<域>-<三位序号>`，域为 CFG、PRV、LOOP、TOOL、PERM、FS、CTX、SES、SEC、MCP、ACP、PLG、HOOK、DEC、AGT、RUN、SRV、CLI、INT。
- 序号不复用；废弃的错误码保留在注册表并标记 `deprecated`。
- 插件自定义错误使用 `SY-X-<插件短名>-<序号>`，避免与内核冲突。
- 每个错误码在 `docs/errors/` 有独立页面，由注册表自动生成。

## 9.4 严重级别与恢复策略定义

| 级别 | 含义 | 对运行的影响 |
| --- | --- | --- |
| info | 信息性，行为符合预期 | 无 |
| warning | 已降级或已自动处理 | 继续运行 |
| error | 当前操作失败 | 通常回填给模型，运行继续 |
| fatal | 无法继续 | 事件流以 `session.end` 结束 |

| recovery | 含义 |
| --- | --- |
| retry | 稍后重试同一操作可能成功（由重试中间件处理） |
| fix\_input | 需要调整输入，通常由模型自我纠正 |
| ask\_user | 需要用户决策，如继续、授权、选择 |
| reconfigure | 需要修改配置、密钥或版本 |
| abort | 无法恢复，终止运行 |
| none | 无需处理 |

## 9.6 传播与出口

同一个错误同时走三条出口，内容一致但详略不同：

| 出口 | 内容 | 说明 |
| --- | --- | --- |
| 模型 | `tool_result`（`isError: true`）的 `modelMessage` | 仅 error 级及以下且与工具相关的错误；不含路径之外的内部细节与密钥 |
| 应用 | `error` 事件加最终 `session.end` 的 reason；`run()` 便捷方法在 fatal 时抛出 | 序列化后的 `SyaoError` |
| 观测 | 日志、OTel span 状态与属性 `error.code` | 日志可含脱敏后的 `cause` |

**终止规则**：`fatal` 终止运行；`error` 若发生在工具内则回填模型继续，若发生在 provider 且重试耗尽则终止；`warning` 与 `info` 不终止。

## 9.7 恢复策略

- **重试**：由重试中间件按 BR-014 执行，只处理 `retryable: true`。
- **回退模型**：主模型连续失败（默认 3 次）后切换到 `fallback` 角色，并发出 `warning`。
- **自动压缩**：`SY-PRV-004` 触发一次压缩后重试，仍失败则 `SY-CTX-002`。
- **自我纠正**：`fix_input` 类错误回填模型，同一错误重复出现触发循环检测（BR-011）。

## 9.8 modelMessage 编写规范

1. 先说发生了什么，再说如何纠正。
2. 给出可操作的具体信息（匹配数量、行号、可用工具名、期望的字段类型）。
3. 不包含密钥、工作区外路径、堆栈信息。
4. 简短，不超过 300 字符。

示例（`SY-FS-003`）：`The string appears 3 times (lines 12, 40, 88). Add surrounding lines to make it unique, or set replace_all to true.`

## 9.9 API 约定

- 内部对可预期失败使用 `Result<T, SyaoError>`，只有不可恢复的情况才 `throw`。
- 对外公共异步 API 失败时抛出 `SyaoError`；事件流 API 不抛出，而是通过 `error` 事件与 `session.end` 报告。
- 使用 `SyaoError.is()` 判定，不使用 `instanceof`（避免多份包副本导致失效）。

## 9.10 治理

1. 新增错误码须同时提交：注册表条目、zh-CN 消息、文档页、至少一个触发该码的测试。
2. CI 校验：注册表与文档页一致；每个 `active` 错误码均有测试引用；无未注册的 `new SyaoError` 字面量码。
3. 废弃流程：标记 `deprecated` 并保留一个主版本后才允许从文档移除，编号永不复用。

2. **路径穿越**：`../`、符号链接、Windows 短路径与大小写、UNC 路径、特殊设备文件。
3. **脱敏与泄密**：在所有输出通道检查密钥是否残留。
4. **供应链**：依赖审计、许可证、gitleaks。

**性能测试**：NFR-001、002、003、016 的基准脚本，相对上一基线退化超过 10% 则 CI 失败。

## 12.4 快速开始示例（草案）

```ts
import { createAgent } from 'syaocode';
import { anthropic } from 'syaocode/providers/anthropic';
import { builtinTools } from 'syaocode/tools';

const agent = createAgent({
  model: {
    provider: anthropic({ apiKey: { env: 'ANTHROPIC_API_KEY' } }),
    name: 'YOUR_PROVIDER_MODEL_ID', // 替换为所选 Provider 当前支持的模型 ID
  },
  tools: builtinTools(),
  permissionHandler: async (req) => ({
    decision: (await askUser(`允许 ${req.call.name} 吗？`)) ? 'allow' : 'deny',
    remember: 'session',
  }),
  limits: { maxTurns: 50, maxBudgetUsd: 2 },
});

for await (const ev of agent.run('修复 src/utils 中失败的测试')) {
  if (ev.type === 'text.delta') process.stdout.write(ev.text);
  if (ev.type === 'error') console.error(ev.error.code, ev.error.message);
}

await agent.close();
```

## 12.8 对外安全与隐私声明要点

1. 默认不收集、不上传任何遥测；OpenTelemetry 导出由使用者显式配置，且默认不含提示词与文件内容。
2. 数据只发送到使用者自行配置的模型服务与 MCP 服务；文档需绘制数据流向图。
3. 会话文件保存在本地，可能包含源代码与命令输出，须提示使用者妥善保护目录权限。
4. bypass 权限模式会关闭确认，适用于隔离环境，文档须给出明确的风险警告。
5. 进程内插件不是安全沙箱（DD-10），安装第三方插件等同于运行其代码。
6. 提示注入无法被彻底消除，SYAOCode 提供多层缓解，但不能替代对高风险操作的人工确认。
7. 检查点与回滚只覆盖经 SYAOCode 文件工具修改的文件，不覆盖 bash 命令的任意副作用。
