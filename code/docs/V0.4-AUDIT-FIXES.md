## 3. C-1 修复（安全回归，最高优先级）

**缺陷**：`policy.ts` 的 `presetVerdict()` 只在 `capability.protocol === 'local'` 时咨询 core `PermissionEngine`。因此客户写一条普通 `mcp://**` allow，就等于关闭了 **BR-006 危险命令库 / BR-003 工作区围栏 / 敏感路径清单**。

**本机复现**（修复前）：`rm -rf /`、`/etc/passwd`、`~/.ssh/id_rsa` 经 MCP 边缘 **3/3 succeeded，peer 被调用 3 次**。

**修复**：安全语义是**所有协议的底线**，不是 `local://` 的特例。`presetVerdict` 对所有能力生效，且与规则在**同一优先级**参与裁定（deny > ask > allow），因此只能收紧、不能被 ARF 的 allow 放宽。

**修复后**：三例全部 `denied`，peer 调用 **0** 次。回归测试：`redteam.test.ts` 的「C-1」两条（正向边缘 + ACP 反向）。

## 8. C-3 修复：ACP 提示回合（`session/prompt`）

**缺陷**：`syao serve --acp` 从不注入 `runTurn`，ACP 服务端可以 `initialize`／`session/new`，但每个 `session/prompt` 都以 `-32603 "this agent has no prompt handler"` 失败——设计 §5.5 的 `syao acp --stdio` 场景完全不可用。

**修复**：新增 `packages/cli/src/acp-turn.ts` 的 `createAcpTurnRunner()`，把一次提示回合接到**与 `syao -p` 同一条受治理的 agent 路径**（`installMainPathGovernance`），因此该回合产生的工具调用同样留下 ARF 回执、审计链与预算预留；`rpc-command.ts` 在 `cmd.protocol === 'acp'` 时构建 runner 并注入 `ServeFabricContext.runTurn`（只有 ACP 边缘付出模型配置的代价）。agent 事件映射为 `session/update`：`agent_message_chunk` / `agent_thought_chunk` / `tool_call` / `tool_call_update` / `usage_update`；`stopReasonOf()` 把 ARF 终态映射为 ACP 词汇，**取消 → `cancelled`**（绝不 `refusal`）。

**真机验证**（`serve --acp --stdio`，NDJSON 帧）：
```
initialize  : protocolVersion 1, agentCapabilities{loadSession,promptCapabilities,mcpCapabilities}
session/new : acp_…
prompt      : {"stopReason":"end_turn"}          ← 修复前是 -32603
updates     : 6 → usage_update, tool_call, tool_call_update, agent_message_chunk
agent text  : "agent finished the turn"
```
并且该回合是**受治理**的：随后新进程 `syao rpc audit` 显示 `policy.decide` + `invocation.succeeded` 两条链（§10）。

回归测试：`packages/cli/test/serve-acp.test.ts`（4 项，驱动真实的 `mountServerEdge('acp', …)`，断言 JSON-RPC 应答；未注入 runner 时仍 fail-closed）。

### 8.1 同时修掉一个我引入的帧错误（重要）

上一轮为修 HTTP 帧，把 stdio 通道的 framing 无条件改成 `json-lines`，**同时破坏了 MCP stdio**（MCP 要求 `Content-Length` 帧）。04 C16 明确 ACP stdio 是 **NDJSON**，而 MCP stdio 是 `Content-Length`——framing 必须**按绑定**决定。

修复：提取 `framingFor(protocol, transport)`（`packages/cli/src/serve.ts`），规则为 MCP+stdio → `content-length`，其余（ACP/A2A stdio、所有 HTTP）→ `json-lines`。回归测试 `rpc-command.test.ts` 4 项钉住四种组合。真机复核：MCP stdio 收到正确 `Content-Length` 应答，ACP stdio 收到 NDJSON 应答，MCP HTTP 官方 SDK 互通仍 8/8。

## 9. C-4 修复：治理记录持久化

**缺陷**：内核所有记录都在内存，`syao -p` 跑完回执与审计链随进程消失，`syao rpc audit` 永远 `0 checked`——"可审计"只是接口而非能力。

**修复**：`packages/rpc/src/runtime/file-stores.ts` 提供与内存版**同形状**的文件 store 束，`createFabric({ stores })` 不关心拿到哪一种。记录以 JSONL 落在 `~/.syaocode/arf/<tenant>/`：tasks / sessions / approvals / budget / idempotency / receipts / audit / events（registry/identity/evidence 属派生，仍内存）。CLI 默认启用；`persist: false` 保持测试隔离；显式 `stores` 覆盖优先。

两条完整性规则：
- **加载时校验链**。回执**重算自身哈希**（只比 `prevHash` 会漏掉"链接仍对齐但内容被改"的篡改），审计链逐环校验；被篡改的文件**报错**而不是悄悄成为新的可信链头。
- 事件日志从持久化行恢复每个 task 的 `seq`，重启后**无缺口、无重复**。

**真机验证**（跨进程）：进程 1 执行一次受治理调用 → 进程 2 `syao rpc audit` 显示 `intact (2 checked)` 并列出 `policy.decide` / `invocation.succeeded`；`syao rpc tasks` 看到该任务；预算账户带出已结算的 $0.50。

回归测试：`packages/rpc/test/persistence.test.ts`（5 项，含回执链与审计链篡改负例）、`packages/cli/test/arf.test.ts`（2 项，跨 fabric 可见 + `persist:false` 无落盘）。

> 顺带修掉测试卫生问题：CLI 测试原先在**真实 `~/.syaocode`** 上建 fabric，一次测试运行会写进开发者的家目录。现已显式传 `home`/`persist`。

## 10. C-6 修复：测试质量与入站标签

### 10.1 契约测试改为驱动真实内核（审计的核心批评）

审计指出 `protocols/test/helpers/contract.ts` 的 `GovernedHarness` **在测试助手内部重新实现了一遍**策略/幂等/审批，因此 8 条"通用合约属性"里 #2/#3/#4/#6 由该假实现决定，**删掉治理内核它们照样通过**。

现改为：`run()` 构建**真实 `createFabric`**、挂载真实适配器、走 `fabric.call()`（即完整的十步流水线），回执从内核的 store 读回。三个协议合约套件（MCP 14 / A2A 12 / ACP 21）全部在真内核上运行。

**变异验证（决定性证据）**：临时把 `dispatcher.ts` 的 policy deny 分支改成恒不触发（模拟"内核坏了"）→ 契约套件**立即失败**（`2. a policy-denied invocation never reaches the peer`）。改回后 14/14 通过。这正是审计说"以前做不到"的能力。

改写过程中被真内核暴露并修掉的 3 个**测试自身**的缺陷（假实现掩盖了它们）：
1. 挂载本身会调用 `discover()`，所以"未触达对端"必须断言**增量**而不是绝对 0；
2. 测试租户必须与 rig 的调用租户一致（`ten_test`），否则 I1 会拒绝每一次调用、合约什么都没断言到；
3. `waitForApproval()` 与 presenter 存在竞态：latch 必须在发起调用**之前**上膛，否则释放先于提问、审批超时变 `denied`。

### 10.2 入站协议标签与租户

`packages/cli/src/edges.ts` 的 `invokeGoverned()` 曾对入站 MCP 与 ACP 反向调用硬编码 `protocol: 'native'`，后果有两个：回执的协议字段错误，且 `match.protocols: ['mcp'|'acp']` 的策略规则**永远匹配不到入站流量**。同时它**没有把 `tenantId` 传给 `DispatchContext`**，于是 I1 的租户校验对"来自外部"的流量恰好被跳过。

现按边缘标注协议（MCP 执行器 → `mcp`，ACP 反向网关 → `acp`），并传入宿主租户。真机复核：入站 MCP `tools/call` 的回执 `protocol` 现为 `mcp`（原 `native`）。回归测试 `packages/cli/test/edges.test.ts` 3 项（含跨租户入站被拒的负例）。

## 12. ACP `authenticate` 不再伪造成

原实现无条件 `return { authenticated: true }`：无论代理是否声明过认证方式、客户端传的是哪个 methodId，都回答"已认证"。这与 C-2（`serve --a2a` 伪造成 COMPLETED）是同一类诚信问题——对调用方声称一件没有发生的事。

现按 ACP 语义处理：`initialize` 里 `auth: authMethods.length > 0`；`authenticate` 仅在**声明过该 methodId** 时被接受，未声明任何认证方式 → `-32602 InvalidParams`，未知 methodId → `-32602`，宿主 `verifyAuthenticate()` 返回 false → `-32000 AuthRequired`。回归测试 `acp-server.wire.test.ts`（1 项，断言 wire 上的 `-32602`）。
